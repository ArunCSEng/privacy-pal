What a UUID Is

A UUID (also called a GUID) is a 128-bit identifier written as 36 characters — xxxxxxxx-xxxx-Mxxx-Nxxx-xxxxxxxxxxxx. Its purpose is uniqueness without coordination: two systems can each mint UUIDs and trust they won't collide, so you never need a central authority to hand out IDs. The M position encodes the version and the N position the variant, which is how a tool can read back what kind of UUID it is. This generator makes and inspects them in your browser.

The Versions, and When to Use Each

VersionWhat it isUse for
v4122 bits of randomnessThe general-purpose default when you just need a unique ID
v7Unix-millisecond timestamp + randomness (RFC 9562)IDs that should sort by creation time — ideal as database keys
v1Timestamp + clock sequence + nodeLegacy systems; largely superseded by v7
NilAll zerosA placeholder or "no value" sentinel

For most needs, v4 is the right choice. Reach for v7 when IDs are used as database primary keys: because the timestamp sits at the front, v7 values sort in creation order, which keeps database indexes compact and fast — a well-known weakness of fully-random v4 keys. v7 is the current recommendation for new time-ordered IDs.

A Privacy Note on v1

Classic version 1 UUIDs embed the generating machine's MAC address, which can leak hardware identity. This tool avoids that: it generates a random node value with the multicast bit set, so a v1 UUID from here doesn't expose a real MAC. Even so, prefer v7 for new designs — it gives you time-ordering without the baggage.

UUIDs Identify; They Don't Authenticate

A UUID is an identifier, not a secret. Two cautions matter:

  • Time-based UUIDs reveal when they were made. v7 and v1 contain a readable timestamp — useful for sorting, but it also means the creation time is visible to anyone who has the ID.
  • Don't use v1 or v7 as security tokens. Their timestamp portion is predictable, so they're guessable in part. If you need an unguessable token (a session ID, a password-reset link), use a dedicated random token. A v4 UUID is cryptographically random, but for security tokens it's cleaner to use a purpose-built secret of adequate length than to repurpose a UUID.

Frequently Asked Questions

Should I use v4 or v7?
Use v4 for general-purpose unique IDs. Use v7 when the ID will be a database primary key or otherwise needs to sort by creation time — its leading timestamp keeps indexes efficient, which random v4 keys don't. v7 is the modern choice for time-ordered identifiers.
Are UUIDs guaranteed to be unique?
Not guaranteed, but the collision probability for v4 is so small it's ignored in practice — you'd need on the order of 2.7 quintillion UUIDs for an even chance of one collision. For normal use they're effectively unique without any central coordination.
Can I use a UUID as a secret or session token?
A v4 UUID is cryptographically random, but v1 and v7 contain a predictable timestamp and shouldn't be used as secrets. For session IDs or reset links, use a dedicated random token of adequate length rather than repurposing a UUID, so the security properties are explicit.
Does a v1 UUID expose my MAC address?
Traditional v1 UUIDs can embed the machine's MAC address. This tool doesn't — it uses a random node value with the multicast bit set, so no real hardware address is revealed. For new systems, v7 is preferable anyway.
What do the version and variant mean when I inspect a UUID?
The version (the 13th hex character) says how the UUID was made — 4 for random, 7 or 1 for time-based. The variant (the 17th character's high bits) marks the layout standard, normally RFC 4122/9562. The inspector reads both, plus the timestamp for time-based versions.
