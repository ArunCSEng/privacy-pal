What PBKDF2 Does

PBKDF2 turns a password and a salt into a fixed-length key by running them through a keyed hash (HMAC) many thousands of times. That repetition is the point: it makes each guess slow, so an attacker who steals the output can't test passwords at the speed a plain hash would allow. It's defined in RFC 8018 (PKCS #5) and used for two jobs — deriving an encryption key from a passphrase, and hashing passwords for storage. This tool runs PBKDF2 through the browser's Web Crypto API.

The Parameters

ParameterWhat it's for
PRF (hash)The HMAC hash inside PBKDF2. HMAC-SHA-256 is the standard default
SaltRandom, unique per password. Defeats precomputed tables; stored, not secret
IterationsThe work factor — the main security dial. More iterations, slower guessing
Key lengthOutput size, e.g. 256 bits for an AES-256 key

This tool defaults to 600,000 iterations with HMAC-SHA-256, which is exactly what OWASP currently recommends for PBKDF2 — so the default is production-grade, and the reason a derivation takes a noticeable moment is that it's doing real work. Pick the iteration count so one derivation takes roughly a few hundred milliseconds on your target hardware, and don't go below the default for password storage.

PBKDF2 or Argon2? An Honest Comparison

PBKDF2 is only CPU-hard: it costs time, but not much memory, so attackers with GPUs or custom ASICs can parallelise it efficiently. Newer functions — Argon2id, and also scrypt and bcrypt — are memory-hard, which blunts that hardware advantage. For new password-storage systems, Argon2id is the preferred choice.

PBKDF2 is still the right tool in two cases: when you need FIPS-140 compliance (PBKDF2 is approved; Argon2 generally isn't yet), and when you must interoperate with something that already uses it. It remains secure when configured with a high iteration count — it just asks more of the defender to match the attacker's hardware.

The SHA-1 value is the RFC 6070 test vector, and both match openssl and language libraries given the same inputs — confirming the tool is a standard PBKDF2 implementation. (4096 iterations is used here only so the example matches the published vectors; use the 600,000 default for real work.)

Storing the Result

Unlike Argon2's self-describing output, PBKDF2 returns only raw key bytes. To verify a password later you must store the algorithm, iteration count, salt and key length yourself, alongside the derived key — the derived bytes alone aren't enough. When PBKDF2 is used to derive an encryption key, keep the same salt and iteration count so the key can be re-derived.

How to Use the Tool

Frequently Asked Questions

How many iterations should I use?
At least 600,000 for PBKDF2-HMAC-SHA256, which is OWASP's current recommendation and this tool's default. Tune it so one derivation takes a few hundred milliseconds on your hardware, and raise it over time as hardware gets faster.
Should I use PBKDF2 or Argon2?
For new password storage, Argon2id is generally the better choice because it's memory-hard and resists GPU and ASIC attacks. Use PBKDF2 when you need FIPS-140 compliance or must interoperate with an existing system. PBKDF2 is still secure with a high iteration count.
Does the salt need to be secret?
No. The salt just needs to be random and unique per password so that identical passwords don't produce identical keys and precomputed tables don't work. It's stored alongside the derived key and isn't secret. Use at least 16 random bytes.
Why does computing take a second or two?
Because it's doing 600,000 HMAC iterations by design. That deliberate slowness is what protects against fast password guessing. A faster result would mean a weaker configuration, so the short wait is a feature, not a problem.
What do I need to store to verify a password later?
The derived key plus its parameters: the PRF (hash), the iteration count, the salt and the key length. PBKDF2's raw output isn't self-describing like Argon2's encoded string, so you must record those values yourself to recompute and compare.
