What AES-GCM Does

AES-GCM is authenticated encryption: it keeps data confidential and, at the same time, produces an authentication tag that detects any change to the ciphertext. Decryption checks that tag before returning anything, so a wrong key, a wrong nonce, altered ciphertext or altered associated data all fail cleanly instead of yielding garbage. This tool runs AES-GCM through the browser's Web Crypto API, so the encryption is the same primitive your platform and OpenSSL use.

The Inputs, and What Each One Is For

FieldMeaning
Key128- or 256-bit secret. Both parties need the same key; it's the only secret
IV / nonceA 96-bit value per message. Not secret, but must be unique for a given key
AADAssociated data that is authenticated but not encrypted — e.g. a header or message ID
TagThe 128-bit authentication tag GCM appends; 128-bit is the NIST-recommended length

The tool returns the ciphertext (Base64 and hex), the tag, and a combined package. Web Crypto appends the tag to the ciphertext, so the combined value is what you feed back in to decrypt.

The One Rule That Matters Most: Never Reuse a Nonce

AES-GCM is only secure if each message under a given key uses a unique IV. Reusing the same key-and-IV pair for two different messages is catastrophic: it leaks the XOR of the two plaintexts and exposes the value used to forge authentication tags, breaking both confidentiality and integrity. This is the single most common way GCM deployments fail.

That's why this tool generates a fresh random 96-bit IV for every encryption. A random 96-bit nonce is safe as long as you don't exceed roughly 232 (about four billion) messages under one key; past that, collision risk grows and you should rotate the key or use a counter-based nonce scheme. The IV is not secret, so you can send it alongside the ciphertext — just never repeat it with the same key.

How to Use the Tool

  1. Encrypt: generate (or paste) a key, let it generate a fresh IV, add optional AAD, enter your plaintext, and execute. Keep the key, IV and tag together to decrypt later.
  2. Decrypt: paste the JSON package, or the Base64/hex ciphertext, and supply the matching key, IV and AAD. A failed tag check reports an authentication error rather than returning wrong plaintext.
  3. Change the key size between 128 and 256 bits; both are standard. Keep the tag at 128 bits unless you have a specific reason not to.

Scope and Limits

  • This is a learning, testing and interop tool. It's useful for understanding GCM, checking a payload, or confirming two systems agree — not for managing production secrets.
  • It isn't key management. The key is shown in hex on screen and generated per session. Real systems derive keys with a KDF, store them in a secrets manager or KMS, and rotate them.

Frequently Asked Questions

Why must the IV be unique for each message?
Reusing a key-and-IV pair across two messages leaks the XOR of their plaintexts and the value GCM uses to authenticate, which breaks both confidentiality and integrity. The IV isn't secret, but it must never repeat under the same key. This tool generates a fresh random 96-bit IV each time for that reason.
What's the difference between AAD and plaintext?
Plaintext is encrypted and authenticated. Associated data (AAD) is authenticated but left in the clear — it's for context like a header, version or message ID that you want bound to the ciphertext so it can't be swapped. Decryption fails if the AAD doesn't match.
Is a 128-bit key weaker than 256-bit for GCM?
Both are standard and considered secure. AES-128-GCM is faster and fine for most uses; AES-256 adds margin against future advances. The key size doesn't change the nonce rule — unique IVs matter regardless.
What does an authentication failure on decryption mean?
The tag didn't verify, so GCM refuses to return any plaintext. The cause is a wrong key, a wrong or mismatched IV, mismatched AAD, or ciphertext that was altered. It's working as intended — tampered or mis-keyed data is rejected rather than silently decrypted.
Can I decrypt this output with OpenSSL or another library?
Yes. The tool uses standard AES-GCM, so its ciphertext and tag interoperate with OpenSSL, Node's crypto, and other correct implementations given the same key, IV and AAD. That's a good way to verify a cross-system integration.
