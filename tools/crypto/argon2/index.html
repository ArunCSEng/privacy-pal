What Argon2 Is For

Argon2 is a password-hashing function and key-derivation function: you feed it a password and a salt, and it returns a hash that's deliberately slow and memory-hungry to compute. That cost is the point. An attacker who steals a database of Argon2 hashes can't test billions of guesses per second on a GPU the way they can against a plain SHA-256, because each guess forces them to spend real memory and time. Argon2 won the Password Hashing Competition and is specified in RFC 9106. This tool runs the actual Argon2 WebAssembly implementation in your browser.

The Three Variants

VariantUse it for
Argon2idThe default and the recommended choice for password storage (RFC 9106). A hybrid that resists both GPU cracking and side-channel attacks
Argon2iData-independent memory access, aimed at side-channel resistance. Use only if you specifically need it
Argon2dData-dependent, maximum GPU resistance, but exposed to side channels. For cryptocurrency-style uses, not password storage

If you're unsure, use Argon2id. It's the setting both OWASP and RFC 9106 point to for authenticating users.

The Parameters

  • Memory cost (m), in KiB. The main defence. More memory makes parallel GPU/ASIC attacks far more expensive. This is the knob to raise first.
  • Iterations / time cost (t). How many passes over memory; increases work linearly.
  • Parallelism (p). How many lanes run in parallel; set to the number of cores you'll allow per hash.
  • Hash length and salt. A 32-byte hash is standard. The salt must be random and unique per password; it's stored in the output, so it doesn't need to be secret.

About the defaults: this tool starts at 4 MiB memory, t=3, p=1 so it stays responsive in a browser. That's fine for experimenting, but it's below what OWASP currently recommends for real password storage — a minimum of about 19 MiB (m=19456) with t=2, p=1, or equivalents like 12 MiB with t=3. For production, raise the memory and tune the parameters so one hash takes roughly half a second to a second on your server hardware.

A Worked Example You Can Reproduce

With Argon2id, password correct horse battery staple, salt 0123456789abcdef, m=4096, t=3, p=1 and a 32-byte hash, the tool outputs this encoded string: 

$argon2id$v=19$m=4096,t=3,p=1$MDEyMzQ1Njc4OWFiY2RlZg$L4GG97BxMlE+u3mgGDPLh1+u5UMvLCHQCTxwICszmDc

That's the standard PHC format. Reading it: the variant and version (argon2id, v=19), the parameters (m,t,p), then the Base64 salt and the Base64 hash. Because every parameter is embedded, this one string is all you store, and it interoperates with server libraries like argon2-cffi (Python) or node-argon2 — the same inputs produce the same encoded hash.

How to Use the Tool

  1. Pick a variant (Argon2id unless you have a reason not to) and set the memory, iterations, parallelism and hash length.
  2. Enter a password and generate or type a salt. Leave the salt blank and the tool generates a fresh random one.
  3. Compute to get the PHC-encoded hash and the raw hash in hex.
  4. Verify by pasting an existing encoded hash into the verify field with a candidate password; the tool reports MATCH or MISMATCH, re-deriving the hash from the parameters baked into the encoded string.
  5. Store the encoded string, not the raw hex — verification needs the embedded salt and parameters.

Scope and Limits

  • Hash passwords server-side in production. This browser tool is for learning, testing and verifying; a real login flow runs Argon2 on the server so the password and parameters aren't exposed to the client.
  • Tune parameters to your hardware. The right memory and iteration counts depend on your servers and traffic; benchmark rather than copying a fixed number.
  • One salt per password. Never reuse a salt across users; the generator produces a fresh random one each time.
  • Runs locally. The password, salt and hash stay in your browser — nothing is uploaded.

Frequently Asked Questions

Which Argon2 variant should I use?
Argon2id for password storage — it's the default here and the choice recommended by OWASP and RFC 9106. Argon2i and Argon2d exist for specific threat models; unless you have one, Argon2id is the right answer.
Is the default 4 MiB memory strong enough?
It's fine for trying the tool, but below current guidance for real password storage. OWASP recommends at least around 19 MiB (m=19456, t=2, p=1) or an equivalent trade-off. For production, raise the memory and tune so one hash takes roughly half a second to a second on your hardware.
Why is Argon2 better than SHA-256 for passwords?
SHA-256 is fast, which helps attackers test huge numbers of guesses cheaply. Argon2 is deliberately slow and memory-hard, so each guess costs real memory and time. That narrows the gap between a defender hashing one password and an attacker cracking millions.
Does the salt need to be kept secret?
No. The salt's job is to make each password's hash unique so attackers can't use precomputed tables. It's stored inside the encoded hash in plain Base64. What matters is that it's random and never reused across passwords.
Can I verify a hash made by another library?
Yes, as long as it's a standard Argon2 PHC string. Paste it with the candidate password into the verify field. The tool reads the variant, version, parameters and salt from the string and re-derives the hash to check it, so it interoperates with argon2-cffi, node-argon2 and similar.
