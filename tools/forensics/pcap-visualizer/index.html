⚠️ Limitations & Disclaimer

This is a reader, not a full protocol analyzer. It opens classic libpcap files and decodes the common layers — Ethernet, VLAN, IPv4/IPv6, TCP, UDP, ICMP and ARP — enough to see who talked to whom and how. It does not reassemble TCP streams, follow IPv6 extension headers, decode application protocols above the transport layer, or judge whether traffic is malicious; it reports flags and fields, it does not flag threats. Captures that are not Ethernet, or that use PCAPNG, are outside its scope. Everything runs in your browser and nothing you open is uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them — for deep analysis use a full tool such as Wireshark or tshark.

What This Tool Does

A packet capture, or PCAP, is a recording of network traffic: every frame that crossed an interface, saved byte-for-byte. This tool opens a classic libpcap capture in your browser, walks the packets, and shows them in a table you can filter, with a decoded layer view and a hex dump for whichever packet you select. It is handy when you want to look at a small or medium capture quickly without installing anything, or on a machine where you would rather not. For stream reassembly, application-protocol decoding or large captures, a full tool like Wireshark is still the right choice.

Nothing you open leaves your browser — the file is read into memory locally and every step runs there.

How to Use the Tool

  1. Open a capture — drag a .pcap or .cap onto the dropzone, or click to browse. If you need one to try, tcpdump -i any -c 20 -w test.pcap produces a small file quickly.
  2. Scan the packet table — each row gives No., Time (s) relative to the first packet, Source and Destination, the Protocol, the Length and a Summary Info line.
  3. Narrow it down — the protocol dropdown filters to TCP, UDP, ICMP / ICMPv6, ARP or Other, and the search box filters by IP, MAC, port or any text in the summary. Combine the two to isolate one conversation.
  4. Inspect a packet — click a row to expand its decoded layers alongside a hex-and-ASCII dump of the frame, which is where you confirm what the summary claims.
  5. Page and export — large captures load 100 packets at a time, so use ← Prev and Next → to move through them. Export JSON saves the parsed packets; Clear starts over.

If the file is refused, check it is classic libpcap rather than PCAPNG — Wireshark can re-save it with File > Export Specified Packets in pcap format.

How a Classic PCAP File Is Laid Out

The format is deliberately simple. A file begins with a 24-byte global header: a 4-byte magic number, the version, and a link-layer type. The magic number also encodes byte order and timestamp precision — A1 B2 C3 D4 is big-endian microseconds, D4 C3 B2 A1 the little-endian form, and two further values (A1 B2 3C 4D and its swap) mark nanosecond timestamps. This tool reads all four and sets its decoding accordingly.

After the global header come the packets, each introduced by a 16-byte record header: a timestamp (seconds and sub-seconds), the number of bytes captured, and the original length on the wire. The captured bytes follow, then the next record header, and so on to the end of the file. The tool reads records in sequence, stops cleanly at a truncated final record, and skips zero-length records so a damaged file cannot trap it.

What Gets Decoded

This tool decodes Ethernet captures (link type DLT_EN10MB). For each frame it walks the layers it understands:

LayerDecoded
Ethernet IISource and destination MAC, EtherType. An 0x8100 EtherType is read as an 802.1Q VLAN tag, with the VLAN ID shown and the inner EtherType followed through.
IPv4 (0x0800)Source and destination address, header length, total length, TTL and protocol number.
IPv6 (0x86DD)Source and destination address, payload length, next header and hop limit. The next-header value is treated as the transport protocol; extension-header chains are not followed.
ARP (0x0806)Opcode (request/reply), sender and target IP, rendered as a readable "who has / is at" line.
TCPSource and destination port (with a name for well-known ports), sequence and acknowledgment numbers, and the flag set (SYN, ACK, FIN, RST, PSH, URG).
UDPPorts and length, with a hint for common services (DNS, DHCP, NTP, mDNS, and QUIC on 443).
ICMP / ICMPv6Type and code, with a description for the common ones (echo request/reply, destination unreachable, the IPv6 neighbor-discovery messages).

Anything above the transport layer — the actual HTTP, DNS or TLS content — is shown only as raw bytes in the hex view; the tool summarises the packet, it does not parse the application payload.

A Worked Example You Can Reproduce

If you have Wireshark or tcpdump, make a tiny capture to try it on — for instance a single ping: 

# capture a few packets of a ping to a local address
tcpdump -i any -c 4 -w ping.pcap icmp &
ping -c 2 192.168.1.1

Open ping.pcap here and you will see the echo requests and replies in the table, each marked ICMP, with source and destination IPs and an info column reading "Echo (ping) Request" or "Echo (ping) Reply". Select a row and the layer view breaks it into Ethernet, IPv4 and ICMP, while the hex pane shows the raw frame with the familiar ping payload bytes on the right. The duration and total-bytes figures in the summary come straight from the record headers, so they match what Wireshark reports for the same file.

Where This Is Useful

  • A quick look without tooling: glance at a capture on a machine that has no analyzer installed, or when you only need to see the conversation at a glance.
  • Captures with sensitive content: traffic can contain internal addresses, hostnames and cleartext data, so keeping the file in your own browser rather than uploading it to a web service avoids handing that to a third party.
  • Learning the wire format: the layer view beside the hex dump makes it easy to see exactly which bytes become the MAC addresses, the IP header, the ports and the TCP flags.
  • Triage before deep analysis: find the packets of interest here, then open the same file in Wireshark for stream reassembly and application decoding.

Frequently Asked Questions

What file formats can this tool open?
Classic libpcap captures (.pcap, .cap) in either byte order and with microsecond or nanosecond timestamps. It reads the 24-byte global header, then each packet record, in your browser. PCAPNG files are detected and declined with a message; export them from Wireshark as classic pcap first.
Which protocols does it dissect?
For Ethernet captures it decodes Ethernet II, 802.1Q VLAN tags, IPv4, IPv6, ARP, and then TCP, UDP, ICMP and ICMPv6, showing ports, flags, addresses and a short summary per packet. Captures with a non-Ethernet link type are listed but not dissected beyond that.
Can it open a PCAPNG file?
Not directly. PCAPNG is a different, block-based format. This tool recognises it and asks you to re-save as classic pcap, which Wireshark and tshark can do with File > Export Specified Packets or the pcap format option.
Does it handle 802.1Q VLAN frames?
Yes. When a frame's EtherType is 0x8100 the parser reads the VLAN ID, then continues to the inner EtherType and decodes the Layer 3 header (IPv4 or IPv6) that follows. A single VLAN tag is handled; stacked (QinQ) tags are not.
Is my capture uploaded anywhere?
No. The file is read into memory in your browser with the FileReader API, and all parsing, filtering, the hex view and the JSON export run there. Nothing you open is sent to a server; the page makes no network request for your capture.
