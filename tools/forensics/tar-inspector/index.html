⚠️ Limitations & Disclaimer

This inspects an archive's headers; it does not extract to disk or give a safety verdict. It parses the 512-byte TAR headers, verifies checksums, and flags common risks — path traversal, absolute paths, SUID/SGID and sticky bits, non-zero trailer data — so you can look before running tar. It checks each entry's stored path on its own, so a two-stage symlink trick (a link to /etc followed by a write through it) is not something a single-entry check resolves, and a crafted archive can still carry risks it does not model. For gzip it decompresses in the browser; other compressors are out of scope. Everything runs in your browser and nothing you open is uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them, and evidentiary work belongs in a proper forensic environment.

What This Tool Does

A TAR archive bundles files and their metadata into one stream. Opening one with tar -xf writes its contents to disk — which is exactly what you do not want to do blindly with an untrusted archive, because a malicious entry can try to write outside the folder you extracted into. This tool lets you look first: drop in a .tar (or gzip-compressed .tar.gz) and it lists every entry, shows each header's fields, verifies the checksums, and flags entries that look dangerous — all by reading the headers, without extracting anything. It runs in your browser and uploads nothing.

How to Use the Tool

  1. Open an archive — drag in an uncompressed .tar or a gzip-compressed .tar.gz or .tgz. Gzip is decompressed in the browser; bzip2, xz and zstd are not handled, so convert those to a plain .tar first.
  2. Check the risk count before anything else — that is the reason to inspect rather than extract. A non-zero count means at least one entry would write outside the folder you extract into.
  3. Read the entry table — each row shows the Type, File Path, Size, Mode, Owner (UID/GID), MTime (UTC) and an Integrity column carrying the header checksum result. Flagged paths are highlighted.
  4. Narrow a large archive — the filter box matches on filename, owner, type or anomaly, so you can list just the flagged entries in an archive with thousands of files.
  5. Inspect or extract one entry — click a row to open its full header detail with a preview of its contents, and use Download Entry File to pull out that single file without unpacking the archive.
  6. Keep a record — Export Manifest JSON saves the full entry list; Clear Workspace resets.

Pulling one file out individually is the safe way to retrieve something from an archive you do not trust enough to run tar -xf on.

How TAR Is Laid Out

Unlike ZIP, TAR has no index at the end; it is a plain sequence. Each entry is a single 512-byte header block — holding the file name, size, mode, owner, modification time, a type flag and a checksum, with numeric fields stored as ASCII octal — followed by the file's data padded up to the next 512-byte boundary, then the next header. The archive ends with two all-zero blocks. The tool walks this sequence block by block, reads each header, and skips over each entry's data to find the next one.

Formats and Long Names

The tool recognises the common variants. USTAR (the ustar magic at offset 257) adds a 155-byte prefix field, extending the path limit beyond the original 100 characters. GNU tar stores over-long names and link targets in special pseudo-entries (type flags L and K). PAX uses extended header records (type flags x and g) of UTF-8 key/value pairs for arbitrarily long paths, large sizes and precise timestamps. The tool reads these so an entry's real name is shown, not a truncated one.

Checksums and Risk Flags

Every header has a checksum over its 512 bytes, with the checksum field itself counted as spaces. Because early Unix summed bytes as signed and later systems as unsigned, the tool computes both and accepts the header if either matches; a header matching neither is flagged as corrupted or altered. Alongside that, each entry is checked for:

  • Path traversal — a name or link target containing ../ or ..\, or beginning with / (the Tar-Slip pattern).
  • Risky permission bits — SUID, SGID or the sticky bit set in the file mode.
  • Suspicious or hidden paths, and non-zero trailer data after the end-of-archive marker, which can hide appended content.

Flagged entries are counted and highlighted, and you can open an entry to see its header detail and a hex or text preview of its data.

A Worked Example You Can Reproduce

You can build a deliberately malicious archive to see the flagging work. On any Unix-like system: 

# craft an entry whose path escapes the extraction folder
mkdir -p demo && echo pwned > demo/payload
tar -cf evil.tar --transform 's#demo/#../../../tmp/#' demo/payload

Open evil.tar here and the entry's stored path shows as ../../../tmp/payload, flagged with a Path Traversal Risk, and the risk count is non-zero — a warning you would not get until too late if you had simply run tar -xf. A normal archive of the same files, created without the transform, lists the same entries with no flags. Either way the SHA-256 in the summary matches sha256sum on the file.

Limits Worth Knowing

  • Single-entry checks: each path is judged on its own, so a two-stage symlink attack (a link entry plus a later write through it) is not resolved by a per-entry path check.
  • gzip only: .tar.bz2, .tar.xz and .tar.zst are not decompressed — convert them to a plain .tar first.
  • Structural, not behavioural: the flags are heuristics on header fields; a clean result means nothing obvious was found, not that the archive is safe to extract.

Frequently Asked Questions

How is a TAR archive structured?
TAR is a sequential stream, not a format with a central index like ZIP. Each file is one 512-byte header block (name, size, mode, checksum and more) followed by its data padded up to a multiple of 512 bytes, then the next header, and so on. The archive ends with two all-zero 512-byte blocks. This tool walks that sequence block by block.
What is Tar Slip, and how does inspecting headers catch it?
Tar Slip (a path-traversal flaw) is when an entry's name or link target points outside the extraction folder — using ../ or an absolute path like /etc/cron.d/x — so a careless extractor overwrites files elsewhere. Reading the header shows the stored path before you extract, so this tool flags entries whose path contains ../ or ..\ or begins with /. Verify a flagged archive before running tar on it.
How is the TAR header checksum verified?
Each header carries a checksum computed over all 512 bytes with the checksum field treated as spaces. Because old Unix systems summed bytes as signed and newer ones as unsigned, this tool computes both and accepts the header if either matches the stored value. A header that matches neither is flagged as corrupted or tampered.
Does it open compressed .tar.gz files?
Yes for gzip: it detects the gzip header and decompresses in the browser with the built-in DecompressionStream API before parsing. Other compressors — bzip2 (.tar.bz2), xz (.tar.xz), zstd (.tar.zst) — are not handled; decompress those to a plain .tar first and open that.
Is my archive uploaded anywhere?
No. The file is read into memory in your browser, and the decompression, parsing, SHA-256 hash and entry previews all run there. Nothing you open is sent to a server; the page makes no network request for your archive.
