How TAR Archive Structure Works

The Tape Archive (TAR) format specifies an uncompressed sequential byte stream structured into contiguous 512-byte blocks. Each archived item begins with a 512-byte header block defining file metadata, followed immediately by the payload data rounded up to the nearest 512-byte multiple, followed by a 1024-byte zero-block end-of-archive marker.

Supported Format Standards & Field Offsets

  • V7 (Early Unix): Legacy headers containing basic 100-character name, 8-character octal mode, UID, GID, size, mtime, and checksum fields.
  • POSIX USTAR (IEEE Std 1003.1): Introduces the ustar\0 magic signature at offset 257, uname/gname text strings, and a 155-byte prefix field allowing total paths up to 256 bytes.
  • GNU TAR: Extends USTAR with ././@LongLink blocks (types L and K) to accommodate arbitrarily long filenames and symlink targets without string truncation.
  • PAX Extended Format (POSIX.1-2001): Uses typeflag x and g blocks formatted with UTF-8 key-value records to support nanosecond timestamps, unlimited file sizes, and international paths.

Forensic Checksums and Threat Audits

This analyzer performs the following client-side forensic validations:

  • Checksum Recalculation: Sums all 512 bytes with the 8 checksum bytes (offset 148–155) treated as ASCII spaces (0x20), verifying both unsigned and signed sums to detect tampered headers.
  • Path Traversal Risk (Zip Slip / Tar Slip): Flags archive entries utilizing directory traversal strings (../, absolute root /, or Windows drive prefixes) designed to escape extraction target roots.
  • Privilege Escalation Artifacts: Highlights SUID (04000) and SGID (02000) permission bits that could introduce security vulnerabilities if extracted onto Unix hosts.
  • Trailer Slack & Anomaly Detection: Evaluates bytes beyond the standard two 512-byte zero blocks to discover steganographic payloads or hidden slack data.
