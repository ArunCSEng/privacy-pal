⚠️ Limitations & Disclaimer

This is a denylist sanitizer for triage and convenience, not a guarantee. It parses the SVG as an XML DOM and removes elements, event handlers and URIs known to be dangerous, and lists each change in an audit log. Because it removes what it knows to be bad rather than keeping only what is known to be safe, a novel, obfuscated or browser-specific (mXSS) vector could slip through. Why an SVG Is Not Just an Image

A PNG or JPEG is a block of compressed pixels — there is nothing in it to execute. An SVG is different: it is an XML document that the browser parses much like a small web page. The SVG standard allows a <script> element, on* event handlers such as onload and onerror, hyperlinks, embedded HTML through <foreignObject>, and SMIL animation. When an SVG is rendered in an active context — opened directly, inlined into a page, or embedded with <iframe>/<object> — that markup can run JavaScript in the page's origin. That is the cross-site-scripting (XSS) risk a user-uploaded SVG carries, and why it should be cleaned before being trusted.

What This Tool Does

Drop in an SVG and the tool cleans it in your browser and shows you exactly what it changed. It works on the document structure, not by blind text search:

  1. It first strips <!DOCTYPE> and <!ENTITY> declarations from the text, which removes the surface for XML-entity attacks before parsing.
  2. It parses the file into an XML DOM and confirms the root really is an <svg>.
  3. It removes known-dangerous elements — script, foreignObject, iframe, object, embed, style, form controls and others — matching on the local element name so a namespace trick cannot hide them.
  4. It strips every on* event-handler attribute, and javascript:, vbscript: or data: URIs on href, src and SMIL animation values, plus dangerous CSS in style attributes.

Every removal is written to an audit log, and the result is shown three ways: the cleaned source, a SHA-256 hash of it, and a preview rendered through an <img> tag — the browser's own restricted mode, so nothing in the file runs while you look at it. You can download the cleaned SVG.

How to Use the Tool

  1. Open an SVG — drag in the file you want to clean, or paste its markup. A user-uploaded or downloaded SVG you intend to inline into a page is exactly the case this is for.
  2. Read the audit log first — this is the most useful output. It lists every element, event handler and URI that was removed, so you learn what the file was actually carrying rather than just getting a cleaned result. A threat count of zero means nothing matched the rules.
  3. Check the preview — the cleaned image is rendered through an <img> tag, which is the browser's restricted mode, so nothing in the file can run while you look at it. Confirm the artwork still looks right after sanitising.
  4. Compare the source — the cleaned markup is shown alongside a SHA-256 of the result, so you can diff it against your original if you need to justify the change.
  5. Take the file — Download Sanitized SVG saves the cleaned version; Reset Analysis clears the workspace.

For anything you will serve to other users, treat this as a first pass and keep a maintained allowlist sanitiser plus a strict Content-Security-Policy in the pipeline behind it.

Why Structure, Not Regex

Searching for <script> with a regular expression is easy to evade: mixed case, split tokens, CDATA sections, entity encodings and namespace aliases all defeat simple text matching. Parsing into a DOM and inspecting real elements and attributes is far more reliable, which is the approach here. The one text-level step is removing DOCTYPE/ENTITY before parsing, which is a deliberate pre-pass to take entity-expansion tricks off the table.

Limits Worth Knowing

  • Denylist, not allowlist: it removes known-bad constructs. A maintained allowlist sanitizer like DOMPurify, which keeps only known-safe markup, is the stronger choice for production use.
  • mXSS and engine quirks: browsers parse edge-case markup differently, and mutation-XSS can turn seemingly safe markup dangerous on insertion. Cleaning is one layer, not the whole defence.
  • Prefer safe embedding: render untrusted SVGs with <img> or as a CSS background rather than inlining them, add a strict CSP, and serve them from an isolated origin.

Frequently Asked Questions

Why can an SVG run JavaScript when a PNG or JPEG cannot?
A PNG or JPEG is just compressed pixels. An SVG is an XML document that the browser parses like a small web page: it can contain a script element, on* event handlers, links, embedded HTML via foreignObject, and SMIL animation. Rendered in an active context, that markup can run JavaScript, which is why an untrusted SVG needs cleaning or careful embedding.
Does loading an SVG with an HTML img tag make it safe?
Largely, yes. Browsers render an SVG loaded through an <img> tag in a restricted mode where scripts and external loads do not run, which is also how this tool previews the cleaned file. The danger is the other ways an SVG is used: opened directly, embedded via <iframe>, <object> or <embed>, or inlined into a page with innerHTML — there its scripts can run. Sanitizing matters most when the SVG will be inlined.
What exactly does this tool remove?
It strips DOCTYPE and ENTITY declarations from the text, then parses the XML and removes known-dangerous elements (script, foreignObject, iframe, object, embed, style, form fields and others), every on* event-handler attribute, javascript:/vbscript:/data: URIs on href, src and SMIL animation values, and dangerous CSS in style attributes. Each removal is listed in the audit log.
Is this as thorough as DOMPurify?
Not necessarily. This tool uses a denylist — it removes things known to be dangerous — which is good for triage and for seeing what a file contains, but a denylist can miss a novel or obfuscated vector. For production, a maintained allowlist sanitizer such as DOMPurify (which keeps only known-safe markup) is the stronger choice. Use this tool to inspect and clean, and defence-in-depth (CSP, serving from an isolated origin) alongside it.
Is my SVG uploaded anywhere?
No. The file is read and parsed in your browser, the cleaning and the SHA-256 hash run there, and the preview is built from the cleaned file locally. Nothing you open is sent to a server; the page makes no network request for your file.
