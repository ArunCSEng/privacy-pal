    ⚠️ Limitations & Disclaimer

    This opens and queries a live SQLite database; it is not a recovery or forensics suite. It reads the tables, views and schema that the database engine exposes and runs the SQL you type against an in-memory copy, so your original file is never changed. It does not recover deleted rows from free space, read the -wal write-ahead log alongside the .db, or open encrypted databases such as SQLCipher. The sql.js engine (script and WebAssembly) is fetched once from a public CDN, so the page needs the network to start; after that your file is handled only in your browser and is not uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them, and for evidentiary work verify hashes against a write-blocked source image.

    What This Tool Does

    SQLite packs an entire relational database — tables, indexes and data — into a single file, which is why it turns up everywhere: phone apps, browsers, and desktop software all store data in .db, .sqlite or .sqlite3 files. This tool opens one in your browser so you can browse its tables, read the schema and run SQL against it, then export results to CSV. It is handy for a quick look at a database without installing anything, and for keeping a sensitive file on your own machine rather than uploading it to an online viewer.

    It runs on sql.js — the real SQLite engine compiled to WebAssembly — so the SQL it runs is genuine SQLite. The engine loads from a CDN the first time the page opens; your database itself is read locally and never sent anywhere.

    How to Use the Tool

    1. Open a database — drag in a .db, .sqlite, .sqlite3 or .sqlitedb file. It is loaded into an in-memory copy, so your file on disk is never modified no matter what you run.
    2. Find the table you want — the table list is on the left, and the Filter tables box narrows it quickly in a database with dozens of them. Selecting a table shows its rows.
    3. Check the structure — Inspect Schema shows how each table is defined, including column types and keys, which is worth a look before writing a query against unfamiliar data.
    4. Run your own SQL — type a statement in the editor and click Execute SQL. It is real SQLite, so joins, aggregates and PRAGMA statements all work; start with something like SELECT * FROM table_name LIMIT 100; to see the shape of the data.
    5. Export or finish — Export CSV saves the current result set, and Close DB discards the in-memory copy.

    Because edits only touch the copy in memory, you can safely test an UPDATE or DELETE here — reopen the file afterwards and the original data is still there.

    How It Works, Safely

    When you open a file, the tool first checks the 16-byte header every SQLite 3 file begins with (SQLite format 3\0); if it is absent, the file is not a SQLite binary and the tool says so. It then loads the whole file into an in-memory copy inside the WebAssembly engine and lists the tables and views from sqlite_master. Every query you run — including ones that change data — acts on that in-memory copy only. The file on your disk stays exactly as it was, so you can experiment freely; reloading the page simply discards the working copy.

    Browsing, Querying and Exporting

    Pick a table to see its rows, or write your own SQL — a filtered SELECT, a join, an aggregate — and run it. The schema view shows how each table is defined, and any result set can be exported to CSV. Because it is full SQLite, the usual tools are available: PRAGMA table_info('t') for columns, SELECT sql FROM sqlite_master for the full schema, and so on.

    A Worked Example You Can Reproduce

    You can make a tiny database to try it. With the sqlite3 command line: 

    sqlite3 demo.db "CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO users(name) VALUES ('alice'), ('bob');"

    Open demo.db here and the users table appears in the list; selecting it shows the two rows. Run SELECT name FROM users WHERE id = 2; and you get bob. Now run DELETE FROM users WHERE id = 1; — the result set updates to show only bob, but that change lives only in memory: reopen demo.db from disk and alice is still there, which is the clearest way to see that the tool never writes back to your file.

    Where This Is Useful

    • A quick look at app data: inspect a browser history file, a messaging app's store, or any application's SQLite database without a desktop tool.
    • Sensitive databases stay local: an app database can hold personal data, so opening it in your own browser avoids uploading it to a web service.
    • Ad-hoc querying: run a real SQL query over a .db you were handed, and export the answer, with nothing to install.
    • Learning and testing: because changes are in-memory only, it is a safe place to try SQL against a copy of a real database.

    Frequently Asked Questions

    Is my database uploaded anywhere?
    No. Your database file is read into memory in your browser and never sent to a server. The one thing fetched over the network is the sql.js engine itself (its script and WebAssembly), loaded from a public CDN the first time the page runs; after that, opening and querying your file needs no network.
    Can running a query change my original file?
    No. The tool works on an in-memory copy of the file. Even an UPDATE, INSERT, DROP or CREATE only changes that copy in the browser's memory; the file on your disk is not touched. Close or reload the page and the in-memory changes are gone.
    Why does it say the file is not a valid SQLite database?
    Every SQLite 3 file starts with the 16-byte header SQLite format 3\0. If that is missing, the file is something else: a plain .sql text dump (open it as text, or import it), an encrypted database such as SQLCipher (sql.js cannot open it without the key), or a corrupted file. The tool checks this header before trying to open the database.
    Can it recover deleted rows?
    No. This viewer runs normal SQL through sql.js, so it sees only live rows the database engine returns. Deleted rows can linger in a database's free space until overwritten, but reading them requires a carving tool that scans the raw pages; that is outside what this tool does.
    Do I need the -wal and -shm files too?
    For a database in WAL mode, recent changes can live in a companion -wal file rather than in the main .db. This tool opens only the single .db file you give it, so if you open a .db whose recent writes are still in its -wal, you may see a slightly out-of-date picture. Checkpoint the database, or use a tool that reads the .db and -wal together, when that matters.
