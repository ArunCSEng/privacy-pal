The Critical Mechanics of Zip Slip (CWE-22)

Among software supply-chain vulnerabilities, few architectural flaws possess the destructive simplicity and widespread impact of Zip Slip. Disclosed broadly in 2018 by the Snyk security research team, Zip Slip is a widespread arbitrary file overwrite vulnerability that occurs when an archive containing directory traversal filenames is extracted by an application using vulnerable decompression logic.

Formally categorized under CWE-22: Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal'), Zip Slip affects virtually any archive format that encapsulates hierarchical directory trees—including standard .zip, Java .jar and .war archives, Android .apk packages, Microsoft Office Open XML documents (.docx, .xlsx, .pptx), .tar, .cpio, and .7z files.

The vulnerability does not stem from a flaw in the archive specification itself, nor does it require memory corruption or buffer overflows. Rather, it exploits an unstated, perilous assumption made by application developers: the belief that archive entry names are benign, relative paths confined to the folder where they are being extracted.

When an unarchiving library or custom developer script concatenates a designated destination directory (e.g., /var/www/uploads/) with an attacker-crafted archive entry path (e.g., ../../../../etc/shadow) without validating canonical path boundaries, the operating system's filesystem resolver traverses upwards out of the intended directory. The resulting write operation lands in arbitrary filesystem locations, allowing an unauthenticated attacker to overwrite mission-critical files, inject scheduled tasks, place web shells, or replace executable binaries.

Deep Dive: The Binary Architecture of PKZIP Archives

To understand why Zip Slip is so ubiquitous and how this scanner detects it without extracting payload data, one must understand the internal architecture of the PKZIP file format, designed by Phil Katz in 1989.

Unlike simple sequential file streams, a ZIP file is structured into three distinct logical segments: 

[PKZIP File Layout]
+------------------------------------------------------------------+
| Local File Header 1 (0x04034B50) + Compressed Payload Data 1     |
+------------------------------------------------------------------+
| Local File Header 2 (0x04034B50) + Compressed Payload Data 2     |
+------------------------------------------------------------------+
| ... Local File Header N + Compressed Payload Data N              |
+------------------------------------------------------------------+
| Central Directory Header 1 (0x02014B50)                          |
+------------------------------------------------------------------+
| Central Directory Header 2 (0x02014B50)                          |
+------------------------------------------------------------------+
| ... Central Directory Header N                                   |
+------------------------------------------------------------------+
| End of Central Directory Record (EOCD - 0x06054B50)              |
+------------------------------------------------------------------+

1. The Central Directory vs. Local File Headers

Every entry in a ZIP file possesses two independent records containing metadata:

  • Local File Header (LFH): Precedes each chunk of compressed payload data at the start of the archive. It contains file sizes, compression method (e.g., DEFLATE, BZIP2, or uncompressed Store), CRC-32 checksums, and the filename.
  • Central Directory (CD) Header: Clustered together near the very end of the file. This acts as the authoritative table of contents for the entire archive. It repeats the filename, flags, and attributes, while providing a 32-bit pointer indicating the exact byte offset where the corresponding Local File Header begins.

2. The End of Central Directory (EOCD) Record

Standard archive utilities do not read ZIP files from front to back. Instead, they seek directly to the end of the file to find the End of Central Directory (EOCD) record, identified by the 4-byte signature 0x06054B50 (or PK\x05\x06).

The EOCD record specifies:

  • The total number of Central Directory records on this disk.
  • The total size of the Central Directory in bytes.
  • The byte offset of the start of the Central Directory relative to the start of the archive.
  • A variable-length archive comment (up to 65,535 bytes).

Because the archive comment can vary in length, locating the EOCD requires scanning backward from the final byte of the file across a 65KB window—a procedure implemented with boundary validation in the BitDark scanning engine.

Worked Forensic Example: Step-by-Step Attack Walkthrough

To see how Zip Slip executes in a vulnerable environment and how static auditing thwarts it, let us walk through a practical scenario involving an automated document conversion platform.

1. The Vulnerable Backend Implementation

Consider a Python web application that allows users to upload custom plugin packages packaged as ZIP archives. The developer writes the following seemingly standard decompression routine: 

# VULNERABLE EXTRACTION PATTERN (Do NOT use)
import zipfile
import os

def extract_plugin(archive_path, target_directory):
    with zipfile.ZipFile(archive_path, 'r') as zip_ref:
        for member in zip_ref.namelist():
            # Flawed: Naive string concatenation
            destination = os.path.join(target_directory, member)
            
            # Create subdirectories if needed
            os.makedirs(os.path.dirname(destination), exist_ok=True)
            
            # Write payload to disk
            with open(destination, 'wb') as f:
                f.write(zip_ref.read(member))

2. The Attacker's Weaponized Archive

An attacker crafts a custom ZIP archive containing two files:

  • manifest.json: A harmless configuration file.
  • ../../../../../../../../home/target_user/.ssh/authorized_keys: A file containing the attacker's public SSH key.

3. The Execution Mechanics

When the server invokes extract_plugin("/tmp/upload.zip", "/var/app/plugins/"):

  1. The loop encounters manifest.json and safely writes it to /var/app/plugins/manifest.json.
  2. The loop encounters the second entry. os.path.join("/var/app/plugins/", "../../../../../../../../home/target_user/.ssh/authorized_keys") resolves through the operating system's pathname canonicalizer.
  3. Because eight ../ tokens step up from /var/app/plugins/ all the way to the filesystem root (/), the target resolves to /home/target_user/.ssh/authorized_keys.
  4. The script writes the attacker's SSH key over the existing file. The attacker immediately connects to the server via SSH as target_user, achieving full remote code execution without authentication.

Secure Remediation Patterns Across Programming Languages

Remediating Zip Slip requires strictly enforcing canonical path containment verification. The golden rule is: Always resolve the absolute canonical path of the target file, and verify that it starts with the canonical path of the destination folder plus a trailing path separator.

1. Secure Python Remediation

# SECURE EXTRACTION PATTERN (Python 3)
import zipfile
import os

def safe_extract(zip_path, target_dir):
    # Resolve absolute, symlink-resolved canonical target directory
    canonical_target = os.path.realpath(target_dir) + os.path.sep
    
    with zipfile.ZipFile(zip_path, 'r') as archive:
        for member in archive.infolist():
            # Resolve intended destination
            target_file = os.path.realpath(os.path.join(canonical_target, member.filename))
            
            # Enforce boundary containment
            if not target_file.startswith(canonical_target):
                raise SecurityError(f"Zip Slip attempt detected: {member.filename}")
            
            if member.is_dir():
                os.makedirs(target_file, exist_ok=True)
            else:
                os.makedirs(os.path.dirname(target_file), exist_ok=True)
                with open(target_file, 'wb') as f:
                    f.write(archive.read(member.filename))

2. Secure Java Remediation

// SECURE EXTRACTION PATTERN (Java 11+)
import java.io.*;
import java.nio.file.*;
import java.util.zip.*;

public class SecureUnzipper {
    public static void extract(File zipFile, File destinationDir) throws IOException {
        Path targetDir = destinationDir.toPath().toRealPath();
        
        try (ZipInputStream zis = new ZipInputStream(new FileInputStream(zipFile))) {
            ZipEntry entry;
            while ((entry = zis.getNextEntry()) != null) {
                Path resolvedPath = targetDir.resolve(entry.getName()).normalize();
                
                // Strictly verify canonical prefix
                if (!resolvedPath.startsWith(targetDir)) {
                    throw new SecurityException("Zip Slip directory traversal breakout: " + entry.getName());
                }
                
                if (entry.isDirectory()) {
                    Files.createDirectories(resolvedPath);
                } else {
                    Files.createDirectories(resolvedPath.getParent());
                    Files.copy(zis, resolvedPath, StandardCopyOption.REPLACE_EXISTING);
                }
                zis.closeEntry();
            }
        }
    }
}

3. Secure Node.js Remediation

// SECURE EXTRACTION PATTERN (Node.js)
const path = require('path');
const fs = require('fs');

function isSafePath(destinationDir, entryName) {
    const dest = path.resolve(destinationDir);
    const resolved = path.resolve(dest, entryName);
    
    // Ensure resolved path starts with destination + path separator
    return resolved.startsWith(dest + path.sep);
}

Advanced Archive Evasions & Parser Differentials

Security engineers must recognize that modern archive exploitation goes beyond simple string matching. Attackers frequently exploit parser differentials—subtle discrepancies between how different unarchiving tools interpret malformed or ambiguous binary structures:

1. Central Directory Desynchronization (Shadowing)

An attacker can craft a ZIP file where the Local File Header declares a benign filename (e.g., image.png), while the Central Directory Header for that exact same entry declares a malicious path (e.g., ../../../../etc/passwd)—or vice versa.

Because some streaming extraction libraries (such as certain streaming tar/zip parsers) read sequentially from the beginning without ever parsing the Central Directory, while desktop utilities (like WinRAR or 7-Zip) read the Central Directory at the end, the two tools will extract completely different files to completely different locations. The BitDark scanner mitigates this by scanning Central Directory records first, falling back to Local File Headers if the Central Directory is missing or truncated.

2. Symlink Traversal (Tar Slip & Zip Symlink Chaining)

Even if an application validates that an archive entry contains no ../ tokens, an attacker can execute a two-stage symlink breakout:

  1. The archive contains an entry named link_dir that is marked as a symbolic link pointing to /var/www/html/.
  2. The archive contains a subsequent entry named link_dir/shell.php.
  3. When unpacked, the unzipper creates the symlink inside the safe directory. On the next entry, the OS follows the symlink, writing shell.php directly into the web root.
Hardened Defense: During extraction, unarchivers should explicitly disable symbolic link creation (e.g., setting follow_symlinks=False) unless strictly required, and verify that intermediate path segments are not pre-existing symlinks.

Common Mistakes in Archive Validation

When attempting to protect applications against Zip Slip, developers often introduce flawed security controls that fail under adversarial pressure:

  • Non-Recursive String Stripping: Calling filename.replace("../", "") is completely ineffective against nested traversal strings like ....//. When ../ is removed, the remaining characters collapse back into ../.
  • Checking Only Forward Slashes: Windows systems recognize both forward slashes (/) and backslashes (\) as path separators. Filtering for ../ while allowing ..\ leaves Windows servers completely vulnerable.
  • Validating Paths Before Decoding: Performing traversal checks on URL-encoded or Unicode strings before decoding allows attackers to bypass filters using percent-encoding (e.g., %2e%2e%2f). Always normalize and decode prior to validation.
  • Relying on File Extensions for Content Verification: Renaming a malicious ZIP archive to .docx, .xlsx, .jar, or .apk does not change its internal PKZIP binary structure. A vulnerable Office parser or package unzipper will still process traversal headers regardless of extension.

Frequently Asked Technical Questions

What is the difference between Zip Slip and standard Path Traversal?
Standard Path Traversal (CWE-22) typically occurs when an application accepts user input directly into file read/write parameters (e.g., an HTTP parameter like ?file=../../etc/passwd). Zip Slip is a specialized subclass of path traversal where the traversal payload is packaged inside the binary header records of an archive, exploiting the unarchiver's automatic file creation process.
Can Zip Slip vulnerabilities lead directly to Remote Code Execution (RCE)?
Yes. While Zip Slip is fundamentally an arbitrary file write flaw, it frequently escalates to Remote Code Execution. By overwriting executable binaries, dynamic link libraries, crontab jobs (/etc/cron.d/), shell initialization scripts (.bashrc), SSH authorized_keys, or web server script directories (.php, .jsp, .aspx), attackers trigger code execution upon the next system or service invocation.
Does this tool inspect the file contents inside the archive?
No. The BitDark Zip Slip Inspector operates purely on archive directory metadata (Central Directory and Local File Headers). It does not decompress or analyze file payloads, ensuring rapid analysis even for archives containing large files.
Why does the tool support DOCX, XLSX, and APK files?
Modern Microsoft Office documents (DOCX, XLSX, PPTX), Java packages (JAR, WAR), and Android applications (APK) are all standard PKZIP archives wrapped in specialized file extensions. If an application unzips an uploaded Word document to process embedded XML files, it is fully vulnerable to Zip Slip if canonical containment is not enforced.
What is an NTFS Alternate Data Stream (ADS) exploit?
On Windows NTFS filesystems, files can contain multiple data streams using the filename:stream syntax. If an archive contains an entry with a colon (e.g., test.txt:hidden.exe), extracting it can write hidden streams or overwrite filesystem attributes (::$DATA), potentially evading antivirus scanners or causing unexpected file locks.
What are Windows Reserved Device Names and why are they dangerous?
In Windows and legacy MS-DOS, names such as CON, PRN, AUX, NUL, COM1-9, and LPT1-9 refer to physical hardware devices rather than filesystem files. Attempting to create or extract an archive entry with one of these names can freeze the unarchiving process, cause the operating system to hang, or crash server threads.
Does BitDark transmit my archives to an external server?
Never. BitDark operates on an air-gapped zero-network-egress security model. All binary inspection, SHA-256 checksumming, and Central Directory parsing execute exclusively inside your browser's private JavaScript memory space. Zero bytes leave your device.
How does ZIP64 affect Zip Slip detection?
Standard PKZIP is limited to 4GB archives and 65,535 entries. ZIP64 extends these limits using 64-bit headers. The BitDark scanner detects the ZIP64 End of Central Directory Locator (0x07064B50) and ZIP64 EOCD Record (0x06064B50) to accurately parse 64-bit Central Directory offsets.
