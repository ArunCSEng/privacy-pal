This is a fast triage check, not a malware verdict. It reads the first bytes of a file and matches them against a built-in list of common signatures, then compares the result to the extension. What Magic Bytes Are

People recognise a file by its name and extension — .pdf, .png, .exe. Programs do not: the extension is just part of the name and can say anything. What a program actually reads is the start of the file, where most formats place a short, fixed sequence of bytes that identifies them. These are the file's magic bytes (also called its signature or magic number). A PNG always begins with 89 50 4E 47 0D 0A 1A 0A; a Windows executable begins with the two letters MZ (4D 5A). The idea goes back to early Unix and its file command, which identified files this way instead of trusting their names.

Because the header travels inside the file, renaming the file cannot change it. That is what makes this check useful: if a file called invoice.pdf actually starts with 4D 5A, it is a Windows program wearing a PDF name, and the mismatch between header and extension gives it away.

What This Tool Does

Drop in a file and it reads the bytes in your browser, then reports four things:

  • Identified type — the first matching entry from a built-in list of about twenty common signatures (images, archives, executables, media, a few others).
  • Extension check — whether the filename extension is one the matched format normally uses. If the header is an executable but the name ends in .pdf, .jpg, .png, .gif, .docx, .xlsx or .txt, it is flagged as a high-risk masquerade; other mismatches are flagged as a plain mismatch.
  • SHA-256 hash — computed over the whole file with the browser's Web Crypto API, so you can record or compare it.
  • Hex dump — the first 128 bytes as hex and ASCII, with the matched signature bytes highlighted.

You can also export a JSON report of the findings. Everything happens locally; the page never sends your file anywhere.

How to Use the Tool

  1. Add a file — drag it onto the dropzone or click to browse. Good candidates are an unexpected email attachment, a download whose icon looks wrong, or anything with a double extension such as invoice.pdf.exe.

An unrecognised result is not a warning. Plain-text formats and anything outside the built-in signature list have no magic bytes to match, so they report as unknown rather than as a problem.

A Worked Example You Can Reproduce

Take any small Windows .exe and rename it to Q4_Internal_Audit_Statement.pdf, then drop it in. A real PDF would start with 25 50 44 46 (%PDF); this file instead starts like a PE executable: 

Offset        Bytes (Hex)                                       ASCII
0x0000        4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00   MZ..............
0x0010        B8 00 00 00 00 00 00 00 40 00 00 00 00 00 00 00   ........@.......

The tool identifies the header as Windows / DOS Executable (PE / MZ), sees that the name ends in .pdf, and because that pairs an executable header with a document extension, reports CRITICAL SPOOF DETECTED: Executable Masked as .pdf. A little further into a real PE you will usually find the ASCII text This program cannot be run in DOS mode in the hex dump, which is the DOS stub every PE carries. Rename the same file back to .exe and the verdict changes to a verified match — the bytes never changed, only the name did.

Where This Is Useful

  • Attachment triage: a file sent as invoice.pdf that is really an executable is caught immediately, since its header reads MZ rather than %PDF. Double extensions like document.pdf.exe are the same idea — the real header still shows through.
  • Understanding uploads: seeing that a file's real header disagrees with its name is a good illustration of why servers should check bytes, not just the client-supplied name or MIME type. Note the limit: a plain-text web shell renamed to .png has no binary signature, so it shows here as unrecognised, not as a spoof.
  • Quick identification: an unlabelled or oddly named file — is it a ZIP, an ELF binary, a SQLite database, a media container? The header usually answers in the first few bytes.
  • Recording a hash: the SHA-256 gives you a stable fingerprint to note in a ticket or compare against a known-good or known-bad value elsewhere.

A few entries are worth a note. The ZIP signature is listed for the Office extensions as well, so an ordinary .docx reads as consistent; distinguishing a true Office file from a bare .zip needs a look inside the archive, which this tool does not do. CA FE BA BE is shared by Java .class files and Mach-O universal binaries. The pcap entry matches only the little-endian byte order; the big-endian form (A1 B2 C3 D4) is not in the list. And plain-text formats such as .txt, .csv and .json have no fixed signature, so they are reported as unrecognised unless they happen to start with a byte-order mark like EF BB BF.

What Header Checking Cannot Do

Matching the first bytes is quick and reliable for honest files and for crude disguises, but it is not a complete analysis:

  • Trusting the browser's reported type. A file's type in the browser comes from its extension, so a renamed malware.exe can report image/jpeg. That is the mistake this tool exists to expose — verify bytes, not the name.
  • Signatures that are not at offset 0. MP4/MOV put their ftyp marker at offset 4; checking only the first byte would miss them. This tool checks the correct offset for each listed format, but a format whose signature sits elsewhere and is not in the list will not be found.
  • Office files versus plain ZIPs. Both start with 50 4B 03 04, so a header check alone cannot separate them; that needs the archive's internal directory (for example [Content_Types].xml).
  • Polyglots and appended data. A file can present a valid header for one format while carrying a second format — a GIF header with a ZIP/JAR appended, say — or hide a payload after the part a header check reads. A valid-looking header does not rule these out.

Frequently Asked Questions

What are magic bytes?
Magic bytes are a short, fixed sequence at a known position in a file — usually the very start — that identifies its format. A PNG begins with 89 50 4E 47 0D 0A 1A 0A; a Windows executable begins with the letters MZ (4D 5A). Programs read these bytes to know how to handle a file, independently of its name.
Does renaming a file change its magic bytes?
No. Renaming payroll.exe to payroll.pdf changes only the name stored by the filesystem. The bytes inside the file, including the leading signature, are untouched — which is exactly why comparing the header to the extension exposes a disguised file.
Why do .docx, .xlsx and .pptx files show a ZIP signature?
Modern Office files are ZIP archives of XML and media, so they start with the ZIP local-header bytes 50 4B 03 04 (PK..). This tool lists those extensions as valid for the ZIP signature, so a normally named .docx is reported as consistent rather than as a mismatch. Telling a real .docx from a plain .zip would require looking inside the archive, which this header-only tool does not do.
Will this tool catch every disguised file?
No. It only recognises files whose format is in its built-in list and whose signature sits where it expects. A disguised file with no known signature — a renamed script or plain-text web shell, for example — shows as unrecognised, not as a spoof. Polyglots and payloads appended after a valid header also pass a header-only check. Treat a clean result as one quick check, not proof the file is safe.
Is my file uploaded anywhere?
No. The file is read into memory in your browser, and the hashing, signature matching and hex dump all run there. Nothing you load is sent to a server; this page makes no network request for your file at all.
