⚠️ Limitations & Disclaimer

This viewer reads a hive; it is not a full forensic suite. It walks the allocated keys and values of a REGF hive (or a .reg export) and shows them, with triage filters, search and JSON/CSV export. It does not carve deleted keys from unallocated space, replay the .LOG1/.LOG2 transaction logs that a "dirty" hive needs, decrypt SAM password hashes, or give a per-key timeline — it reports the hive's own header timestamp, not one per key. If the key tree is damaged it falls back to a simple name scan, which is a best effort. Everything runs in your browser and nothing you open is uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them, so confirm important findings with a dedicated tool such as Registry Explorer.

What This Tool Does

The Windows Registry stores configuration as a tree of keys, each holding named values. On disk it lives in several hive files — SYSTEM, SOFTWARE, SAM, SECURITY and each user's NTUSER.DAT — in a binary format called REGF. This tool opens a hive (or a .reg text export) in your browser, walks its key tree, decodes the values, and lets you search, filter and export to JSON or CSV. It reads bytes only; nothing is executed and nothing you open is uploaded.

It is built for a quick look and for triage, not to replace a full registry-forensics tool. What it does well is let you browse a hive's structure and pull out values without installing anything or sending the file anywhere.

How a Hive Is Structured

A REGF hive begins with a 4-byte signature, regf, and a header that includes the hive's last-written time as a Windows FILETIME — a 64-bit count of 100-nanosecond intervals since 1 January 1601 UTC, which the tool converts to a readable date. The actual data starts at offset 0x1000 and is organised into bins and cells. The cells that matter for browsing are the named keys (nk), the values (vk), and the index cells (lf, lh, ri, li) that link a key to its subkeys. Starting from the root key, the tool follows those indexes down the tree, reading each key's name and its list of values.

Value Types It Decodes

Registry values are typed, and the tool renders the common ones in a readable form:

TypeShown as
REG_SZA plain text string.
REG_EXPAND_SZA string with unexpanded variables such as %SystemRoot%.
REG_DWORD / REG_QWORDA 32- or 64-bit number, in hex and decimal.
REG_MULTI_SZA null-separated list, joined for display.
REG_BINARYA hex preview of the first bytes, with the total length.

Other types are labelled by their type number. For a .reg export the tool reads the same information from the text form: dword:, hex: and quoted-string values under each [key path] heading.

Triage Filters and Search

Alongside free-text search over key paths, value names and data, the tool offers quick filters that match keys commonly looked at first in an investigation: Run / Startup (autostart and services), User Activity (UserAssist, TypedURLs, RecentDocs and similar), USB / Storage (USBSTOR and mounted devices), and Network (interfaces, TCP/IP, DNS). These are keyword filters on the key path — a fast way to jump to the interesting areas, not a guarantee that every relevant key matches.

A Worked Example You Can Reproduce

You do not need a full hive to try it. In regedit, export a small key to a .reg file — for example right-click HKEY_CURRENT_USER\Software and choose Export — then drop that file here. You will see the exported keys appear in the tree on the left; selecting one lists its values with their types and data on the right, and the summary shows the file's SHA-256 and the key/value counts. To try a real binary hive, copy your own NTUSER.DAT from a backup or disk image (it is locked while you are logged in) and open that; the tool reports it as a REGF hive, shows the header's last-written time, and walks the tree.

How to Use the Tool

  1. Open a file — drag a hive or .reg export onto the dropzone, or click to browse.
  2. Browse the tree — keys appear on the left; click one to see its values on the right.
  3. Narrow it down — type in the search box, or use a triage filter to jump to startup, user-activity, USB or network keys.
  4. Export — save everything parsed as JSON or CSV, or clear and open another file.

Where This Is Useful

  • Reading a hive without tooling: glance at an exported hive or .reg file on any machine, without installing a registry editor or forensics suite.
  • Sensitive files stay local: hives can contain account and system data, so keeping the file in your own browser rather than uploading it to a web service avoids handing it to a third party.
  • Quick triage: the filters jump straight to the keys most often checked first, and search finds a value across the whole hive.
  • Learning the format: browsing a hive you know, with the value types shown, is a direct way to see how the registry is laid out.

Frequently Asked Questions

What files can this tool open?
Binary Registry hives in the REGF format — NTUSER.DAT, SYSTEM, SOFTWARE, SAM, SECURITY, Amcache.hve and the like — and .reg text exports from regedit. It detects the format from the file's contents, not its name, so a hive with any filename is read as a hive.
Can it open a hive that is in use on a running Windows PC?
Not directly. Windows keeps the active hives locked, so you cannot simply copy them in Explorer. Work from a copy obtained another way — an offline disk image, a Volume Shadow Copy, a tool like FTK Imager, or reg.exe save — and open that copy here. The tool reads whatever bytes you give it.
Does it show the last-modified time of every key?
It shows the hive's own last-written timestamp from the REGF header (a Windows FILETIME, converted to UTC), not a separate time for each individual key. Every key cell does carry its own timestamp, but this viewer reports the hive-level one; for per-key timeline work use a dedicated registry forensics tool.
What value types does it decode?
REG_SZ and REG_EXPAND_SZ strings, REG_DWORD and REG_QWORD numbers, REG_MULTI_SZ lists, and REG_BINARY (shown as a hex preview). Other types are labelled by their type number. REG_SZ is a plain string; REG_EXPAND_SZ holds unexpanded variables like %SystemRoot%; REG_MULTI_SZ is a null-separated list.
Does it recover deleted keys or read transaction logs?
No. It parses the allocated cells of the primary hive. It does not carve unallocated space or slack for deleted keys, and it does not replay the .LOG1/.LOG2 transaction logs that a "dirty" hive needs to be made current. If the hive tree is damaged it falls back to a simple scan for key-name cells, which is a best effort, not full recovery.
Is my hive uploaded anywhere?
No. The file is read into memory in your browser, and the parsing, the SHA-256 hash and the JSON/CSV exports all run there. Nothing you open is sent to a server; the page makes no network request for your file.
