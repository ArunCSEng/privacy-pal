What This Tool Does

WebAssembly (Wasm) lets browsers run compiled code at near-native speed. A .wasm module is a compact binary, not readable text, so to understand one you disassemble it into WAT (WebAssembly Text) — the same module written out in a human-readable form. This tool does that in your browser: drop in a .wasm and it validates it, shows a map of its sections, lists what it imports and exports, and renders the functions as WAT instructions, with a SHA-256 hash and a JSON view. It reads the file only — nothing runs, and nothing is uploaded — so it is a safe way to look inside an untrusted module.

How to Use the Tool

  1. Open a module — drag in a .wasm binary. Nothing is executed, only parsed, so an untrusted module is safe to read here.
  2. Check the summary — it confirms the magic bytes and version, reports whether the module passes the browser's own validation, and gives the section and function counts plus a SHA-256 of the file.
  3. Read the disassembly — Linear WAT Disassembly renders the module as WebAssembly Text with the opcodes decoded. Start with the imports and exports: they carry real names even in a stripped build, and they usually tell you what the module talks to and what it offers.
  4. Switch views as needed — Section Breakdown maps each section to its byte offset and size, which is the view for understanding layout; Structured JSON Analysis gives the same information in a form you can process elsewhere.
  5. Export — Download .wat saves the disassembly for use with other WebAssembly tooling, and Export JSON saves the structured analysis. Clear resets.

Functions shown as $func_0, $func_1 and so on simply mean the optional name section was stripped at build time, which is normal for production modules.

The Binary, Briefly

Every module begins with the 8-byte preamble: the magic bytes 00 61 73 6D (\0asm) and a 4-byte version. After that comes a sequence of sections, each a one-byte ID and a length, covering types, imports, functions, tables, memory, globals, exports, the code (the function bodies), data, and a few more — thirteen in all, including the custom section that can hold the debug name table. The tool reads the preamble, confirms the magic, and walks the sections in order.

LEB128 and Opcodes

Wasm stores its integers — section lengths, counts, indices, constants — as LEB128, a variable-length encoding that uses seven bits of each byte for data and the top bit to signal whether another byte follows, so small numbers take fewer bytes. The tool decodes unsigned, signed and 64-bit LEB128 as the format requires. Inside the code section each function body is a stream of opcodes — stack-machine instructions such as local.get, i32.add, call and br_if — and the tool maps those bytes to their mnemonics to produce the WAT listing.

Imports, Exports and Names

The import and export sections are often the most telling part of a module, and they always carry real names because the host needs them to link. The imports show what the module asks of its environment — memory, functions, host calls — and the exports show what it exposes. Internal function names are a different matter: they live in an optional custom name section that production builds usually strip, so disassembled functions commonly appear as $func_0, $func_1 and so on, numbered by index rather than named.

A Worked Example You Can Reproduce

Compile a tiny module to try it. Save this as add.wat and assemble it with WABT's wat2wasm: 

(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
wat2wasm add.wat -o add.wasm

Drop add.wasm in and the summary shows the magic \0asm and version 1, the module validates, and the WAT tab shows one function exporting add with the body local.get 0 / local.get 1 / i32.add / end — matching the source you compiled. The Sections tab lists the Type, Function, Export and Code sections with their offsets and sizes, and the SHA-256 in the summary matches sha256sum add.wasm.

Where This Is Useful

  • Seeing what a module does: the import/export list and the WAT often reveal a module's purpose — what host functions it calls, what it exposes — without running it.
  • A safe look at an untrusted module: because nothing executes, you can inspect a suspicious .wasm and read its instructions before deciding whether to trust it.
  • Learning the format: comparing a small source module to its disassembly is a direct way to learn how sections, LEB128 and opcodes fit together.
  • Recording a hash: the SHA-256 is a stable fingerprint to note or compare.

Frequently Asked Questions

What is the difference between .wasm and WAT?
A .wasm file is the compact binary WebAssembly module a browser runs. WAT (WebAssembly Text) is its human-readable, S-expression text form — the same module written out so a person can read it. This tool disassembles the binary into WAT so you can see the module's structure, imports, exports and instructions.
Is this a decompiler? Will it give me the original source?
No. It is a disassembler: it turns the binary opcodes into readable WAT instructions, not back into the C, C++ or Rust the module was compiled from. For higher-level, C-like output you would use a decompiler such as WABT's wasm-decompile or a tool like Ghidra; WAT shows you the real instructions, which is often enough to understand what a module does.
Why do functions show names like $func_42 instead of real names?
Function names live in an optional custom name section that compilers include only with debug flags. Production builds usually strip it, so the disassembler has no names to show and falls back to the function's index, like $func_42. Imports and exports still carry their real names, because those are required for the module to link.
What does it mean when the module validates?
The tool runs the browser's own WebAssembly.validate() on the bytes. A pass means the module is structurally well-formed by the WebAssembly specification — its types, sections and control flow are consistent. It is a structural check, not a safety judgement: a valid module can still do something harmful, and an invalid one is simply malformed or truncated.
Is my file uploaded anywhere?
No. The .wasm is read into memory in your browser, and the validation, parsing, disassembly, SHA-256 hash and exports all run there. Nothing you open is sent to a server; the page makes no network request for your file.
