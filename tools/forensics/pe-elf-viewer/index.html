What This Tool Does

Every executable starts with a header that tells the operating system how to load it: what architecture it targets, where execution begins, and how its contents are divided into sections. This tool reads that header for the two dominant formats — Windows PE (.exe, .dll, .sys) and Linux/Unix ELF — and lays the fields out in a table, alongside a section map and a SHA-256 hash of the file. It is static: it only reads bytes, so opening even a malicious sample never runs it. For disassembly, import resolution or unpacking you still need a dedicated tool; this is for a fast, safe first look.

Nothing you open leaves your browser; the file is read into memory locally and every step runs there.

How to Use the Tool

  1. Open a binary — drag a Windows PE (.exe, .dll, .sys, .ocx) or a Linux/Unix ELF file onto the dropzone. Nothing is executed, so an untrusted sample is safe to inspect here.
  2. Confirm what it is — the summary reports the detected format and architecture, the entry point and the file's SHA-256. If you are on Linux, sha256sum on the same file should match exactly.
  3. Read the header table — each row pairs a Property with its Value and an Interpretation, so a raw machine code or subsystem number is explained rather than left as a number to look up.
  4. Study the section table — this is where the useful signals are. Compare Virtual Size against Raw Data Size: a section reserving far more memory than it occupies on disk is a classic packer footprint. Then check Flags / Permissions for anything both writable and executable, which is unusual in ordinary code.
  5. Keep the result — Export Analysis JSON saves everything parsed; Clear Analysis resets for the next file.

Those two signals are prompts to investigate further, not verdicts — plenty of legitimate binaries are packed, and this tool does not unpack or disassemble.

The PE Header, Briefly

A PE file opens with a small DOS stub beginning with the bytes MZ (4D 5A); at offset 0x3C a pointer gives the location of the PE\0\0 signature. After it comes the COFF header (machine type, section count, timestamp) and the optional header, which despite its name holds the important run-time fields: the magic that distinguishes PE32 from PE32+ (64-bit), the address of entry point as an RVA, the preferred image base, and the subsystem. This tool reads each of those and names the machine architecture and subsystem rather than leaving you a raw number.

The ELF Header, Briefly

An ELF file begins with 7F 45 4C 46 (\x7fELF). The bytes that follow record the class (32- or 64-bit), the byte order, and the OS/ABI. The header then gives the file type (relocatable, executable, shared object/PIE, or core dump), the machine, the entry-point virtual address, and the offset and count of the section headers. The tool follows the section-header string table to recover section names and reads each section's address, size, offset and flags.

The Section Table

Both formats carry a table of sections, and the tool shows the same columns for each: name, virtual address, virtual size, raw (on-disk) size, raw offset, and permission flags. The flags are where a quick read pays off — a section marked both writable and executable is unusual in ordinary code and worth a second look, and a section whose on-disk size is tiny next to a large virtual size is a classic packer footprint. The tool surfaces these numbers; interpreting them is left to you, which is the honest division of labour for a header viewer.

A Worked Example You Can Reproduce

On Linux, point it at a system binary you already have: 

# /bin/ls is a normal ELF64 executable on most systems
# just drag /bin/ls (or a copy of it) onto the tool

You will see the format reported as ELF64, the architecture as AMD x86-64 on a typical 64-bit machine, the file type as ET_DYN (modern distributions build position-independent executables), and the entry-point virtual address. The section table lists the familiar names — .text marked executable, .data writable, .rodata read-only — and the summary gives the file's SHA-256, which you can compare against sha256sum /bin/ls in a terminal to confirm the tool is reading the same bytes. On Windows, dropping C:\Windows\System32\notepad.exe shows the equivalent PE32+ view.

Where This Is Useful

  • Identifying an unknown binary: confirm whether a file is a 32- or 64-bit PE or ELF, what it targets, and whether it is an executable, a library or a shared object — without running it.
  • A safe first look at a sample: since nothing is executed, you can read a suspicious file's headers to spot an odd section layout or a writable-executable section before deciding whether it is worth deeper analysis.
  • Recording a hash: the SHA-256 gives a stable fingerprint to note or to check against a known value.
  • Learning the formats: seeing the real header fields and section flags of a binary you know is a direct way to learn how PE and ELF are laid out.

Frequently Asked Questions

What is the difference between PE and ELF?
PE (Portable Executable) is the Windows format for .exe, .dll and .sys files; it carries a DOS stub, a COFF header and an optional header. ELF (Executable and Linkable Format) is the format used on Linux and other Unix-like systems. Both describe the architecture, an entry point and a table of sections, which is what this tool reads from each.
Does opening a binary here run it?
No. The tool only reads the file's bytes and interprets the header structures; it never loads or executes the code. Reading the headers of a malicious sample this way does not run it. That said, keep handling the sample itself with the usual care — reading headers is not a safety verdict on the file.
What does a section's Virtual Size versus Raw Data Size tell me?
Virtual Size is how much space a section takes once mapped into memory; Raw Data Size is how much it occupies on disk. In normal binaries the two are close. A section with a tiny raw size but a large virtual size can be a sign of a packer, which unpacks into that reserved space at run time. This tool shows both numbers so you can compare them; it does not compute or flag the difference for you.
Which architectures and formats does it recognise?
For PE it reads PE32 and PE32+ and names common machines (x86, x64, ARM, ARM64, Itanium). For ELF it reads ELF32 and ELF64 in either byte order and names x86, x86-64, ARM, AArch64 and RISC-V, with the OS/ABI and file type. A file that is neither PE nor ELF is reported as unsupported.
Is my file uploaded anywhere?
No. The file is read into memory in your browser, and the parsing, the SHA-256 hash and the JSON export all run there. Nothing you open is sent to a server; the page makes no network request for your binary.
