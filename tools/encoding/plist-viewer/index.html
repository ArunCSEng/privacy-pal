Understanding Apple Property Lists (plist): The Structural Backbone of macOS and iOS

Across Apple operating systems—ranging from macOS, iOS, iPadOS, and watchOS to tvOS and visionOS—the Property List (.plist) format serves as the foundational data serialization protocol. Whether managing core operating system daemons, persisting user desktop preferences, declaring application sandbox entitlements, or enforcing enterprise Mobile Device Management (MDM) configuration profiles, property lists represent the universal language through which Apple platforms define configuration, state, and permissions.

Originating in the late 1980s as part of NeXTSTEP's object-oriented architecture, early property lists utilized an ASCII-based syntax inherited from the OpenStep API. These historical plists resembled simplified C-style structures, utilizing curly braces { ... } for associative dictionaries, parentheses ( ... ) for sequential arrays, double quotes for strings, and semicolons as statement terminators. While easily editable by human administrators using standard text editors, the OpenStep ASCII format lacked formal typing primitives for booleans, dates, floating-point numbers, and raw binary streams.

With the commercial launch of Mac OS X (now macOS), Apple modernized the property list standard into an explicit, typed XML Document Type Definition (DTD) schema: http://www.apple.com/DTDs/PropertyList-1.0.dtd. This XML serialization introduced unambiguous typing markers (such as <true/>, <false/>, <real>, <date>, and Base64-encoded <data>). However, as macOS evolved and iOS expanded onto embedded hardware with constrained memory and battery budgets, the verbose nature of XML text parsing introduced unacceptable CPU and memory overhead during system boot.

To eliminate this bottleneck, Mac OS X 10.2 Jaguar introduced the Binary Property List (bplist00) format. By discarding XML closing tags, packing primitives into single-byte markers, memory-mapping objects directly from disk, and organizing an indexed offset table with a 32-byte trailer, binary plists achieved massive speedups and file-size reductions. Today, the vast majority of configuration and state manifests across iOS and macOS are compiled into binary bplist00 files by default.

Binary Plist (bplist00) Architecture: Byte-Level Engineering Specification

To understand the byte-level mechanics executed by the BitDark decoding engine, consider the internal binary topology of a bplist00 file. Unlike standard hierarchical formats that serialize nodes top-down, Apple's binary plist format is designed for random-access memory mapping and reads from the bottom up. 

+--------------------------------------------------------------------------+
| Apple Binary Property List (bplist00) Structure                          |
+--------------------------------------------------------------------------+
| 0x00000000: Header (8 Bytes: "bplist00")                                 |
|--------------------------------------------------------------------------|
| Object Table: Packed serialized objects (Primitive singles, integers,   |
|               reals, dates, data blobs, ASCII/UTF-16 strings, arrays,     |
|               sets, and key-value dictionaries).                        |
|--------------------------------------------------------------------------|
| Offset Table: Linear array of byte offsets pointing directly to each     |
|               object in the Object Table. Width is 1, 2, 4, or 8 bytes.   |
|--------------------------------------------------------------------------|
| Trailer (Final 32 Bytes):                                                |
|   - 6 Bytes: Unused padding (zeros)                                      |
|   - 1 Byte:  Offset Table Integer Size (offsetIntSize)                   |
|   - 1 Byte:  Object Reference Size (objectRefSize)                       |
|   - 8 Bytes: Total Object Count (numObjects - Big-Endian UInt64)         |
|   - 8 Bytes: Root Object Index (topObject - Big-Endian UInt64)           |
|   - 8 Bytes: Offset Table Byte Offset (offsetTableOffset - UInt64)       |
+--------------------------------------------------------------------------+

1. The 32-Byte Trailer

Parsing a binary plist begins not at the first byte, but at the final 32 bytes of the file. The trailer contains the mathematical coordinates required to navigate the entire data graph:

  • offsetIntSize (Byte 6 of trailer): The size in bytes (typically 1, 2, or 4 bytes) of each integer stored in the offset table.
  • objectRefSize (Byte 7 of trailer): The size in bytes used to reference other objects within arrays, sets, and dictionaries.
  • numObjects (Bytes 8–15 of trailer): An 8-byte big-endian unsigned 64-bit integer representing the total count of distinct objects in the object table.
  • topObject (Bytes 16–23 of trailer): An 8-byte big-endian unsigned 64-bit integer indicating the offset table index of the root object (almost universally index 0).
  • offsetTableOffset (Bytes 24–31 of trailer): An 8-byte big-endian unsigned 64-bit integer pointing to the absolute byte position where the offset table begins.

2. The Offset Table

The offset table is an indexed lookup table. To locate any object by its index $i$ (where $0 \le i < \text{numObjects}$), the parser calculates:

$$\text{Target Byte Offset} = \text{ReadInt}\Big(\text{offsetTableOffset} + (i \times \text{offsetIntSize}),\, \text{offsetIntSize}\Big)$$

This architecture enables constant-time $O(1)$ random access to any object node without needing to traverse or deserialize predecessor objects.

3. Object Markers & Type Descriptors

Every object in the Object Table begins with a 1-byte marker. The marker is divided into two 4-bit nibbles:

  • High Nibble (Bits 7–4): Identifies the abstract type of the object.
  • Low Nibble (Bits 3–0): Represents the size or count. If the count is smaller than 15 (`0x0F`), the low nibble directly contains the count. If the low nibble is equal to `0x0F`, the count exceeds 14 and is stored in an immediately following typed integer byte sequence ($2^{\text{info}}$ bytes).
High Nibble Object Type Low Nibble Meaning Encoding Mechanics & Characteristics
0x0 Primitive / Singleton Value identifier 0x00 = null; 0x08 = boolean false; 0x09 = boolean true; 0x0F = fill byte.
0x1 Integer Exponent $n$ ($1 \ll n$ bytes) Value occupies $2^n$ bytes (1, 2, 4, 8, or 16 bytes), big-endian signed/unsigned integer.
0x2 Real / Float Exponent $n$ ($1 \ll n$ bytes) IEEE 754 floating-point number. $n=2$ (4-byte float), $n=3$ (8-byte double).
0x3 Date Fixed length (0x3) 8-byte IEEE 754 float: seconds elapsed since Apple Epoch (2001-01-01 00:00:00 UTC).
0x4 Data Blob Byte count (or 0xF + int) Raw binary byte sequence (e.g., certificates, icons, serialized cryptographic hashes).
0x5 ASCII String Character count Standard 1-byte ASCII characters, uncompressed and null-free.
0x6 Unicode String Character count Big-Endian UTF-16 character stream ($2 \times \text{count}$ bytes).
0x8 UID (Keyed Archiver) Byte length minus 1 Unique Identifier used exclusively by NSKeyedArchiver class reference graphs.
0xA Array Item count Followed by an array of object references ($\text{count} \times \text{objectRefSize}$ bytes).
0xC Set Item count Unordered collection of object references ($\text{count} \times \text{objectRefSize}$ bytes).
0xD Dictionary Key-value pair count Followed by $\text{count}$ key references, then immediately followed by $\text{count}$ value references.

Worked Example: Byte-by-Byte Dissection of a Binary Plist

To illustrate the precision of the parser, let us dissect a minimal 70-byte binary property list that serializes a single dictionary containing two keys: "Name" = "BitDark" and "Active" = true.

1. The Raw Hex Stream

00000010:  6d 65 56 41 63 74 69 76  65 57 42 69 74 44 61 72  meVActiveWBitDar
00000020:  6b 09 08 0d 14 1c 21 00  00 00 00 00 00 01 01 00  k.....!.........
00000030:  00 00 00 00 00 00 05 00  00 00 00 00 00 00 00 00  ................
00000040:  00 00 00 00 00 00 22                               ......"

2. Reading the Trailer (Final 32 Bytes: Offset 0x26 to 0x45)

Trailer Field Hex Bytes Decoded Value Interpretation
offsetIntSize 01 1 Byte Each entry in the offset table is a 1-byte integer (file is < 256 bytes).
objectRefSize 01 1 Byte Object reference IDs are 1-byte indexes.
numObjects 00 00 00 00 00 00 00 05 5 Objects The object table contains exactly 5 distinct nodes.
topObject 00 00 00 00 00 00 00 00 Index 0 The root node of the graph is object #0.
offsetTableOffset 00 00 00 00 00 00 00 22 Byte Offset 0x22 (34) The offset table begins at file position 34.

3. Resolving the Offset Table (5 Bytes starting at 0x22)

Reading 5 consecutive 1-byte entries from 0x22:

  • Object #0 Offset: 0x08 (Points to root dictionary)
  • Object #1 Offset: 0x0D (Points to key string "Name")
  • Object #2 Offset: 0x14 (Points to key string "Active")
  • Object #3 Offset: 0x1C (Points to value string "BitDark")
  • Object #4 Offset: 0x21 (Points to boolean true value)

4. Traversal of the Object Table

  • Object #0 at 0x08: Marker byte 0xD2. High nibble 0xD indicates a dictionary; low nibble 2 indicates 2 key-value pairs. Following the marker are 4 object references: 01 02 (keys) and 03 04 (values).
  • Object #1 at 0x0D: Marker 0x54 (ASCII string of length 4). Characters: 4E 61 6D 65 = "Name".
  • Object #2 at 0x14: Marker 0x56 (ASCII string of length 6). Characters: 41 63 74 69 76 65 = "Active".
  • Object #3 at 0x1C: Marker 0x57 (ASCII string of length 7). Characters: 42 69 74 44 61 72 6B = "BitDark".
  • Object #4 at 0x21: Marker 0x09 (Primitive boolean: true).

The engine reconstructs the object graph into native JSON in milliseconds: 

{
  "Name": "BitDark",
  "Active": true
}

Forensic Incident Response: Auditing macOS Persistence Plists

In macOS digital forensics and incident response (DFIR), property lists represent primary forensic artifacts. Attackers frequently utilize Apple's native process supervision subsystem—launchd—to maintain persistence across system reboots.

1. Primary Persistence Directories

Security analysts triage the following directories to identify suspicious or unauthenticated launch items:

  • /System/Library/LaunchDaemons and /System/Library/LaunchAgents: Protected by Apple System Integrity Protection (SIP); contains authentic OS daemons.
  • /Library/LaunchDaemons: System-wide background services running as root prior to user login (common target for rootkits and elevated trojans).
  • /Library/LaunchAgents: System-wide services executing in the context of the logging-in user.
  • ~/Library/LaunchAgents: User-specific services executing automatically upon user login (the single most prevalent persistence vector for consumer macOS adware and info-stealers).

2. Critical launchd Keys to Inspect

When inspecting a launch plist in the BitDark viewer, analysts examine these key attributes: 

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.malicious.payload.service</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/bin/python3</string>
        <string>-c</string>
        <string>import socket,subprocess,os;...</string>
    </array>
    <key>RunAtLoad</key>
    <true/>
    <key>KeepAlive</key>
    <true/>
    <key>StandardErrorPath</key>
    <string>/tmp/err.log</string>
</dict>
</plist>
  • Label: The unique reverse-DNS identifier of the job. Attackers often masquerade as legitimate Apple services (e.g., com.apple.updater.plist).
  • ProgramArguments: The exact executable path and command-line flags. Look for suspicious script interpreters (bash, sh, python, curl, osascript) pointing to temporary folders like /tmp, /var/tmp, or hidden user folders.
  • RunAtLoad: When set to true, the job executes automatically the moment the plist is registered or when the user logs in.
  • KeepAlive: Instructs launchd to restart the process immediately if it terminates or crashes, ensuring continuous persistent beaconing.
  • WatchPaths: Directs launchd to execute the program whenever specific filesystem paths are created or altered.

Common Pitfalls and Forensic Caveats

Engineers and forensic investigators should be mindful of several critical edge cases when analyzing property lists:

  • The NSKeyedArchiver Object Graph Trap: Many binary plists (such as those generated by Xcode Interface Builder, state restorations, or NSSecureCoding) do not serialize straightforward key-value objects. Instead, they use an internal schema with top-level keys $archiver, $version, $classes, and an array of $objects containing UID tokens (type 0x8). Viewing these raw plists yields numeric UID cross-references rather than nested JSON structures.
  • Base64 Data Truncation: Binary plists support arbitrary binary byte buffers (type 0x4), which can store embedded X.509 certificates, code signatures, or image icons. When converted to JSON or displayed in web viewers, these buffers must be represented cleanly as Base64 strings or hex snippets to prevent memory bloat and string corruption.
  • Date Epoch Discrepancies: Apple Core Foundation timestamps calculate seconds elapsed from January 1, 2001 (Apple Epoch), whereas Unix timestamps measure seconds from January 1, 1970. The constant difference is exactly $978,307,200$ seconds. Parsers that mistakenly treat Apple dates as Unix timestamps will report dates in 1970 or 1971.
  • Corrupting Code Signatures on Re-Serialization: Modifying an Info.plist inside an existing application bundle (App.app/Contents/Info.plist) and converting it between XML and binary invalidates the bundle's cryptographic seal (Code Directory hash inside _CodeSignature/CodeResources). Any modified app will fail Gatekeeper verification and crash with a SIGKILL on launch unless re-signed with codesign --force.

How does Apple's plutil command compare to this web tool?
plutil is Apple's built-in command-line tool (e.g., plutil -convert json file.plist), but it is exclusively available on macOS. BitDark's web-based decoder replicates binary bplist00 decoding, XML parsing, and JSON conversion across Windows, Linux, Android, ChromeOS, and iOS without requiring Xcode or Apple command-line developer tools.
What is the Apple Core Foundation Date Epoch?
Unix timestamps count seconds from January 1, 1970 (POSIX epoch). In contrast, Apple's Core Foundation (CFDate) counts seconds as an 8-byte IEEE 754 float from January 1, 2001, 00:00:00 UTC. To convert an Apple epoch timestamp to a standard JavaScript Date, add 978,307,200 seconds and multiply by 1,000 to convert to milliseconds.
Can this tool parse Apple Keyed Archives (NSKeyedArchiver)?
Yes. The tool successfully decodes the binary structure of keyed archives, extracting the $archiver, $version, and $objects arrays along with UID markers. Note that keyed archives store flattened object graphs with class mapping tables rather than simple hierarchical key-value pairs.
Can I convert an edited JSON object back into a valid Apple XML plist?
Yes. When you load a plist, BitDark automatically generates both the formatted JSON representation and the clean Apple-compliant XML Plist (version 1.0) complete with the official Apple DTD schema header. You can download the XML directly using the "Download XML Plist" button.
What causes a "File too small to be a valid binary plist" error?
An authentic Apple binary plist must contain at minimum the 8-byte magic header bplist00 and the 32-byte trailer at the end of the file. Any file smaller than 40 bytes cannot structurally contain a valid trailer and offset table, indicating that the file is either empty, truncated, or corrupted.
Does this tool support older NeXTSTEP ASCII property lists?
Yes. Legacy ASCII plists containing curly braces { ... } and semicolon-separated pairs can be pasted into the "Paste Raw Text / XML" tab. The parser sanitizes and extracts string-based key-value pairs, converting them into standard JSON structures.
