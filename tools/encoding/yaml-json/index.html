⚠️ Limitations & Disclaimer

YAML and JSON do not express exactly the same things, so some constructs change on conversion. When YAML becomes JSON, comments are dropped and multi-line block scalars become single strings with \n escapes. YAML anchors and merge keys are expanded, so shared data is duplicated rather than referenced. This tool reads a single YAML document, so a file that uses --- to separate several documents raises a parse error; convert each document on its own. Everything runs in your browser and the text you paste is not uploaded. Results are provided as-is; BitDark.net is not liable for decisions made using them, so validate converted configuration before deploying it.

What This Tool Does

YAML and JSON describe the same kinds of data — maps, lists, strings, numbers, booleans and null — in two different styles. JSON (RFC 8259) uses explicit braces, brackets and quotes; YAML uses indentation and is easier to read and comment. Teams routinely author Kubernetes manifests, CI pipelines and API specs in YAML, then need JSON for a tool that only speaks JSON — or the reverse. This converter does that translation in your browser.

It is built on the js-yaml library. YAML → JSON parses your YAML and serialises the result with the browser's own JSON.stringify; JSON → YAML parses your JSON and emits YAML. You can switch direction, swap the panes, choose 2- or 4-space indentation, and format or minify JSON. Nothing you type is sent anywhere; the only network request is the one-time load of the js-yaml file when the page opens.

The Core Schema and the Norway Problem

The best-known YAML trap is the Norway problem. Older YAML 1.1 parsers treated many bare words as booleans: yes, no, on, off, y and n, in several capitalisations. So a list of ISO country codes that included an unquoted NO (Norway) would come out as false: 

# The YAML 1.1 boolean trap
countries:
  - US
  - GB
  - NO   # intended: Norway

Under YAML 1.1 that last entry parses as boolean false. This tool uses js-yaml's default YAML 1.2 core schema, where only true and false (and True/False/TRUE/FALSE) are booleans. Everything else — NO, yes, on, off — stays a string. You can confirm it: paste the list above and convert, and the JSON keeps "NO" as text. If you actually want a boolean, write true or false; if you want the literal word, you are already safe.

A Worked Example You Can Reproduce

Here is a small Kubernetes deployment, covering nested maps, a list, numbers and booleans. Paste the YAML into the left pane with YAML → JSON selected and 2-space indent:

1. Input YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: auth-proxy-service
  namespace: production
  labels:
    tier: edge-gateway
spec:
  replicas: 2
  selector:
    matchLabels:
      tier: edge-gateway
  template:
    metadata:
      labels:
        tier: edge-gateway
    spec:
      containers:
        - name: envoy-proxy
          image: envoyproxy/envoy:v1.28.0
          ports:
            - containerPort: 8443
              name: https
          securityContext:
            readOnlyRootFilesystem: true
            runAsNonRoot: true
            runAsUser: 10001
          env:
            - name: ENABLE_TLS_STRICT
              value: "true"

    "labels": {

    }
  },
  "spec": {
    "replicas": 2,
    "selector": {

        "tier": "edge-gateway"

      "metadata": {
        "labels": {
          "tier": "edge-gateway"
        }
      },
      "spec": {
        "containers": [
          {
            "name": "envoy-proxy",
            "image": "envoyproxy/envoy:v1.28.0",
            "ports": [
              {
                "containerPort": 8443,
                "name": "https"
              }
            ],
            "securityContext": {
              "readOnlyRootFilesystem": true,
              "runAsNonRoot": true,
              "runAsUser": 10001
            },

              {
                "name": "ENABLE_TLS_STRICT",
                "value": "true"
              }
            ]
          }
        ]
      }

}

Two details are worth noticing. replicas: 2 and runAsUser: 10001 become JSON numbers, while value: "true" stays the string "true" because it was quoted in the YAML — it is an environment-variable value, not a boolean. Unquoting it would make it the boolean true, which Kubernetes would reject for that field. That quote-or-not distinction is the single most common source of surprise when moving between the two formats.

Anchors and Merge Keys

YAML can name a node with an anchor (&name) and reuse it through an alias (*name), and the merge key (<<) folds a referenced map's entries into another map. JSON has none of this, so on conversion the references are expanded — the shared data is written out in full at each place it is used: 

# YAML with an anchor and a merge key
default_limits: &resources
  cpu: "500m"
  memory: "512Mi"

services:
  api:
    name: "catalog-service"
    <<: *resources

Converting that YAML produces this JSON, with cpu and memory merged into the api map:

{
  "default_limits": {
    "cpu": "500m",
    "memory": "512Mi"
  },
  "services": {
    "api": {
      "name": "catalog-service",
      "cpu": "500m",
      "memory": "512Mi"
    }
  }
}

The expansion is correct, but it is one-way: going back from this JSON to YAML gives you the fully written-out version, not the original anchor and merge key. If the compactness of anchors matters to you, keep the YAML source rather than regenerating it from JSON.

What Does Not Round-Trip

Converting YAML to JSON and back will not always return the exact original file, because some YAML features have no JSON equivalent:

YAML feature On conversion to JSON
Comments (# ...) Dropped — JSON has no comment syntax.
Anchors & merge keys (&, *, <<) Expanded inline; the shared reference is lost.
Block scalars (| literal, > folded) Become ordinary strings with \n escapes.
Multiple documents (---) Not supported — a single document is expected, so this raises a parse error.
Key ordering & quoting style Re-serialised by the formatter; original spacing and quote choices are not preserved.

For most configuration work these are fine — the data is identical, only the presentation changes. Keep them in mind when a file's exact formatting matters, such as a checked-in manifest you intend to diff against the original.

How to Use the Tool

  1. Pick a direction — YAML → JSON or JSON → YAML.
  2. Add your source — paste it into the left pane, drag a file onto it, or use Upload. Sample loads a small Kubernetes manifest to start from.
  3. Set the indent — 2 spaces (common for Kubernetes) or 4.
  4. Convert — conversion runs as you type; Convert re-runs it, and on the JSON pane Format and Minify reshape the output.
  5. Take the result — Copy or Download the target, or Swap to send the output back through the other direction.

If a conversion fails, the banner shows the parser's message with a line and column for YAML errors. The usual causes are a tab used for indentation (YAML needs spaces), inconsistent indentation, or a trailing comma in JSON, which RFC 8259 does not allow.

Frequently Asked Questions

Does this converter parse NO, yes and on as booleans?
No. It uses js-yaml with the YAML 1.2 core schema, where only true and false (and their capitalised forms) are booleans. Unquoted NO, yes, on and off stay strings, so a country code like NO is not silently turned into false.
What happens to YAML anchors and merge keys when I convert to JSON?
They are expanded. JSON has no anchors or references, so an anchored node (&name) referenced by an alias (*name) is inlined wherever it is used, and a merge key (<<) copies the referenced mapping's entries into the surrounding map. The JSON output contains the fully expanded data.
Can I convert a multi-document YAML file?
Not in one pass. This tool loads a single YAML document, so a file that uses --- to separate several documents raises a parse error. Convert each document on its own, or remove the separators first. JSON itself has no multi-document concept.
Why do tabs cause an error in my YAML?
YAML does not allow tab characters for indentation, because tab width varies between editors and would make the structure ambiguous. Use spaces. The editor's Tab key inserts spaces for you, matching the indent size you selected.
Is my input uploaded anywhere?
No. Parsing and conversion run in your browser with the js-yaml library, and the text you paste is not sent to a server. The library file itself is loaded once from a CDN when the page opens; after that the conversion needs no network.
