What HTML Entities Are

In HTML, a handful of characters carry special meaning: < and > delimit tags, & starts an entity, and quotes delimit attribute values. To show those characters literally instead of having the browser interpret them, you replace each with an entity — < becomes &lt;, & becomes &amp;. This tool encodes text into entities and decodes entities back into text, in your browser.

Three Ways to Write the Same Entity

Format< becomesBest for
Named&lt;Readability — the common choice for the special characters
Decimal&#60;Any character, including ones with no named entity
Hex&#x3C;Matching code points written in hexadecimal

All three render identically; they're just different notations for the same character. Named entities are easiest to read, while the numeric forms can represent any character — the tool falls back to a numeric entity whenever a character has no standard name.

Choosing What to Encode

  • Special characters only — the OWASP set (< > & " ' / `). This is what you normally want: it neutralises the characters that affect HTML while leaving ordinary text alone.
  • Special + non-ASCII — also encodes accented letters, symbols and emoji, useful when a channel only accepts plain ASCII.
  • Every character — encodes all text. It's labelled "full obfuscation," and that word is the honest description: it makes text unreadable to a person but is trivially decoded, so it is not a security or privacy measure.

A Worked Example You Can Reproduce

Encode <script>alert('x')</script> with named entities, special-characters scope: 

&lt;script&gt;alert(&apos;x&apos;)&lt;&#x2F;script&gt;

The angle brackets become &lt;/&gt;, so a browser shows the text instead of running a script tag. Decoding reverses it exactly. The tool also handles Unicode correctly: an emoji like 😀 encodes to &#128512; (its real code point, U+1F600) rather than mangling the surrogate pair, and &copy;, &#233; and &#x1F600; all decode back to ©, é and 😀.

Encoding and Security: the Honest Version

Encoding the special characters is the core idea behind safely putting untrusted text into HTML — entity-encoded input can't break out and become markup. But two caveats matter. First, this is a manual convenience tool; in a real application you should rely on your framework's automatic escaping, which encodes for the right context every time. Second, HTML-body encoding isn't a complete fix on its own — text placed in an attribute, a URL, a CSS value or JavaScript needs that context's encoding. For putting data into HTML safely, think context, not just "encode the angle brackets."

Frequently Asked Questions

What's the difference between named, decimal and hex entities?
They're three notations for the same character. Named (&lt;) is the most readable; decimal (&#60;) and hex (&#x3C;) use the character's code point and can represent any character, including those without a named entity. Browsers render all three identically.
Which characters should I encode?
Usually just the special set — < > & and the quotes — which is the "special characters only" scope. That's enough to display text safely in HTML body content. Encode non-ASCII characters too only when a channel requires plain ASCII.
Does "encode every character" make my text secure?
No. That option just makes text hard to read for a person, but anyone can decode it instantly — it's obfuscation, not encryption. Use it for ASCII-safe transport if needed, never to hide sensitive data.
Is entity encoding enough to prevent XSS?
Encoding the special characters protects text placed in HTML body content, but it isn't a complete fix. Data in attributes, URLs, CSS or JavaScript needs encoding for that specific context, and real applications should use their framework's automatic, context-aware escaping rather than manual encoding.
Does it handle emoji and accented characters?
Yes. It works on Unicode code points, so an emoji encodes to its real numeric entity (😀 becomes &#128512;) and decodes back correctly, and accented letters like é are handled the same way — nothing is split or corrupted.
