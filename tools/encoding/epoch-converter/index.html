What Unix Epoch Time Is

Unix epoch time is the number of seconds since 1970-01-01 00:00:00 UTC — a single integer that represents a moment unambiguously, with no timezone attached. It's how computers store and exchange time almost everywhere: log files, API responses, databases, JWT expiry fields, file timestamps. This tool converts an epoch value into human-readable dates and back, and shows a live epoch clock, all in your browser.

Seconds, Milliseconds, and the Off-by-1000 Trap

The most common mistake with epoch time is the unit. Plain Unix time is in seconds (a 10-digit number today), but JavaScript and Java use milliseconds (13 digits), and some systems use microseconds or nanoseconds. Mixing them puts a date off by a factor of 1000 — a timestamp that should read 2023 lands in 1970, or far in the future.

Auto-detect picks the unit from the number's magnitude, but if a result looks a thousandfold wrong, set the unit explicitly — that's almost always the cause.

Epoch Is UTC; Your Local Time Is a View

An epoch value is always anchored to UTC. When you convert one, the tool shows the UTC moment (ISO 8601 and the RFC/UTC string) alongside your browser's local time, so you can see both. Going the other way — a human date to an epoch — you choose whether the date you typed is UTC or local, because 2023-11-14 22:13 is a different instant in London than in New York. Getting that selector right is what avoids the classic "my timestamp is a few hours off" bug.

A Worked Example You Can Verify

1700000000  (seconds) → 2023-11-14T22:13:20.000Z   (hex 0x6553F100)
0           (seconds) → 1970-01-01T00:00:00.000Z   (the epoch itself)

Those are exact: 1700000000 is 2023-11-14 22:13:20 UTC, and converting that date back with the UTC option returns 1700000000. Epoch 0 is the definition point, midnight UTC on 1 January 1970. The hex form is just the same integer in base 16, which you'll sometimes see in low-level data.

A Note on the Year 2038

Systems that store Unix time in a signed 32-bit integer can only count to 03:14:07 UTC on 19 January 2038, after which the value overflows — the "Year 2038 problem." Modern systems use 64-bit timestamps and are fine, and this tool handles large values without that limit, but it's worth knowing when you work with older software or embedded devices.

Frequently Asked Questions

My timestamp converted to 1970 — what went wrong?
Almost certainly a unit mismatch. A milliseconds value (13 digits) read as seconds lands near 1970 when divided down, and a seconds value read as milliseconds lands far in the future. Set the unit explicitly to seconds or milliseconds to match your source.
Why does the date look a few hours off?
That's a timezone issue. Epoch time is UTC, so if you interpret a local date as UTC (or vice versa) you'll be off by your UTC offset. Use the UTC/local selector when converting a human date to an epoch so the instant is interpreted correctly.
What exactly is epoch 0?
It's the Unix epoch: 1970-01-01 00:00:00 UTC, the moment all Unix timestamps are counted from. Positive values are after it, and negative values represent times before 1970.
What is the Year 2038 problem?
Systems storing Unix time as a signed 32-bit integer overflow on 19 January 2038, after which the value wraps to a negative number. Modern 64-bit systems aren't affected, and this tool handles large values fine, but older or embedded software may need attention.
Is my data sent anywhere?
No. All conversions run in your browser using its built-in date handling, so nothing you enter is uploaded. The live clock also runs locally.
