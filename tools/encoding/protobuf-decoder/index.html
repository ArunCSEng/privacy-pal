What This Decoder Does

Protocol Buffers (protobuf) is a compact binary format, and normally you need the .proto schema to read a message. This tool decodes the raw wire format without the schema — the equivalent of protoc --decode_raw. Paste a message as hex or Base64, or drop a file, and it shows each field's number, wire type and value, detecting nested messages automatically. Everything runs in your browser.

How the Wire Format Works

A protobuf message is a flat sequence of fields. Each starts with a tag — a varint whose lower 3 bits are the wire type and whose upper bits are the field number — followed by the field's data. There are four wire types in use:

Wire typeCarries
0 — Varintint32/64, uint, bool, enum, sint (zig-zag)
1 — 64-bitfixed64, sfixed64, double
2 — Length-delimitedstrings, bytes, nested messages, packed fields
5 — 32-bitfixed32, sfixed32, float

Varints store integers seven bits at a time with a continuation bit, so small numbers take one byte. That's why the encoding is compact — and why you can't read it by eye without a decoder.

What You Can and Can't Recover Without the Schema

This is the key thing to understand. Without the .proto file, the decoder can give you the field numbers and wire types, but not field names, and the exact type is often ambiguous:

  • A varint could be an int, a bool, an enum, or a zig-zag-encoded signed number — the tool shows the raw value and the sint (zig-zag) interpretation side by side so you can judge.
  • A length-delimited field could be a string, raw bytes, or a nested message. The decoder tries to parse it as a nested message and shows text when the bytes are printable, but a value that happens to look like one form may really be another.

So treat the output as a well-informed interpretation of the bytes, not a definitive decode. With the schema you'd get names and exact types; without it, you get the structure.

A Worked Example You Can Reproduce

Decode these hex messages — the results match protoc --decode_raw exactly: 

08 96 01                        → Field 1 (varint): 150
12 07 74 65 73 74 69 6E 67       → Field 2 (length-delimited): "testing"
1A 02 08 01                     → Field 3 (nested): { Field 1 (varint): 1 }

In the first, 08 is the tag (field 1, wire type 0) and 96 01 is the varint 150. In the last, field 3 is length-delimited but its two bytes 08 01 parse cleanly as an inner message, so the tool shows it nested. The decoder also notes the zig-zag reading — 150 as a sint is 75 — which is the value you'd get if that field were declared sint32.

Frequently Asked Questions

Why does it show field numbers instead of names?
Field names aren't stored in a protobuf message — only field numbers are. The names live in the .proto schema, which this decoder doesn't have. It reads the wire format directly, so it can recover the numbers, wire types and values, but not the human-readable names.
Is a length-delimited field a string or a nested message?
Without the schema it's ambiguous — it could be a string, raw bytes or a nested message. The tool tries to parse it as a nested message and shows text when the bytes are printable, but that's a best guess. A value may genuinely be one form while looking like another.
What is the "sint" value shown next to a number?
It's the zig-zag-decoded signed interpretation. Protobuf's sint32/sint64 types encode signed numbers with zig-zag so negatives stay small, and the raw varint differs from the signed value. The tool shows both because, without the schema, it can't know which the field intends.
Does this match protoc --decode_raw?
Yes. It parses the same wire format and produces the same field-number, wire-type and value breakdown, including nested messages. The worked examples here decode identically under protoc --decode_raw.
Is my message uploaded anywhere?
No. Decoding runs entirely in your browser, so nothing you paste or drop is sent to a server. That makes it safe to inspect private or proprietary protobuf payloads.
