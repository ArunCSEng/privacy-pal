What ReDoS Is

ReDoS — Regular Expression Denial of Service — happens when a crafted input makes a regular expression take a huge amount of time to evaluate, hanging the thread that runs it. A single malicious string against a vulnerable pattern can pin a CPU core for seconds, minutes or effectively forever, which is enough to take a server down. It's a real risk wherever user input meets a regex: form validation, log parsing, routing rules. This tool checks a pattern for the weakness, in your browser.

Catastrophic Backtracking

The cause is "catastrophic backtracking." Backtracking regex engines try every possible way to match, and certain patterns create exponentially many ways. The usual culprits are structures where the same text can be divided many ways:

  • Nested quantifiers — (a+)+, (a*)* — the inner and outer repeats overlap.
  • Overlapping alternation under repetition — (a|a)*, (a|ab)*.
  • Unbounded wildcards repeated — (.*)+, (.*a)+.

Against input that almost matches — a long run of a followed by a character that fails the pattern — the engine backtracks through every combination before giving up, and the time grows exponentially with input length.

How the Tester Works

It combines two checks:

  1. Static analysis scans the pattern for the dangerous structures above and flags them before anything runs.
  2. A live, sandboxed test runs the regex against a synthesized attack payload inside a Web Worker, timing it against a two-second watchdog. If it finishes quickly, the pattern is safe on that input; if the watchdog has to kill it, you've reproduced catastrophic backtracking.

Running the regex in a Web Worker is what makes this safe to use: a pattern that would otherwise freeze the whole page is confined to a background thread the watchdog can terminate, so your browser stays responsive even when you test a genuinely dangerous expression.

ReDoS Depends on the Engine

An important caveat: whether a pattern is vulnerable depends on the regex engine. Backtracking engines — JavaScript, Python's re, Java, .NET, PCRE — are susceptible. Linear-time engines built on finite automata, such as RE2 (the default in Go, and usable from other languages) and Rust's regex crate, are immune to catastrophic backtracking by design. This tool runs in the browser's JavaScript engine, so a pattern it flags might still be perfectly safe under RE2. Test against the engine your code actually uses.

Fixing a Vulnerable Pattern

  • Remove the ambiguity. Rewrite nested quantifiers so text can only be split one way — often a+ instead of (a+)+.
  • Anchor and bound the pattern, and cap the length of input you feed it.
  • Use atomic groups or possessive quantifiers where your engine supports them (JavaScript doesn't natively, but many do) to stop backtracking.
  • Switch engines for untrusted input — a linear-time engine like RE2 removes the whole class of problem.

How to Use the Tool

  1. Enter the regex and any flags you use in production.
  2. Synthesize a payload (or set the probe length) and run the live test.
  3. Read both signals — the static flags and the measured execution time or watchdog kill.
  4. Treat a kill as a confirmed vulnerability for that engine, and rewrite the pattern.

Scope and Limits

  • Static detection is heuristic. It catches common dangerous structures but can miss unusual ones or flag a safe pattern — use it alongside the live test, not instead of it.
  • A clean live result isn't a proof. It tests one synthesized payload; a different input might still backtrack, so clean means "not triggered here," not "safe for all inputs."
  • Engine-specific. Results reflect the JavaScript engine; verify against the engine your application uses.
  • Runs locally. The pattern and payload are tested in your browser — nothing is uploaded.

Frequently Asked Questions

What makes a regex vulnerable to ReDoS?
Ambiguity that lets a backtracking engine match the same text many ways — typically nested quantifiers like (a+)+, overlapping alternation, or repeated unbounded wildcards. Against input that nearly matches, the engine explores exponentially many combinations, and evaluation time blows up with input length.
Why doesn't testing a dangerous pattern freeze the page?
Because the regex runs in a Web Worker — a background thread — with a two-second watchdog that terminates it if it hangs. The main page stays responsive, so you can safely reproduce catastrophic backtracking without locking up your browser.
Is a pattern that's flagged here always dangerous?
Not necessarily. ReDoS depends on the regex engine: backtracking engines like JavaScript, Python, Java and .NET are vulnerable, but linear-time engines such as RE2 and Rust's regex are immune. A pattern flagged here may be safe under RE2. Test against the engine your code actually uses.
How do I fix a vulnerable regex?
Remove the ambiguity — for example use a+ rather than (a+)+ — anchor and bound the pattern, cap input length, and use atomic groups or possessive quantifiers if your engine supports them. For untrusted input, consider a linear-time engine like RE2, which eliminates the problem entirely.
Does a clean result mean my regex is completely safe?
No. The live test uses one synthesized payload, so a clean pass means it wasn't triggered by that input, not that no input could ever trigger it. Combine the static analysis with the live test, and reason about your pattern's structure rather than relying on a single probe.
