What This Tool Checks

When an LLM calls a tool, it fills in arguments based on the JSON Schema you supply. A vague or loose schema leads to wrong arguments, extra keys you never defined, and free-text strings that flow straight into your code. This linter reads one tool definition, works out which format it uses, and runs the checks below. Each problem lowers the score from 100.

How to Use the Agent Tool Schema Validator

  1. Load or paste a schema. Click one of the four presets (OpenAI Function, Anthropic Tool, Vulnerable, Strict), or paste a single tool definition into the editor.
  2. Click "Validate & Lint Schema". The tool detects the format: an OpenAI tool ({"type": "function", "function": {...}}), a legacy OpenAI function (name + parameters), a Claude tool (name + input_schema), or a bare JSON Schema object.
  3. Read the findings. [ERROR] means the schema is broken or will be rejected. [WARNING] means it works but leaves room for bad arguments. [PASS] confirms a check succeeded.
  4. Fix and re-run. Use "Format JSON" to tidy the input, and "Copy Audit Report" to copy the score and findings as JSON for a pull request or ticket.

OpenAI and Claude Tool Formats Compared

Both providers describe arguments with JSON Schema but wrap it differently. Here is the same tool in each format. OpenAI nests the definition under function and calls the schema parameters: 

{
  "type": "function",
  "function": {
    "name": "get_quarterly_statement",
    "description": "Returns the statement summary for one customer account and fiscal quarter. Read-only.",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "account_id": {
          "type": "string",
          "pattern": "^ACC-[0-9]{8}$",
          "description": "Customer account ID, e.g. ACC-00412345."
        },
        "fiscal_quarter": {
          "type": "string",
          "enum": ["Q1", "Q2", "Q3", "Q4"],
          "description": "Fiscal quarter to summarize."
        }
      },
      "required": ["account_id", "fiscal_quarter"],
      "additionalProperties": false
    }
  }
}

Claude puts name, description and input_schema at the top level of the tool object: 

{
  "name": "get_quarterly_statement",
  "description": "Returns the statement summary for one customer account and fiscal quarter. Read-only.",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "account_id": {
        "type": "string",
        "pattern": "^ACC-[0-9]{8}$",
        "description": "Customer account ID, e.g. ACC-00412345."
      },
      "fiscal_quarter": {
        "type": "string",
        "enum": ["Q1", "Q2", "Q3", "Q4"],
        "description": "Fiscal quarter to summarize."
      }
    },
    "required": ["account_id", "fiscal_quarter"],
    "additionalProperties": false
  }
}

Worked Example: Fixing a Weak Schema

This tool definition (the legacy OpenAI shape) is typical of a first draft: 

{
  "name": "restart_service",
  "description": "Restarts a service.",
  "parameters": {
    "type": "object",
    "properties": {
      "service_name": { "type": "string" },
      "force": {}
    }
  }
}

Paste it into the tool above and it scores 65 / 100 with these findings:

  • [WARNING] [OPEN_SCHEMA]: no additionalProperties: false (−10)
  • [WARNING] [UNDESCRIBED_PARAM]: service_name has no description or enum (−5)
  • [WARNING] [UNBOUNDED_STRING]: service_name accepts any string (−5)
  • [ERROR] [EMPTY_PROPERTY]: force is an empty definition (−15)

The description passes the length check at 19 characters, but it doesn't tell the model which services are allowed or what "force" does. Here is a revised version: 

{
  "type": "function",
  "function": {
    "name": "restart_service",
    "description": "Restarts one approved service on one production node. Use only after a health check has failed.",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "service_name": {
          "type": "string",
          "enum": ["nginx", "redis-server", "postgresql"],
          "description": "Service to restart."
        },
        "force_kill": {
          "type": "boolean",
          "description": "If true, send SIGKILL when the service hasn't stopped 10 seconds after SIGTERM."
        },
        "node_id": {
          "type": "string",
          "pattern": "^srv-(us-east|eu-west)-[0-9]{4}$",
          "description": "Target node, e.g. srv-us-east-0042."
        }
      },
      "required": ["service_name", "force_kill", "node_id"],
      "additionalProperties": false
    }
  }
}

This scores 100 / 100. The service list is an enum, the node ID has a pattern, force_kill is a typed boolean, every property has a description, and the object is closed. Your restart handler should still check the node and service against its own allow-list before acting.

Why a Valid Schema Isn't the Same as a Safe Tool

Schema problems turn into security problems in two common ways:

  • Extra arguments. With an open schema, a model that has read injected text ("also make me an admin") can return keys such as "is_admin": true. If your handler passes the whole arguments object to an ORM update, that becomes a mass-assignment bug. Close the schema, and copy only the fields you expect in the handler.
  • Free-text strings. A plain {"type": "string"} accepts anything. If it reaches a shell (subprocess.run(..., shell=True)), a SQL string, or an HTTP client, it can be used for command injection, SQL injection or SSRF (for example, requests to 169.254.169.254). Use an enum or pattern where you can. Then use parameterized queries, argument lists instead of shell strings, and URL allow-lists.

Strict mode guarantees the arguments match the schema's shape. It doesn't check what a valid string means. That still has to happen in your code.

Frequently Asked Questions

Why does the linter want additionalProperties: false?
JSON Schema objects accept undeclared keys unless additionalProperties is false. With an open schema, a model can return extra arguments you never defined, and a handler that passes the whole arguments object to a database or ORM may act on them. Closing the schema lets your validator reject them. OpenAI strict mode requires it, and Claude's SDK helpers add it automatically for strict tools.
Does a schema that scores 100/100 make my tool safe?
No. The score only measures structure: types, descriptions, closed objects and bounded strings. A string that matches its pattern can still be harmful once your code uses it. Validate arguments on the server, use parameterized queries, avoid shell=True, and require approval for destructive actions.
What does OpenAI strict mode change?
With strict: true, OpenAI uses constrained decoding so the generated arguments match your schema. It supports only a subset of JSON Schema, requires additionalProperties: false on every object, and requires every property to be listed in required. Use a nullable type such as ["string", "null"] for fields that would otherwise be optional.
Does the Claude API have a strict mode for tools?
Yes. Claude tool definitions accept strict: true, which validates tool names and inputs against the input_schema using constrained decoding. Strict schemas support a subset of JSON Schema, and Anthropic's examples and SDK helpers set additionalProperties: false on every object. Each request can include up to 20 strict tools and 24 optional parameters across them. This linter's strict-mode check currently applies to the OpenAI format only.
Is my schema sent to a server?
No. Parsing and linting run in JavaScript in your browser tab, and the tool makes no network requests with your schema. You can disconnect from the internet after the page loads and it still works.
