What This Tester Does

CORS (Cross-Origin Resource Sharing) decides whether JavaScript on one website may read responses from another. The browser sends an Origin header, and the server answers with Access-Control-Allow-Origin and related headers. If they don't allow the calling site, the browser blocks the script from reading the response.

This tool makes a real fetch() request from this page to the URL you enter, so the request carries this site's origin. The question it answers is: can a page on this origin read that endpoint from a browser? It isn't a general CORS scanner for your own frontend's origin.

How to Read the Results

  • "Cross-Origin Request Blocked by Browser" means the fetch failed. That's usually CORS, but a network error, DNS failure, invalid certificate or HTTP-from-HTTPS block looks identical to JavaScript. Your browser console shows the real reason.
  • A success banner means the browser allowed this page to read the response.
  • The Access-Control-Allow-Origin value is often not read from the server. Browsers hide CORS response headers from scripts unless the server lists them in Access-Control-Expose-Headers. When the header is hidden, the tool fills in "* (Permissive / Cleared)", or this page's origin if credentials were included. So a "wildcard" warning may be wrong.
  • "Allow-Credentials: true (Required by fetch)" is likewise inferred: if a credentialed request succeeded, the server must have allowed credentials.

How to Use the CORS Tester

  1. Enter an endpoint URL and method. The tool really sends this request, so don't use a method like DELETE against a live endpoint you don't own.
  2. Tick "Include Credentials" to send cookies and see whether a credentialed cross-origin read is allowed.
  3. Tick "Force Preflight Probe" to add a custom header (X-BitDark-Preflight-Probe). That makes the browser send an OPTIONS preflight first, testing whether the server allows custom headers.
  4. Confirm with curl, which shows the actual headers (see below).

Checking CORS Properly with curl

Send your own Origin header and read the response headers directly: 

# Does the server reflect an arbitrary origin?
curl -s -D - -o /dev/null -H "Origin: https://evil.example" https://api.example.com/v1/user

# Preflight for a custom header and method
curl -s -D - -o /dev/null -X OPTIONS \
  -H "Origin: https://evil.example" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: Authorization" \
  https://api.example.com/v1/user

If the response contains Access-Control-Allow-Origin: https://evil.example together with Access-Control-Allow-Credentials: true, any website can read that endpoint as the logged-in user. Fix it with an explicit allow-list of origins.

CORS Rules Worth Knowing

  • A wildcard can't be combined with credentials. Browsers reject Access-Control-Allow-Origin: * on credentialed requests, which is why some servers reflect the origin instead. That's only safe with a strict allow-list.
  • Don't allow null. Sandboxed iframes and local files send Origin: null, so allowing it lets attackers in.
  • Simple requests skip the preflight. GET, HEAD and POST with standard headers and form-style content types are sent straight away. CORS only stops the reading of the response, so the server still processes the request. Protect state-changing endpoints against CSRF.
  • Send Vary: Origin when the allowed origin changes per request, so caches don't serve one site's CORS headers to another.

Frequently Asked Questions

Does this tool send a request to the URL I enter?
Yes. It makes a real fetch request from your browser to that URL, carrying this site's Origin header and your IP address, plus your cookies for that site if you tick Include Credentials. Only test endpoints you're allowed to test, and avoid methods that change data on live systems.
Why does it show a wildcard when my server allows a specific origin?
Browsers hide Access-Control-Allow-Origin from JavaScript unless the server lists it in Access-Control-Expose-Headers. When it's hidden and the request succeeds, the tool assumes "*". Check the real value with curl or your browser's Network tab.
Why is my API blocked here but works from my own app?
The request comes from this site's origin, not your app's. If your server allows only your own domains, it will correctly block this page. That means your allow-list is working.
What is the most dangerous CORS misconfiguration?
Reflecting whatever Origin the browser sends, together with Access-Control-Allow-Credentials: true. Any website can then make requests as the logged-in user and read the responses. This tool doesn't flag that case, so test for it with curl using a made-up Origin.
Does CORS protect my API from attackers?
No. CORS only controls whether browsers let scripts read responses. Tools like curl ignore it, and simple cross-site requests still reach your server. Use authentication, authorization and CSRF protection on the server.
