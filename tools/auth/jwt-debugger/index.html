What a JWT Is

A JSON Web Token (RFC 7519) is three Base64url parts joined by dots: header.payload.signature. The header says which algorithm signed the token; the payload holds the claims (who the user is, when the token expires); the signature lets the server confirm the token hasn't been changed. The header and payload are only encoded, not encrypted, so anyone can read them. This debugger decodes all three and, for HS256, checks the signature against a secret you provide.

What This Tool Shows

Field What it reports
Algorithm (alg)The signing algorithm from the header, or none
Token Type (typ)Usually JWT
Expiration (exp)Whether the exp claim is in the past, and the time remaining or the expiry date
Signature VerificationFor HS256, whether the signature matches your secret; for other algorithms, decode only

An alg: none token is flagged as unsigned. RS256, ES256 and EdDSA tokens are decoded and their claims shown, but the tool doesn't verify them, because that needs the issuer's public key rather than a shared secret.

How to Use the JWT Debugger

  1. Paste a token into the encoded box. The header and payload decode as you type, and the expiry status updates.
  2. To verify an HS256 token, enter the signing secret. Tick "Secret is Base64 encoded" if your secret is stored that way.
  3. Read the banner. "Signature Verified" means the token is authentic for that secret; "Verification Failed" means the secret is wrong or the token was altered.
  4. Copy the decoded JSON for a bug report or test. Prefer test tokens over live ones.

The signature is HMAC-SHA256(header.payload, secret), Base64url-encoded. Change a single character of the payload or the secret and the signature no longer matches, which is exactly how tampering is detected. Reading the Standard Claims

ClaimMeaning
issIssuer: who created the token
subSubject: who the token is about, often a user ID
audAudience: who the token is for; your service should check it names you
expExpiry, as a Unix timestamp in seconds
nbfNot valid before this time
iatIssued-at time
jtiA unique token ID, useful for revocation

Timestamps are seconds since 1970, not milliseconds. This tool reads exp and tells you whether the token has expired; a real server must enforce that, and should also check nbf, iss and aud.

What Verifying a Token Does and Doesn't Prove

A valid signature proves the token was issued by someone who holds the secret (HS256) or private key (RS256/ES256) and hasn't been changed since. It does not prove the token is still valid for use. The server must also:

  • Pin the algorithm. Decide which algorithm you accept and reject the rest. Don't trust the alg in the header to choose how to verify, or an attacker can switch an RS256 token to HS256 and sign it with your public key as the secret. The JWT Best Current Practices (RFC 8725) covers this.
  • Reject alg: none unless you specifically expect unsigned tokens, which is rare.
  • Check expiry and timing (exp, nbf), with only a small allowance for clock differences.
  • Check iss and aud so a token meant for another service isn't accepted by yours.
  • Use a strong HS256 secret of at least 256 bits, or asymmetric keys, so the secret can't be guessed.

Frequently Asked Questions

Is a JWT encrypted?
No. A standard JWT (JWS) is signed, not encrypted. The header and payload are only Base64url-encoded, so anyone can read them. Never put secrets such as passwords in a token payload. If you need the contents hidden, use JWE encryption.
Why can't this tool verify my RS256 token?
RS256, ES256 and EdDSA are asymmetric: they're signed with a private key and verified with the matching public key. This tool decodes them and shows the claims, but signature verification needs the issuer's public key, which isn't a shared secret you can type in here.
What does "alg: none" mean?
It's a token with no signature. The standard allows it, but accepting one means anyone can forge a token by writing any claims and leaving the signature empty. Servers should reject alg: none unless they have a specific reason to allow it.
Is the exp claim in seconds or milliseconds?
Seconds since 1 January 1970 (Unix time), per RFC 7519. A common bug is to use JavaScript's Date.now(), which is in milliseconds; that makes a token look valid for thousands of years. This tool reads exp as seconds.
Is my token or secret sent anywhere?
No. Decoding and HS256 verification run in your browser with the Web Crypto API, and the tool makes no network requests with your token or secret. Even so, avoid pasting live production tokens; use a test token where you can.
