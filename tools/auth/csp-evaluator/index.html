What CSP Does

A Content Security Policy is a response header that tells the browser which scripts, styles, frames and other resources a page may load. Its main job is to limit cross-site scripting (XSS): even if an attacker injects a <script> tag, the browser refuses to run it unless the policy allows it. It's a second layer of defence, so you still need to escape output and sanitise input.

Script checks use script-src, or fall back to default-src if it isn't set, which matches browser behaviour. The rating is "Poor / High Risk" with any high finding, "Moderate Hardening" with any medium one, and "Strict / Strong" otherwise.

How to Use the CSP Evaluator

  1. Copy your policy from the Content-Security-Policy response header (Network tab in developer tools), without the header name.
  2. Paste it and click "Evaluate Policy", or load a sample to compare.
  3. Fix high findings first, then use the parsed directive map at the bottom to confirm each directive was read as you intended.
  4. Test in report-only mode before enforcing: send the policy as Content-Security-Policy-Report-Only and watch for violations.

The evaluator reliably catches the obvious problems. It doesn't judge host allow-lists, which are the most common reason real policies fail. Google researchers' 2016 study "CSP Is Dead, Long Live CSP!" found that the large majority of real-world allow-list policies could be bypassed. That's why nonce- or hash-based policies are now recommended.

A Recommended Starting Policy

Content-Security-Policy:
  script-src 'nonce-{RANDOM}' 'strict-dynamic' https: 'unsafe-inline';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self';
  form-action 'self'
  • Generate a new random nonce for every response (at least 128 bits, base64) and add it to each <script nonce="…"> tag. A fixed nonce, like the one in the sample, offers no protection.
  • 'strict-dynamic' lets trusted scripts load further scripts, and makes modern browsers ignore host lists and 'unsafe-inline'. https: and 'unsafe-inline' are fallbacks for very old browsers only.
  • frame-ancestors only works as a header. It's ignored in a <meta> tag, so use the header for clickjacking protection.

Frequently Asked Questions

Does "Strict / Strong" mean my CSP is secure?
Not necessarily. The evaluator doesn't assess host allow-lists, so a policy that allows a public CDN or a large domain can still be bypassed. Prefer nonces or hashes with 'strict-dynamic' over lists of hosts.
Why are domain allow-lists risky in script-src?
Any script hosted on an allowed domain can run on your page. Public CDNs serve thousands of libraries, and many large sites have JSONP endpoints or old library versions that attackers can reuse to run their own code. Nonce- or hash-based policies avoid this.
Is 'unsafe-inline' always dangerous?
In script-src, yes, unless the policy also has a nonce or hash. Browsers that support CSP Level 2 or later then ignore 'unsafe-inline', and it only applies as a fallback in very old browsers. In style-src it's much lower risk and often needed.
Do I still need object-src 'none' now that Flash is gone?
Yes. It stops <object> and <embed> elements from loading content, which closes some injection paths, and it's part of Google's recommended strict CSP. Setting default-src 'none' also covers it.
Is my policy sent anywhere?
No. Parsing and checks run in JavaScript in your browser, and the tool makes no network requests with your policy. It doesn't fetch or test your website.
