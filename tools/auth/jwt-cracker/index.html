Why Weak JWT Secrets Are a Problem

A JSON Web Token signed with HS256 is protected by a single shared secret. The server uses that secret both to sign tokens and to verify them. Anyone who learns the secret can forge a valid token for any user, including an admin. If the secret is a dictionary word or a short string, an attacker who has one real token can test candidate secrets offline until a signature matches, without ever contacting your server.

This tool lets you run that same check against your own tokens, so you can confirm your signing secret isn't guessable before an attacker does. Only test tokens and secrets you are authorised to test.

How the Audit Works

Paste an HS256 token and a wordlist. For each candidate, the tool recomputes the HMAC-SHA256 signature over the token's header and payload and compares it with the token's real signature. A match means that candidate is the signing secret. It never contacts the server, because verifying a signature needs only the public parts of the token plus the guessed secret.

  • HS256 only. The tool rejects other algorithms. RS256, ES256 and EdDSA sign with a private key that isn't in the token, so there's nothing to guess this way.
  • Dictionary attack. It tests the exact strings you provide, one per line. It doesn't generate variations or try every possible character combination.
  • Load a bigger wordlist with "Load Wordlist File" to test against a real password list.

How to Use It

  1. Try the demo first. Pick a preset secret and click to generate a valid token, then start the audit to watch a weak secret fall.
  2. Test your own token. Paste a real HS256 token from your app (preferably a test-environment one) and run it against a password list.
  3. Read the result. "Secret Key Cracked" means your secret is weak and must be rotated. "Wordlist Exhausted" means it wasn't in that list, which is reassuring but not proof of strength (see below).
  4. If a secret is found, rotate it everywhere and invalidate existing tokens, since anyone who had the secret could have forged tokens.

In the browser, this single-threaded tool tested roughly 1,000 to 2,000 candidates per second. That's fine for a quick check, but it's far slower than real attack tools. Auth0's own testing showed a 32-bit secret falling in about 6 seconds and the word secret in under an hour with a native cracker, and GPU-based tools run many orders of magnitude faster still. So "Wordlist Exhausted" here only means your secret survived that list at this speed, not that it's strong.

Choosing a Secret That Can't Be Cracked

  • Follow the spec minimum. RFC 7518 requires an HS256 key of at least 256 bits (32 bytes). Auth0 recommends treating that as the floor and uses 512-bit secrets itself.
  • Make it random, not memorable. Generate it from a cryptographically secure source, for example openssl rand -base64 48, and never reuse a password, app name or environment word.
  • Keep it out of code. Store it in a secret manager or environment variable, not in your repository or client-side code.
  • Consider asymmetric signing. RS256 or ES256 sign with a private key and verify with a public one, so a leaked verification key can't forge tokens and there's no shared secret to brute-force.
  • Reject alg: none and algorithm switching. Pin the expected algorithm on the server so an attacker can't downgrade a token.

Frequently Asked Questions

Is this legal to use?
Use it only on tokens and secrets you own or are authorised to test, such as your own application in a test environment. Testing tokens from systems you don't control may be illegal. It's a defensive tool for checking that your own signing secret is strong.
Does "Wordlist Exhausted" mean my secret is secure?
No. It only means the secret wasn't in the list you tested, at this browser's speed. A dedicated GPU cracker is far faster and uses much larger lists. A short or word-based secret can still be broken. Use a long random secret of at least 32 bytes.
Why does it only support HS256?
HS256 uses one shared secret for signing and verifying, so a guessed secret can be checked against a token. RS256, ES256 and EdDSA use a private signing key that isn't in the token, so there's nothing to brute-force from the token alone.
What should I do if a secret is cracked?
Replace it with a new long random secret, roll it out to every service that verifies tokens, and invalidate existing sessions and tokens. Assume any token signed with the weak secret could have been forged, and review logs for suspicious activity.
Is my token uploaded?
No. Parsing, signing and comparison run in your browser with the Web Crypto API, and the tool makes no network requests with your token or wordlist. Even so, prefer a test token over a live production one.
