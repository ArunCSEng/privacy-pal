The Real Fix Is Parameterized Queries

SQL injection happens when user input is concatenated into a query so that the input can change the query's structure. The reliable defence is not to escape the input but to keep it out of the query text entirely, using parameterized queries (prepared statements). You send the SQL with placeholders, and the values separately; the database driver treats the values strictly as data, never as SQL. This tool shows that pattern first, and also shows engine-specific escaping for the cases where a parameter can't be used.

A plain example makes the point. The surname O'Brien contains an apostrophe. Concatenated into a query it breaks the SQL and, with a crafted value, could rewrite it. With a parameter, O'Brien is just a string: 

-- Parameterized (the value is bound separately, never parsed as SQL)
SELECT * FROM accounts WHERE username = ?;
-- bound value: O'Brien

How to Use This Tool

  1. Prefer the parameterized output. Copy the placeholder style your driver uses and bind the value through the driver, rather than building the string yourself.
  2. Use the escaping output only as a fallback, for a database or query fragment that genuinely can't be parameterized.
  3. Pick the output for your actual engine. MySQL, PostgreSQL and SQLite escape differently; using the wrong one can leave a hole.
  4. Treat this as a learning and reference aid, not a sanitizing library to paste into production.

Why Escaping Alone Is Risky

  • It's context-specific. The escaping here assumes the value sits inside single quotes. Dropped into a numeric field, a LIKE pattern, or an unquoted spot, the same "escaped" value can still be unsafe.
  • Identifiers aren't parameters. Table and column names can't be bound as parameters. Never build them from user input; choose them from a fixed allow-list, and only quote as a secondary measure.
  • Charset and mode matter. Correct MySQL escaping depends on the connection character set, and MySQL's NO_BACKSLASH_ESCAPES mode changes the rules to ANSI quote-doubling. A generic escaper that ignores these can be bypassed, which is one reason to let the driver do it.
  • Hand-built strings drift. Every place you concatenate is a place to get it wrong. Parameterized queries remove the concatenation entirely.

A Few Good Habits

  • Parameterize everywhere, including WHERE, INSERT, IN (...) lists and LIMIT values.
  • Use an ORM or query builder that parameterizes by default, and be cautious with any "raw" escape hatch it offers.
  • Validate input for type and range as well (a numeric ID should be an integer), as defence in depth.
  • Least privilege. The app's database user should have only the rights it needs, so an injection, if one slips through, does less damage.

Frequently Asked Questions

Should I escape input or use parameterized queries?
Use parameterized queries (prepared statements). They keep user data out of the SQL text entirely, so there's nothing to escape. Reserve manual escaping for the rare spots that can't be parameterized, and prefer your driver's own escaping function over hand-built strings.
Do parameterized queries stop all SQL injection?
They stop injection into the values you bind, which is the vast majority of cases. They can't parameterize table or column names or other SQL keywords, so build those from a fixed allow-list, never from user input.
Why is there a different output for each database?
MySQL, PostgreSQL, SQLite and SQL Server quote and escape strings and identifiers differently. Using the wrong engine's rules can leave an input unsafe, which is another reason to let the database driver handle it through parameters.
Can I just strip out quotes and keywords instead?
No. Blocklisting characters or words like SELECT or DROP breaks legitimate input (names, prose) and is easy to evade with encoding, comments or alternative syntax. Parameterize the values and validate their type instead.
Is my input sent anywhere?
No. All escaping and formatting run in your browser, and the tool makes no network requests with what you type. It's a reference aid, so still rely on your database driver's parameter binding in real code.
