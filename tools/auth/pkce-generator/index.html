What PKCE Is For

PKCE (Proof Key for Code Exchange, RFC 7636) protects the OAuth 2.0 authorization-code flow. Without it, an app that can't keep a client secret, such as a mobile or single-page app, is open to one attack: if someone intercepts the authorization code as it returns to the app, they can exchange it for tokens themselves. PKCE closes that gap by having the app prove, at the token step, that it's the same app that started the flow.

It works with two values the app creates:

  • code_verifier: a fresh random string, 43 to 128 characters from the unreserved set A–Z a–z 0–9 - . _ ~.
  • code_challenge: for the S256 method, the Base64url (no padding) encoding of the SHA-256 hash of the verifier.

The app sends the challenge when it starts the flow and the verifier when it exchanges the code. The server hashes the verifier and checks it matches the challenge it stored. An attacker who stole only the code never saw the verifier, so the exchange fails.

Worked Example: The RFC 7636 Test Vector

RFC 7636 Appendix B gives an official example. Paste its verifier into this tool and you get exactly the challenge below: 

code_verifier:  dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
code_challenge: E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
method:         S256

The steps are:

  1. Hash the verifier with SHA-256. The ASCII bytes of the verifier hash to: 
    13d31e961a1ad8ec2f16b10c4c982e0876a878ad6df144566ee1894acb70f9c3
  2. Base64url-encode those 32 bytes, with no padding, replacing + with - and / with _. That gives the challenge E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM.

We confirmed these values against RFC 7636 and a standard SHA-256 implementation; the tool produces the same result.

Using PKCE Correctly

  • Use S256, not plain. The plain method sends the verifier as the challenge, which gives no protection if the request is observed. RFC 7636 requires clients that can do SHA-256 to use S256.
  • One verifier per request. Generate a new random verifier each time and discard it after the exchange.
  • Enough randomness. The RFC requires the verifier to carry enough entropy; a 43-character random string from the unreserved set is the practical minimum, and longer is fine up to 128.
  • PKCE isn't a client secret. It proves continuity within one flow; it doesn't authenticate the app. Confidential servers should still use a client secret as well.
  • Still validate state. PKCE doesn't replace the state parameter, which protects against CSRF on the redirect.

Frequently Asked Questions

What's the difference between S256 and plain?
With S256 the challenge is the SHA-256 hash of the verifier, so seeing the challenge doesn't reveal the verifier. With plain they're identical, which gives no protection if the authorization request is observed. Use S256 unless a client genuinely can't compute SHA-256.
How long should the code verifier be?
Between 43 and 128 characters from the set A–Z, a–z, 0–9, and - . _ ~, chosen with a secure random generator. 43 is the minimum; this tool defaults to 64. Longer within the range is fine.
Do confidential server apps need PKCE?
It's recommended for all OAuth clients now, including confidential ones, as defense in depth. The OAuth 2.1 draft makes PKCE standard for the authorization-code flow. It complements, rather than replaces, a client secret.
Can I reuse a verifier and challenge?
No. Generate a new random verifier for every authorization request and use it only once. Reusing one weakens the protection, because an attacker who ever learns a verifier could use it again.
Are the values generated here sent anywhere?
No. The verifier and challenge are generated and hashed in your browser with the Web Crypto API, and the tool makes no network requests with them. The sample URL is only displayed, not called.
