Contextual XSS Sanitizer & Encoder

Encode an untrusted value for the exact spot it lands in a page: HTML body, HTML attribute, JavaScript string, URI component or CSS value. Each output uses OWASP-recommended contextual encoding, and everything runs in your browser.

Why XSS Encoding Is Context-Specific

The same untrusted string is dangerous in different ways depending on where it lands in a page. A value that's safe inside visible HTML text can break out of a quoted attribute, a JavaScript string, a URL or a CSS value if it isn't encoded for that exact spot. There is no single "escape for HTML" that covers them all, which is why this tool shows five separate outputs for one input. You copy the one that matches the sink your data goes into.

The Five Contexts

HTML attributea quoted attribute valueEncodes every non-alphanumeric character to &#xHH;
JS stringinside a quoted JavaScript string literalEncodes every non-alphanumeric to \uXXXX
URI componentone query-string or path parameterPercent-encodes, including ! ' ( ) *
CSS valuea CSS property valueEncodes every non-alphanumeric to \HH 

The aggressive "encode everything non-alphanumeric" approach for attributes, JavaScript and CSS is deliberate: it's the OWASP recommendation, because it stays safe even in the fiddly cases (unquoted attributes, values that start an expression) without you having to reason about each character.

A Worked Example You Can Reproduce

Type <script>alert('XSS')</script> into the input. The HTML-body and URI outputs are: 

HTML body:  &lt;script&gt;alert(&#x27;XSS&#x27;)&lt;&#x2F;script&gt;
URI:        %3Cscript%3Ealert%28%27XSS%27%29%3C%2Fscript%3E

In the HTML-body form the angle brackets become &lt; and &gt;, so the browser renders the text literally instead of running a script tag. The URI form matches JavaScript's encodeURIComponent with the extra characters ! ' ( ) * also percent-encoded, which is the safe form for a single URL parameter.

Encoding Is Not Sanitizing

These are output encoders: they make a string safe to insert as inert data into one context. They are the right tool when you're inserting untrusted text and want it shown, not interpreted. They are the wrong tool when you actually want to keep some user-supplied HTML (a comment with bold and links, say). Encoding that would display the tags as text; for that you need an HTML sanitizer such as DOMPurify, which parses the markup and strips only the dangerous parts.

Where Encoding Alone Isn't Enough

  • URLs in href or src. Percent-encoding a parameter doesn't stop a javascript: URL if the whole value is attacker-controlled. Also validate the scheme and allow only http/https.
  • Put the value where the encoder assumes. The JS-string output is safe inside a quoted string literal, not dropped raw into a <script> block or an inline event handler.
  • Encode once, at output. Encoding on input, or encoding twice, produces double-encoded text (&amp;lt;) and bugs. Store raw, encode when you render.
  • Prefer your framework's auto-escaping. React, Angular and server templating encode by default for the right context. Reach for manual encoding mainly where you bypass that (for example dangerouslySetInnerHTML or building a URL by hand).
  • Add a Content-Security-Policy as defence in depth, so a missed spot is less likely to execute.

How to Use the Tool

  1. Paste the untrusted value or load a sample payload.
  2. Identify the sink — where in the page this value will appear.
  3. Copy the matching output and place it in that context, keeping the surrounding quotes.
  4. Don't mix contexts: a value that is both in a URL and then in an attribute needs the encoders nested in the order the browser decodes them.

Everything runs in your browser; nothing you paste is uploaded. Treat the tool as a way to see and copy the correct encoding, alongside framework auto-escaping and a sanitizer for rich HTML — not as a standalone XSS fix.

Frequently Asked Questions

Why are there five outputs instead of one?
Because the safe encoding depends on where the value is inserted. The characters that break out of HTML text are different from those that break out of a JavaScript string, a URL or a CSS value. Pick the output that matches the exact spot the data goes into.
What's the difference between encoding and sanitizing?
Encoding turns a string into inert data for one context, so markup is shown as text. Sanitizing parses user-supplied HTML and removes only the dangerous parts while keeping safe tags. If you want to render user HTML, use a sanitizer like DOMPurify; if you want to display untrusted text, encode it.
Does encoding a URL parameter make a link safe?
It makes one parameter safe to embed, but it doesn't stop a javascript: or data: URL if the whole link is attacker-controlled. Validate the scheme too and allow only http and https for links you build from untrusted input.
Do I still need this if my framework auto-escapes?
Usually not for ordinary output — React, Angular and server templates encode for the right context automatically. You need manual encoding mainly where you bypass that, such as dangerouslySetInnerHTML, inline script, or URLs assembled by hand.
Is anything I paste sent to a server?
No. All five encoders run locally in your browser, so you can safely paste real payloads or production values. Nothing is uploaded or logged.
