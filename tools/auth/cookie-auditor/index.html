⚠️ Limitations & Disclaimer

This checks cookie attributes, not your whole session security. It doesn't evaluate expiry or cookie values, and browser defaults differ (Firefox doesn't apply SameSite=Lax by default). What This Auditor Checks

Paste one Set-Cookie header and the auditor parses its attributes and reports on each security-relevant one:

Attribute What it does Finding if missing or weak
HttpOnlyHides the cookie from JavaScript (document.cookie)High
SecureSends the cookie only over HTTPSHigh
SameSiteControls whether the cookie is sent on cross-site requests: Strict, Lax or NoneMedium if missing or None; High if None without Secure
__Host- / __Secure- prefixMakes the browser enforce stricter rules on the cookieLow if no prefix; High if a prefix's rules are broken
DomainShares the cookie with subdomainsMedium when present
PartitionedCHIPS: keeps a third-party cookie separate per top-level siteHigh if used without Secure

The rating is "Insecure / High Risk" if any finding is high, "Moderate Hardening" if any is medium, and "Hardened / Robust" otherwise.

How to Use the Cookie Auditor

  1. Copy a Set-Cookie header from your browser's developer tools (Network tab, response headers) or from curl -I https://yoursite.com.
  2. Paste one cookie at a time. With several lines, the tool merges them into one cookie and the results are wrong.
  3. Click "Audit Cookie" and fix high findings first.
  4. Check the parsed attributes at the bottom to confirm the tool read your header as intended.

Worked Example: Three Session Cookies

Set-Cookie header Rating Key findings
user_auth=admin:true; Path=/app;Insecure / High RiskMissing HttpOnly (high), missing Secure (high), no SameSite (medium)
session_id=…; Secure; HttpOnly; SameSite=Lax; Path=/; Domain=example.comModerate HardeningDomain shares it with every subdomain (medium); no prefix (low)
__Host-auth_token=…; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=7200; PartitionedHardened / RobustAll checks pass, including the __Host- rules

The first cookie has a second problem the tool doesn't look at: its value, admin:true, looks like a role stored on the client, which a user could simply edit. The auditor checks attributes only, never values.

A good default for a session cookie is: 

Set-Cookie: __Host-session=<random value>; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=28800

Use SameSite=Strict if users never need to arrive already logged in from links on other sites. Drop Partitioned for first-party session cookies; it's meant for cookies set inside embedded third-party content.

Cookie Prefix Rules

  • __Secure-: the cookie must have Secure and be set from an HTTPS page.
  • __Host-: the same, plus no Domain attribute and Path=/. The cookie is then locked to one exact host, so a subdomain can't overwrite it.

Browsers reject prefixed cookies that break these rules. The current cookie specification, RFC 6265bis, approved as an IETF Proposed Standard in December 2025 to replace RFC 6265, defines both prefixes along with SameSite.

What the Auditor Doesn't Check

  • Lifetime. Max-Age and Expires aren't evaluated. A session cookie with Max-Age=31536000 (one year) still rates "Hardened / Robust".
  • The value. Predictable IDs, user data or role flags in the value aren't detected.
  • Browser differences. When SameSite is missing, the tool shows "Lax Default". That's true in Chrome and Edge, but Firefox treats a missing SameSite as None. Always set it explicitly.
  • Your server. It reads the header you paste; it doesn't fetch your site.

Frequently Asked Questions

Does HttpOnly protect against XSS?
Only partly. HttpOnly stops JavaScript from reading the cookie, so an XSS attack can't simply steal the session token. But the attacker's script can still send requests from the victim's browser, and the browser will attach the cookie. You still need to prevent XSS itself.
Do all browsers default to SameSite=Lax?
No. Chrome and other Chromium browsers treat a cookie without SameSite as Lax. Firefox tested Lax-by-default but didn't ship it because sites broke, so it treats a missing value as None. Set SameSite explicitly on every cookie.
Should I use SameSite=Strict or Lax for login sessions?
Lax is the usual choice: the cookie is sent when a user follows a link to your site, so they arrive logged in, but not on cross-site form posts or embedded requests. Strict is safer but means users following a link from another site appear logged out on the first page.
What does the __Host- prefix protect against?
It locks the cookie to a single host over HTTPS with Path=/. A compromised or attacker-controlled subdomain can't set or overwrite a __Host- cookie for your main site, which blocks session-fixation and cookie-tossing attacks.
Is my cookie sent anywhere?
No. Parsing and checks run in JavaScript in your browser, and the tool makes no network requests with your header. Even so, avoid pasting live session tokens; replace the value with a placeholder.
