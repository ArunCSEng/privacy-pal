⚠️ Limitations & Disclaimer

A valid address is not a trustworthy one. This verifies that an address is internally consistent — correctly encoded, with a checksum matching its public key and version. It cannot tell you who operates the service, whether it is what it claims to be, or whether it is safe to visit. Phishing addresses pass this check by construction, because an attacker generates a real key pair and a real checksum. Note in particular that attackers brute-force readable prefixes, so comparing the first few characters of an address is the one comparison they plan for; compare the entire string against a source you trust. No connection is made to the address and nothing is transmitted. Results are provided as-is; BitDark.net is not liable for decisions made from them.

What This Tool Does

Paste a v3 onion address and the tool decodes it, pulls out its components, recomputes the checksum and tells you whether it matches. That answers a narrow but useful question: has this address been mistyped, truncated or corrupted somewhere between its source and your screen?

It is a real cryptographic check rather than a pattern match. Fifty-six base32 characters with the right shape will still fail if the checksum does not agree with the key and version bytes, which is exactly what you want from a validator.

How to Use the Tool

  1. Paste the address into the input. A full URL works too — the hostname is extracted from it.
  2. Click Validate Address. The result reports the outcome and the decoded components.
  3. Read the components: the 32-byte ed25519 public key, the 2-byte checksum and the version byte, which is 3 for every current address.
  4. Treat a failure as a transcription problem first. Truncation, a dropped character, or base32 confusion between similar-looking glyphs account for most failures, and re-copying from the original source usually resolves it.
  5. Compare the whole string against your trusted source, character by character or by pasting both into a diff. Checking only the start is precisely what a vanity-prefix attack defeats.
  6. Click Export Analysis JSON if you want a record of the decoded structure.

How the Checksum Is Computed

The address is base32 of 35 bytes: a 32-byte ed25519 public key, then two checksum bytes, then one version byte. To verify, the checksum is recomputed as the first two bytes of SHA3-256 over the literal ASCII string .onion checksum, followed by the public key, followed by the version byte. If those two bytes equal the ones carried in the address, the address is consistent.

Two bytes is sixteen bits, so a corrupted address has roughly a one in sixty-five thousand chance of passing by accident. That is ample for catching typing and transmission errors, which is all a checksum is for. It is not a signature and it provides no protection against a deliberately generated address.

The Address Is the Key

On the ordinary web, a hostname is a name and a certificate authority vouches for the connection between that name and a key. A v3 onion address skips the middle step: the address is the public key, so a client that reaches the service can verify it is talking to the holder of that key without consulting anyone.

That removes an entire trust hierarchy, and with it the ways that hierarchy fails. The cost is memorability: a key cannot be short, so the address is 56 characters of base32 that no one will recall. Version 2 addresses were 16 characters because they encoded a truncated hash of a weaker key, and they were retired after that truncation proved too short to resist collision attacks.

A Worked Example You Can Reproduce

Validate the example address shown in the input placeholder. It decodes to 35 bytes, the version byte is 0x03, and the embedded checksum matches the recomputed one, so the address passes. Now change a single character in the middle and validate again: the decode still produces 35 bytes and the version is still 3, but the checksum no longer matches, and the address is rejected. That is the check doing its job — a one-character error in a 56-character string is otherwise very easy to miss. Change the readable prefix instead and you get the same failure, which is a useful reminder that a familiar-looking opening tells you nothing on its own.

Frequently Asked Questions

Does a valid checksum mean the site is real or safe?
No. The checksum proves the address is internally consistent — that it was not corrupted in transit and was not invented at random. It says nothing about who runs the service or whether it is trustworthy. Phishing onion addresses are themselves perfectly valid; that is the point of generating them. Validity and legitimacy are different questions.
What exactly is checked?
The address is base32-decoded to 35 bytes, which split into a 32-byte ed25519 public key, a 2-byte checksum and a 1-byte version. The checksum is recomputed as the first two bytes of SHA3-256 over the literal string .onion checksum, followed by the public key and the version byte, and compared against the embedded value. A mismatch means the address is wrong.
Why are v3 addresses so long?
Because the address is the key. Fifty-six characters encode a full 32-byte ed25519 public key plus a checksum and version, so connecting to the address is also authenticating the service — no certificate authority involved. The older 16-character v2 addresses encoded a truncated hash of a weaker key, were vulnerable to collision attacks, and have been retired.
Can an attacker make an address that looks like the real one?
They can brute-force a chosen prefix, and tools to do so are widely available — which is why many real services have a readable word at the start. A prefix of a few characters is cheap; the full 56 are not. So comparing the first few characters is exactly the check an attacker plans for. Compare the whole string, or paste from a source you trust.
Does this tool connect to the address?
No. The validation is pure arithmetic on the string you provide: decode, hash, compare. No network request is made, nothing is resolved, and nothing is transmitted.
