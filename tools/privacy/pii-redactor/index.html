⚠️ Limitations & Disclaimer

Pattern matching catches structure, not meaning. The detectors here find things built to a recognisable format — a token with a fixed prefix, an address with a fixed shape. They do not find names, street addresses, internal hostnames, account numbers in a bespoke format, or anything else without a predictable pattern, and a credential in an unusual form can pass through untouched. The reverse also happens: the card detector applies no checksum, so any sixteen-digit sequence is replaced whether or not it is a card. Always read the sanitised output before you share it. One point matters more than any of this: if a real credential has already been pasted somewhere it should not have been, redacting it afterwards changes nothing — rotate the key. Everything runs in your browser and nothing is transmitted. Results are provided as-is; BitDark.net is not liable for decisions made from them.

What This Tool Does

Paste text into the left pane and a sanitised version appears on the right, with each detected identifier or credential replaced by a labelled placeholder so the structure of the text survives. The matching runs as you type, which makes it practical as a step between copying something and pasting it into a ticket, a chat or an AI prompt.

The labels matter. Replacing a key with a marker naming its type keeps the output readable for whoever is helping you, which means they can still reason about the problem without holding the secret.

How to Use the Tool

  1. Paste the original into Original Prompt / Source Payload — a stack trace, a config fragment, a log extract, a half-written prompt.
  2. Watch the sanitised pane populate. Each replacement is labelled by type, so you can see what was found and where.
  3. Read the output carefully. This is the step that does the real work. Look for anything still identifying: a person's name, an internal hostname, a customer reference, a file path containing a username.
  4. Fix what the matcher missed by hand in the output. A pattern cannot know that a particular string is an internal project codename; you can.
  5. Click Copy Clean to take the sanitised version, and paste that rather than the original.
  6. Click Clear All when finished, which removes both the original and the sanitised copy from the page.

Why Some Things Are Detectable and Others Are Not

Modern credentials are designed to be recognisable. A cloud access key, a source-control token and an API secret each follow a documented format — a fixed prefix, a known length, a defined character set — specifically so that scanning tools can find them in repositories and logs before an attacker does. That design decision is what makes detection reliable here.

Unstructured personal data has no such property. A name is a word. An address is a sentence. An internal hostname looks like any other hostname. No pattern distinguishes them from ordinary text, which is why every tool of this kind, including this one, is a filter rather than a guarantee, and why the human read-through is part of the process rather than an optional extra.

What Each Detector Matches, and Where It Misses

Nine patterns are in play, and knowing each one's edges tells you where to look yourself.

AWS keyAKIA followed by sixteen uppercase charactersOnly that prefix. Temporary session and role credentials use different prefixes and pass through.
GitHub tokenThe ghp_, gho_, ghu_, ghs_ and ghr_ prefixesClassic tokens predating the prefix scheme are not matched.

Bearer tokenThe literal word bearer followed by a tokenA token on its own, without the keyword, is not recognised.
EmailStandard address shapesObfuscated forms — spelled-out at and dot, or an address split across lines — are not addresses to a pattern.
IPv4Range-checked octets, so 999.1.1.1 is correctly ignoredVersion numbers that look like addresses can still match.
IPv6Full eight-group form and common compressed formsSome valid compressed and embedded-IPv4 forms are not covered.
UUIDThe standard 8-4-4-4-12 hex layoutOther identifier schemes look nothing like it and are not touched.

The card detector deserves the most attention, because it fails in both directions. Without a checksum, any sixteen-digit sequence is flagged — a millisecond timestamp, an order reference, part of a hash — so you will see placeholders where no card existed. And because the pattern requires exactly sixteen digits in four groups, the fifteen-digit cards used by one major issuer are not caught at all. Treat a card placeholder as a prompt to look, not as a finding, and never assume the absence of one means no card was present.

Redaction Does Not Undo a Leak

It is worth being blunt about this, because the instinct to tidy up afterwards is strong and it does not help. A key pasted into a chat, a ticket, a prompt or a commit has left your control. You do not know what retained it, what indexed it, what was backed up, or who read it. The only response that restores your position is rotation: revoke the old credential and issue a new one.

This tool is for the message you have not sent yet. Run text through it before sharing, not after discovering a problem.

Placeholders Beat Deletion

It is tempting to delete a secret outright, but a labelled placeholder is more useful to whoever reads the text. A support engineer who can see that a line contained an AWS access key, rather than a gap, can still diagnose a permissions problem. A colleague reading a stack trace can tell that two different placeholders mean two different addresses.

Keeping the shape of the data also keeps the text valid for anything that parses it. A configuration fragment with placeholders in the right positions can still be read as configuration; the same fragment with holes cut out usually cannot. That matters when the person helping you wants to reproduce the problem.

A Worked Example You Can Reproduce

Paste a short block containing an email address, an IPv4 address, a UUID and a plausibly formatted access key — invented values, not real ones. Each is replaced by a labelled placeholder and the surrounding text is untouched, so the block still reads as what it is. Now add a line naming a colleague, an internal server such as billing-db-prod-02, and a customer reference in your own organisation's format. None of those is replaced, because none of them has a shape to match. That contrast is the whole lesson: the tool removes what it can recognise, and the review step removes the rest.

Frequently Asked Questions

What does it detect?
Nine patterns with recognisable structure: email addresses, IPv4 and IPv6 addresses, UUIDs, sixteen-digit card numbers, AWS keys beginning AKIA, GitHub tokens, OpenAI secret keys and HTTP bearer tokens. Each has a shape a regular expression can match. Names, street addresses, internal hostnames and free-form identifiers have no such shape and are not detected at all.
Should I rely on it to make text safe for an AI prompt?
Use it as a first pass, then read the output yourself. Pattern matching catches the structured secrets people forget about and misses everything unstructured, so the review is not optional. The output is safer than the input; it is not certified safe.
A key appeared in a prompt I already sent. Is redacting it enough?
No. Once a credential leaves your control, treat it as compromised and rotate it. That means revoking the old key and issuing a new one, regardless of where it went or whether you believe it was read. Redaction protects the next message, never the one already sent.
Why does it flag IP addresses and UUIDs?
Because both are identifiers worth thinking about before sharing. An IP address can identify a network, a host, or roughly a person; a UUID in a log or URL is frequently a database key for a specific user or record. Neither is secret in the way a token is, but both leak more context than people expect when pasted into a ticket.
Is my text sent anywhere?
No. Matching and replacement run in your browser as you type. Nothing is transmitted, nothing is stored, and Clear All removes both panes from the page.
