⚠️ Limitations & Disclaimer

This clears storage for this website only, not for your browser. The same-origin policy confines every page to its own scheme, host and port, so what you see and clear here belongs to bitdark.net and nothing else. No page can reach the storage of an advertising network, a bank or a social site — to clear those you need your browser's own clear-browsing-data menu. What This Tool Does

Four storage mechanisms are read and reported: LocalStorage and SessionStorage, which hold simple string keys; IndexedDB, a full asynchronous database; and the Cache Storage API, which holds complete HTTP request and response pairs. Each panel shows what this origin currently holds, with the browser's own quota estimate alongside.

A simulate button writes synthetic records into all four so you can watch the audit detect them and the purge remove them. That matters more than it sounds: it means you can verify the tool against known state rather than taking its word for an empty result.

How to Use the Tool

  1. Click Scan Origin Storage to see what this origin currently holds. On a first visit the panels are usually near-empty, which is the baseline.
  2. Click Inject Test Records to write known synthetic values into all four mechanisms.
  3. Scan again. The badges should now show two LocalStorage keys, one SessionStorage key, one IndexedDB database and one cache. Confirming that the audit sees known data is what makes a later empty result meaningful.
  4. Reload the page before purging. This closes any database connection the inject step left open, and an open connection will block deletion indefinitely.
  5. Click Purge All Storage, then scan once more. Do not stop at the confirmation message — the scan is the evidence.
  6. If a database is still listed, something still holds it open. Close other tabs on this site, reload, and purge again.

Why Clearing Cookies Stopped Being Enough

For twenty years the privacy conversation was about cookies, and regulation followed: consent banners, cookie policies, cookie controls in every browser. Tracking adapted by moving elsewhere. An identifier in IndexedDB is not a cookie, is not covered by a cookie-clearing routine, and survives the action most people believe clears their tracking data.

The Cache Storage API is the least intuitive of these. It was designed so that offline-capable sites could store responses, but it will store any request and response pair a script constructs — including a fabricated URL whose response body is a tracking identifier. Nothing about that looks like storage to a user, and only code that calls the cache API explicitly will find it.

The Six Mechanisms, and Which Four Are Audited

Modern browsers give an origin several independent places to keep data. They differ in what they hold, how long it survives, and whether a page can reach it at all.

MechanismWhat it holdsLifetimeAudited here
LocalStorageString keys and valuesUntil deleted; survives restartsYes
SessionStorageString keys and valuesUntil the tab closesYes
IndexedDBStructured records and binary dataUntil deletedYes
Cache StorageWhole HTTP request and response pairsUntil deletedYes
CookiesSmall values sent with every requestMax-Age, or the sessionNo — HttpOnly ones are invisible to scripts
Origin Private File SystemA private virtual file treeUntil deletedNo

The two quota regimes are worth distinguishing. LocalStorage and SessionStorage are capped at a few megabytes and are synchronous, which is why writing a lot to them stutters the page. IndexedDB, Cache Storage and the Origin Private File System share a much larger pool sized from available disk, and all three are asynchronous — which is exactly why they became the preferred home for data meant to persist quietly.

How Identifiers Respawn

The technique usually called an evercookie writes the same identifier into several mechanisms at once. Clear one and the next page load repairs it: the script finds LocalStorage empty, reads the surviving copy out of IndexedDB, and writes it back. From the tracker's side nothing was lost; from yours, clearing appeared to work.

This is why simultaneous clearing matters, and why the useful question is not whether you cleared something but whether anything survived to restore it. That is also the honest argument for using your browser's own clearing function for anything serious: it operates across all origins at once, which no page can do.

The Same-Origin Boundary

It is worth being explicit about the limit, because tools in this category are frequently described as if they clean your browser. They cannot. A page runs inside a sandbox keyed to its exact origin, and storage APIs only ever address that origin. A page on this site cannot enumerate what any other site has stored, and a page on another site cannot read what this one holds.

That restriction is a security property rather than a limitation to work around — without it, any page you visited could read every token and database every other site had stored. The consequence for you is simple: this tool demonstrates and manages one origin, and browser-level clearing is what covers the rest.

A Worked Example You Can Reproduce

Scan, inject, scan again: the badges move from empty to two LocalStorage keys, one SessionStorage key, one IndexedDB database named for the audit, and one cache entry. Now purge without reloading first and scan once more. LocalStorage, SessionStorage and the cache are gone — but the database is often still listed, because the connection opened during injection is still open and a blocked delete waits rather than failing. Reload the page, purge again, and scan: this time the database goes too. The lesson generalises beyond this tool. A deletion request is not a deletion, and the only way to know storage is gone is to look again afterwards.

Frequently Asked Questions

Can this clear storage for other websites?
No, and no web page can. The same-origin policy confines a page to its own scheme, host and port, so this tool sees and clears only storage belonging to bitdark.net. It cannot enumerate, inspect or wipe anything held by an advertising network, a bank or a social site. For that you need your browser's own clear-browsing-data menu, which operates outside the sandbox every page lives in.
Does it delete cookies?
No. The audit covers LocalStorage, SessionStorage, IndexedDB and the Cache Storage API, and cookies are deliberately outside that set. Cookies marked HttpOnly are invisible to JavaScript by design — that flag exists precisely so that scripts cannot read or remove them — so any page claiming to purge all your cookies is overstating what it can reach.
Why did a database survive the purge?
Almost certainly because something still had it open. Deleting an IndexedDB database requires every connection to it to be closed first; while one remains open the delete request is blocked and simply waits, and it can wait indefinitely. Reload the page before purging, then scan again afterwards to confirm the result rather than assuming it.
What is an evercookie?
A tracking identifier written into several storage mechanisms at once. If the same value sits in LocalStorage, IndexedDB and the Cache API, clearing only one of them achieves nothing: on your next visit the script notices the gap, reads the surviving copy and writes it back everywhere. This is why clearing storage has to be simultaneous across mechanisms rather than one at a time.
Is anything sent to a server?
No. Every read and every deletion happens through browser APIs in your own browser, against this origin only. Nothing about your storage is transmitted, and the quota figure comes from the browser's own estimate.
