⚠️ Limitations & Disclaimer

This is a static text scan, not a server audit. It matches your pasted configuration against a fixed list of known weak settings and reports each with a line number, severity and fix. Because it pattern-matches rather than parsing Nginx's directive tree, it cannot follow inheritance from blocks you did not paste, may miss a setting written unusually, and can flag one inside a comment. It also cannot see your certificate chain, your upstream applications, your firewall, or which Nginx version is actually running. A clean result means nothing in its rule list matched — not that the server is secure. Verify against the running configuration with nginx -T and test the live behaviour. Everything runs in your browser and nothing you paste is uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them.

What This Tool Does

Most Nginx configurations grow by accretion: a block copied from a blog post years ago, a TLS line nobody has revisited since, a proxy section added in a hurry. The defaults are not always safe, and the weak settings are easy to miss because the server works perfectly well with them. This linter reads the configuration text you paste and points out the settings worth changing, with a line number and a concrete fix for each. It runs entirely in your browser, so pasting a real production file sends nothing anywhere.

How to Use the Tool

  1. Paste your configuration — a full nginx.conf, a single virtual host, or a block from sites-enabled. It is a text scan, so a fragment works; you do not need a complete valid file.
  2. Or compare the two samples — Load Vulnerable Sample loads a configuration with the common mistakes in it, and Load Hardened Sample loads the corrected equivalent. Linting each in turn is the quickest way to see exactly which lines the rules react to and what the fixed version looks like.
  3. Click Lint & Audit Config — the whole text is checked against every rule at once.
  4. Work through the findings by severity — each row gives the Severity, the Line number so you can find it in your editor, the Issue Category, and Diagnostic Details & Remediation explaining both the risk and the change to make. Fix the high-severity rows first: weak TLS and a missing HSTS header affect every request the server handles.
  5. Re-lint after editing — paste the corrected configuration back and run it again until only findings you have consciously accepted remain. Clear Workspace resets everything.

If a finding looks wrong, check whether the directive is inherited from a block you did not paste — the scan only sees the text in front of it.

Old TLS protocolsTLSv1 and TLSv1.1 are deprecated and have known weaknesses. Modern configurations should offer TLSv1.2 and TLSv1.3 only.
Missing Strict-Transport-SecurityWithout HSTS, a browser's first request can still be downgraded to plain HTTP and intercepted.
Missing X-Content-Type-OptionsLets browsers MIME-sniff a response into something executable, turning an upload into a script.

What the Linter Checks

The rule set is small and deliberately so: ten checks across three severities, each one a mistake that appears in real configurations rather than a style preference.

SeverityCheckWhy it matters
ErrorSyntax error (missing semicolon)nginx refuses to start, or starts on an older config you think you replaced.
ErrorUnbalanced block bracesDirectives silently land in the wrong context, so a rule you wrote never applies.
ErrorObsolete and broken SSL versionEnabling SSLv2 or SSLv3 exposes clients to attacks that have been practical for over a decade.
WarningInsecure alias path traversalThe single most dangerous nginx misconfiguration; covered in detail below.
WarningProxy URI forwarding pitfallA trailing slash on proxy_pass changes which path the backend receives.
WarningDeprecated TLS versionTLS 1.0 and 1.1 are retired and fail most compliance baselines.
WarningInsecure cipher suiteWeak or export-grade ciphers undo the benefit of an otherwise current TLS stack.
NoticeDirectory listing enabledautoindex on publishes a browsable index of whatever is in that directory.
NoticeInformation disclosureVersion banners tell a scanner precisely which advisories to try.
NoticeMissing hardening headersAbsent response headers leave browser-side protections switched off.

Two of these cause the incidents. The alias traversal and the proxy_pass trailing slash are both cases where the configuration is syntactically perfect and semantically wrong, so nothing complains and the behaviour is simply not what the author intended. The rest are the kind of thing a review catches; those two are not, which is why they are worth checking mechanically every time.

A Worked Example You Can Reproduce

Load the vulnerable sample and audit it. You will get a set of findings including deprecated TLS protocols, a missing HSTS header, server_tokens left on and directory listing enabled — each pinned to the line that caused it. Now load the hardened sample and audit again: the same structure, but the findings clear because the TLS line names only modern protocols, the security headers are present, and the information-disclosure settings are switched off.

Reading the two side by side is more instructive than the rule list, because the difference between them is small. A handful of lines separates a configuration that leaks its version and allows downgrade attacks from one that does not, and none of those lines affect whether the site works.

Where a Text Scan Stops

  • Inheritance is invisible. Nginx directives cascade from http to server to location. If you paste only a location block, a setting defined higher up is not visible to the scan.
  • It does not test the live server. A header can be set in the config and still be stripped or overwritten further along the chain. Confirm with an actual request.
  • It does not know your application. Permissive CORS may be entirely correct for a public read-only API and dangerous on an authenticated one. The linter flags the pattern; the judgement is yours.
  • The rule list is finite. Nothing matching does not mean nothing is wrong, only that none of these specific patterns were present.

Frequently Asked Questions

What does this linter check for?
It scans the configuration text for well-known weak settings: outdated TLS protocols, missing security headers such as HSTS and X-Content-Type-Options, server tokens left exposed, directory listing enabled via autoindex, overly broad CORS, proxy blocks missing forwarded headers, and patterns that can lead to path traversal or request smuggling. Each finding comes with a severity and a suggested fix.
Is it a real Nginx parser?
No, it is a text scan. That makes it fast and able to work on a fragment of a file or a single server block, but it means it matches patterns rather than understanding directive inheritance. A setting inherited from an outer block it cannot see, or one written unusually, may be missed, and something inside a comment can be flagged.
Why does it warn about server_tokens?
By default Nginx advertises its exact version in response headers and error pages. That tells an attacker precisely which known vulnerabilities to try. Setting server_tokens off removes the version string. It is not a fix on its own — keeping Nginx patched matters far more — but there is no reason to publish the number.
Does a clean result mean my server is secure?
No. It only checks the settings in its rule list, on the text you pasted. It cannot see your TLS certificate chain, your upstream applications, your firewall, or the Nginx version actually running. Treat a clean result as one quick check, and confirm the live behaviour against the running server.
Is my configuration uploaded anywhere?
No. The text you paste is scanned in your browser and nothing is sent to a server. The page makes no network request for your input, so you can check production configurations — which often contain internal hostnames and upstream addresses — without exposing them.
