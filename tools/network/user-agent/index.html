⚠️ Limitations & Disclaimer

A user-agent string is a claim, not a fact. It is a header the client chooses to send, and any client can send any value \u2014 changing it takes one command-line flag. Treat what this tool reports as what the request said about itself, never as verified identity, and never gate access or security decisions on it. Two further limits are worth knowing: parsing is pattern-matching against known formats, so an unusual or deliberately crafted string can be classified wrongly, and browsers are actively reducing the detail these strings contain, so version and device information is increasingly coarse by design. A result claiming to be Googlebot is especially weak evidence, since verifying a real crawler requires a reverse DNS check on the source address. What This Tool Does

A user-agent string is one of the strangest artefacts on the web: a line of text that names four products that are not running in order to satisfy compatibility checks written thirty years ago. Paste one here and it is separated into the browser, rendering engine, operating system and device it is actually describing, with the legacy tokens identified for what they are. It also recognises crawlers and command-line clients, which is handy when you are reading server logs and want to know what is really hitting an endpoint.

How to Use the Tool

  1. Enter a string — paste one from a server log, an analytics report, or a request you are debugging into Target User-Agent Header.
  2.   3. Click Parse String — the table fills with one row per detected component.
  4. Read the classification column — each row pairs a Component / Attribute with its Value & Classification, so you can see not just that a token is present but whether it is meaningful or a historical artefact. The Action column copies any single row.
  5. Compare against your expectation — if a log entry claims to be a browser but has no engine tokens, or claims a crawler without the matching structure, that mismatch is usually the interesting part.

Remember throughout that you are reading an assertion: a string identifying as Googlebot proves only that someone typed that text into a header.

Why Everything Claims to Be Mozilla

The string begins Mozilla/5.0 in essentially every browser, and no current browser is Mozilla. In the mid-1990s servers checked for that token before serving frame-based pages, so competing browsers added it to avoid being served a degraded version. Then each new entrant added the previous leaders' tokens for the same reason. Nobody could remove them afterwards, because somewhere a server was still checking.

So a modern Chrome string names Mozilla, AppleWebKit, KHTML, Gecko, Chrome and Safari in sequence. Only one or two of those are real. The tool labels which tokens actually describe the client and which are compatibility residue, which is the difference between reading the string and guessing at it.

It Is Self-Reported, and That Matters

The practical consequence of the string being client-supplied is that it is useful for statistics and useless for security. curl -A "anything you like" sets it in one flag; browser extensions change it per site. Any logic of the form "if the user-agent says X, allow Y" is bypassed by typing X.

This bites hardest with crawler verification. Plenty of traffic claims to be Googlebot because claiming it sometimes earns better treatment. Real verification means taking the source IP, doing a reverse DNS lookup, confirming it resolves into Google's domain, then forward-resolving that name back to the same address. The string alone is not evidence.

Client Hints and the Shrinking String

Browsers are deliberately reducing what these strings reveal, because a long and highly specific string is a fingerprinting surface: broadcast enough detail to every site on every request and the combination starts to identify you. Modern browsers report coarser versions and generic platform values instead.

Client Hints are the replacement. Rather than one crowded header sent everywhere, a site requests the specific fact it needs — platform, architecture, device model — and the browser decides whether to answer. Low-entropy hints are sent by default; higher-entropy ones require an explicit request, which makes the collection visible instead of passive. For anyone writing detection logic, the direction of travel is clear: the string will keep getting less informative, so depend on feature detection where you can and treat parsed values as hints rather than facts.

Frequently Asked Questions

Why does every browser claim to be Mozilla?
It is a historical accident nobody could undo. Early servers checked for Mozilla before serving frames, so every competing browser added the token to avoid being downgraded, then kept adding each other's names for the same reason. The result is that a modern Chrome string lists Mozilla, AppleWebKit, KHTML, Gecko and Safari, almost none of which describe what is actually running.
Can a user-agent string be trusted?
No. It is a header the client sends, and anything that sends HTTP can set it to whatever it likes — a one-line curl flag or a browser extension is enough. Use it for statistics, compatibility hints and rough debugging, never as a security control or an access check.
What are Client Hints, and why do they exist?
Client Hints replace the single crowded string with specific headers a site can request only when it needs them, such as platform or device model. The aim is to reduce passive fingerprinting: rather than broadcasting everything to every site on every request, a site asks for the narrow fact it needs, and that request is visible.
Why is the user-agent string being frozen?
Because its detail is a fingerprinting surface. Browsers now report reduced strings with coarse version and platform information, so values that were once precise — a full patch version, a specific Android model — are increasingly rounded off or fixed. Parsers that depend on that detail will slowly get less accurate, by design.
Is my user-agent uploaded anywhere?
No. Parsing happens in your browser and nothing is sent to a server. Load My Browser reads the string your browser already exposes to every site you visit, and it stays on this page — the tool makes no network request with it.
