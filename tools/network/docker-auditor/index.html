⚠️ Limitations & Disclaimer

This is a static text scan, not a full container audit. It matches your pasted Compose or run-flag text against a fixed list of well-known risky settings and reports each with a severity and a fix. Because it pattern-matches rather than fully parsing YAML, it can miss a setting written unusually and can flag one inside a comment, and it only knows the rules it ships with — a clean result means none of those patterns were found, not that the container is safe. Image vulnerabilities, secrets from other sources, and runtime policy (seccomp, AppArmor, read-only mounts) are out of its scope. Pair it with image CVE scanning and runtime hardening. Everything runs in your browser and nothing you paste is uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them.

What This Tool Does

A Docker container is only as safe as how it is run. A few settings in a Compose file or a docker run command can hand a container the keys to the host — and they are easy to leave in by accident, copied from a tutorial or a quick fix. This tool scans the text you paste for those settings and lists what it finds, with a severity and a suggested fix for each. It runs entirely in your browser; nothing you paste is sent anywhere, so it is safe to check real production files.

How to Use the Tool

  1. Paste your configuration — drop a docker-compose.yml, a fragment of one, or a docker run command into Docker Compose Configuration. It is a text scan, so a partial snippet works fine.
  2. Or compare the two samples — Load Vulnerable Sample loads a deliberately insecure service and Load Hardened Sample loads its fixed equivalent. Auditing each in turn shows exactly which lines the rules react to.
  3. Click Audit Security Configuration — the text is checked against every rule at once.
  4. Work through the findings — each row gives a Severity, the Security Vector it belongs to, the Detected Finding & Impact explaining why it matters, and concrete Remediation Guidance. Fix the critical rows first: privileged mode and a mounted Docker socket both mean container escape is straightforward.
  5. Re-audit after editing — paste the corrected config back in and run it again until only acceptable findings remain. Clear Workspace resets everything.

Remember the scan only knows its own rule list, so an empty result means nothing matched — not that the container is safe.

What It Flags, and Why

SettingWhy it matters
privileged: trueCritical. Gives the container nearly all host root capabilities and device access — escape is trivial.
/var/run/docker.sock mountCritical. Control of the host Docker daemon; the container can launch a privileged container and own the host.
SYS_ADMIN capabilityCritical. Broad administrative kernel calls, mounts and more — a frequent escape primitive.
network_mode: hostHigh. Removes network isolation; the container shares the host stack and can sniff local traffic.
pid: host / ipc: hostHigh. The container can see, trace or signal host processes, or reach host shared memory.
NET_ADMIN capabilityHigh. Lets the container reconfigure host routing and firewall rules.
Inline secretsHigh. Passwords, API keys or tokens written directly in the file.
user: root (UID 0)Medium. Runs as root instead of a low-privilege account.
No cap_drop: ALLMedium. Keeps Docker's default capability set instead of dropping all and adding back only what is needed.
Writable root filesystemLow. No read_only: true, so the container filesystem can be modified at runtime.
:latest (or untagged) imageLow. Non-deterministic deployments and hard-to-audit provenance; pin a specific tag or digest.

A Worked Example You Can Reproduce

Paste this deliberately insecure service and run the audit: 

services:
  app:
    image: myapp:latest
    privileged: true
    network_mode: host
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    environment:
      - API_KEY=supersecret123

The tool flags five issues: privileged mode and the Docker socket mount (both critical), host network mode and the inline API key (high), and the floating :latest tag (low). Each comes with a fix — drop privileged and add only the capabilities you need, remove the socket mount, use a bridge network, move the key to a secret, and pin the image. Remove those lines and re-run, and the findings clear, which is a good way to see exactly which pattern triggered each one.

Frequently Asked Questions

What does this tool check?
It scans the text you paste for a set of well-known risky container settings: privileged mode, a mounted Docker socket, host network/PID/IPC namespaces, added capabilities like SYS_ADMIN and NET_ADMIN, running as root, a missing cap_drop: ALL, a writable root filesystem, a floating :latest image tag, and secrets written inline. Each finding comes with its severity and a suggested fix.
Why is mounting the Docker socket so dangerous?
Mounting /var/run/docker.sock gives the container control of the host's Docker daemon. Anything inside can then start new containers — including a privileged one that mounts the host filesystem — which is effectively root on the host. It is one of the most common container-escape paths, so the tool flags it as critical.
Is it a full YAML parser, or pattern matching?
It is a text scan: it matches patterns rather than fully parsing the YAML, so it is fast and works on partial snippets and run commands, but it can miss a setting written in an unusual way and can flag something inside a comment. Treat its findings as leads to confirm in the actual file, not a formal parse.
Does a clean result mean my container is secure?
No. It only checks the specific settings in its rule list. A clean result means none of those patterns were found, not that the configuration is safe — the base image may still have vulnerabilities, secrets may come from elsewhere, and runtime policy matters too. Pair it with image CVE scanning and runtime hardening (seccomp, AppArmor, read-only mounts).
Is my configuration uploaded anywhere?
No. The text you paste is scanned in your browser and nothing is sent to a server. The page makes no network request for your input, so you can check production compose files without exposing them.
