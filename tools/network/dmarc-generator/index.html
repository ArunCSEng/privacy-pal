Understanding RFC 7489 and Modern Email Authentication

For decades, the Simple Mail Transfer Protocol (SMTP, RFC 5321) operated on a principle of open, unauthenticated communication. When SMTP was engineered in the early 1980s, networks were localized and participants were presumed benign. Consequently, the basic protocol lacked any cryptographic mechanism to verify that the entity transmitting an email was authorized to use the domain displayed in the message's visible From: header.

This architectural flaw created an epidemic of cybercrime: business email compromise (BEC), brand impersonation, credential harvesting, and spear-phishing campaigns. To counter these threats, the Internet Engineering Task Force (IETF) developed two foundational protocols: Sender Policy Framework (SPF, RFC 7208) and DomainKeys Identified Mail (DKIM, RFC 6376).

While SPF and DKIM were vital leaps forward, they suffered from a critical vulnerability known as the identity disparity problem:

  • SPF verifies the Envelope Sender: SPF validates only the technical Return-Path (also called MAIL FROM or envelope sender), which is completely invisible to human recipients in standard email clients. An attacker could register evil-phish.com, configure valid SPF records for it, pass SPF checks completely, and yet display From: security@yourbank.com in the visible header.
  • DKIM signs arbitrary domains: DKIM proves that a message body and selected headers were signed by a cryptographic key belonging to a domain declared in the d= tag. However, the signing domain in d= does not need to match the domain in the visible From: header. An adversary could sign a spoofed email using their own throwaway domain's DKIM key, and the cryptographic signature would technically verify as valid.

To permanently close this loophole, the industry standardized Domain-based Message Authentication, Reporting, and Conformance (DMARC, RFC 7489). DMARC creates an unbreakable cryptographic bridge by introducing Identifier Alignment: requiring that the visible From: header domain matches the validated SPF domain and/or the validated DKIM signing domain. Furthermore, DMARC empowers domain owners to publish explicit enforcement instructions (none, quarantine, or reject) for receiving mail servers to execute whenever unaligned messages are detected.

The Mechanics of DMARC Identifier Alignment

The central intelligence of DMARC is the concept of alignment. An email may pass raw SPF checks or carry a valid DKIM signature, but if neither mechanism mathematically aligns with the domain displayed to the end user in the RFC 5322 From: header, DMARC produces a definitive FAIL verdict. 

+-------------------------------------------------------------------------------+
|                       RFC 5322 Visible From: Header                            |
|                          user@marketing.example.com                           |
+-------------------------------------------------------------------------------+
                                      |
         +----------------------------+----------------------------+
         |                                                         |
         v                                                         v
+-----------------------------+                           +-----------------------------+
|        SPF Alignment        |                           |       DKIM Alignment        |
|  RFC 5321 Return-Path (MailFrom) |                           |       DKIM Header Tag (d=)  |
+-----------------------------+                           +-----------------------------+
| Relaxed (aspf=r):           |                           | Relaxed (adkim=r):          |
|  Matches root 'example.com' |                           |  Matches root 'example.com' |
|  ===> PASS                  |                           |  ===> PASS                  |
|                             |                           |                             |
| Strict (aspf=s):            |                           | Strict (adkim=s):           |
|  Requires exact match       |                           |  Requires exact match       |
|  'marketing.example.com'    |                           |  'marketing.example.com'    |
|  ===> FAIL if parent used   |                           |  ===> FAIL if parent used   |
+-----------------------------+                           +-----------------------------+
         |                                                         |
         +----------------------------+----------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                          DMARC Evaluation Engine                              |
|           VERDICT: PASS if EITHER (SPF Aligns) OR (DKIM Aligns)               |
|                    FAIL if BOTH Mechanisms Fail Alignment                     |
+-------------------------------------------------------------------------------+

1. Relaxed Alignment (aspf=r, adkim=r)

Under relaxed alignment (the default specification), DMARC evaluates whether the authenticating domain and the visible From: domain share the same Organizational Domain (the root registered domain above the public suffix list, such as example.com).

For instance, if an email displays From: newsletter@sub.example.com, and the message is signed by d=example.com, relaxed DKIM alignment evaluates as PASS because both share the organizational root example.com.

2. Strict Alignment (aspf=s, adkim=s)

Under strict alignment, DMARC requires an exact, character-for-character match between the domains. In the example above, sub.example.com does not strictly match example.com, causing strict alignment to evaluate as FAIL. Strict alignment provides the highest level of cryptographic precision but requires dedicated DKIM keys and SPF Return-Paths for each distinct subdomain.

RFC 7489 Tag Specifications & Grammar Reference

A DMARC record is stored as a standard DNS TXT record at the sub-node _dmarc.<domain>. It is serialized as a semicolon-delimited list of key-value tag pairs governed by formal ABNF grammar:

Tag Status Permitted Values Default Technical Function
v Mandatory DMARC1 None Protocol version identifier. Must be the first tag in the record. Must be uppercase.
p Mandatory none, quarantine, reject None Policy action for receiving MTAs to execute against unaligned emails from the root domain.
sp Optional none, quarantine, reject Inherits p Subdomain policy override. Dictates enforcement behavior for all child subdomains.
pct Optional 1 to 100 100 Percentage of unaligned messages subjected to the policy action (useful for gradual testing).
rua Recommended Comma-separated mailto: URIs None Destination URIs where receiving mailbox providers transmit daily aggregate XML telemetry reports.
ruf Optional Comma-separated mailto: URIs None Destination URIs for receiving MTAs to transmit immediate, redacted forensic failure alerts.
adkim Optional r (relaxed), s (strict) r DKIM identifier alignment mode.
aspf Optional r (relaxed), s (strict) r SPF identifier alignment mode.
fo Optional 0, 1, d, s 0 Failure reporting options specifying which conditions trigger a ruf forensic report.
ri Optional Positive 32-bit integer (seconds) 86400 Requested aggregate report generation interval (86400 seconds = 24 hours).

The 3-Phase Enterprise Deployment Roadmap

Deploying DMARC is an operational migration, not an instantaneous switch. Activating p=reject prematurely without visibility into all third-party transactional mail channels will cause immediate, catastrophic email delivery failure for legitimate enterprise systems. 

[ Phase 1: Monitoring ]       [ Phase 2: Soft Enforcement ]       [ Phase 3: Strict Enforcement ]
    v=DMARC1; p=none;              v=DMARC1; p=quarantine;             v=DMARC1; p=reject;
       pct=100; rua=...              pct=25 -> 50 -> 100; rua=...        pct=100; rua=...
             |                                     |                                   |
             v                                     v                                   v
• Ingest daily XML reports           • Route failing mail to spam        • Block spoofed mail at boundary
• Audit third-party senders          • Verify zero false-positives       • Protect corporate brand equity
• Fix SPF/DKIM misalignments         • Mitigate rollout risks            • Qualify for BIMI certification

Phase 1: Pure Monitoring (p=none)

In Phase 1, you publish a record with p=none and a dedicated rua reporting inbox: 

v=DMARC1; p=none; rua=mailto:dmarc-reports@example.com; pct=100;

Receiving mail servers deliver all mail normally, regardless of authentication verdicts. In the background, providers like Google, Microsoft, Yahoo, and Comcast generate daily XML aggregate reports detailing every sending IP address, message count, SPF outcome, and DKIM status. Maintain this monitoring phase for at least 30 to 60 days to identify all legitimate sending services (e.g., payroll notifications, marketing automation, CRM systems, ticketing platforms).

Phase 2: Graduated Soft Enforcement (p=quarantine)

Once all legitimate sending services have been correctly authenticated with SPF and DKIM, transition to soft enforcement. Use the pct tag to apply quarantine handling to a fraction of unaligned messages initially, mitigating risk: 

v=DMARC1; p=quarantine; pct=25; rua=mailto:dmarc-reports@example.com;

Under this configuration, 25% of unaligned messages are delivered to recipient spam folders, while the remaining 75% fall back to the less restrictive action (none). Gradually advance pct from 25 to 50, 75, and finally 100 over several weeks while monitoring aggregate feedback for complaints or missed customer communications.

Phase 3: Full Enforcement & Zero-Trust (p=reject)

The final objective of DMARC implementation is strict enforcement: 

v=DMARC1; p=reject; sp=reject; pct=100; rua=mailto:dmarc-reports@example.com; aspf=r; adkim=r;

At this stage, any unauthorized email attempting to spoof your domain is blocked and dropped outright at the recipient's SMTP connection gate. Unauthenticated messages never reach the recipient's junk folder or inbox, completely neutralizing direct domain spoofing attacks.

Cross-Domain Reporting: The _report._dmarc Verification Protocol

A frequent administrative hurdle occurs when a company publishes a DMARC record on domain-a.com, but configures the aggregate reporting URI to send reports to a third-party inbox or external monitoring vendor on domain-b.com: 

rua=mailto:reports@domain-b.com

To prevent malicious actors from spamming arbitrary third-party mailboxes with millions of XML aggregate reports, RFC 7489 Section 7.1 mandates External Destination Verification. Before sending reports to domain-b.com, receiving mailbox providers check whether domain-b.com has explicitly authorized receipt by publishing a DNS TXT record at: 

domain-a.com._report._dmarc.domain-b.com   TXT   "v=DMARC1;"

If this authorization record does not exist in DNS, receiving MTAs will silently refuse to transmit aggregate reports to domain-b.com, leaving administrators blind to their telemetry data.

Common Implementation Traps and Syntax Errors

Even minor syntax anomalies in DNS records can invalidate DMARC processing across major mailbox providers:

  • Publishing Multiple DMARC Records: A domain must have exactly one DMARC record. If a DNS zone contains two TXT records starting with v=DMARC1 at _dmarc, receiving mail servers will encounter ambiguity and invalidate DMARC evaluation entirely, defaulting to no enforcement.
  • Case Sensitivity Errors in the Version Tag: The version tag must strictly be uppercase: v=DMARC1. Using lowercase v=dmarc1 violates RFC 7489 ABNF grammar and causes strict validators to ignore the record.
  • Deploying p=reject on Day One: Jumping straight to reject without monitoring aggregate reports almost always breaks critical business processes—such as HR benefits portals, external billing invoices, marketing newsletters, or automated website contact forms.
  • Ignoring the SPF 10-DNS-Lookup Limit: While DMARC itself does not have a lookup limit, SPF is restricted to a maximum of 10 DNS lookups. If your SPF record exceeds 10 lookups, SPF returns a PermError, which causes SPF alignment in DMARC to fail.
  • Omitting Semicolon Delimiters: Every tag pair must be terminated with a semicolon. A missing semicolon between tags (e.g., v=DMARC1 p=none) causes parser syntax errors.

Frequently Asked Technical Questions

What is DMARC and why is it necessary if I already have SPF and DKIM?
SPF and DKIM operate independently and validate hidden technical headers (the envelope sender and signing key domain). Neither protocol requires that the authenticated domain matches the visible From: address seen by the recipient. DMARC solves this by requiring identifier alignment between the visible From address and SPF/DKIM, while giving you central control over how unaligned emails are handled.
Where exactly do I publish this record in my DNS provider?
You must publish a DNS record of type TXT. The host/name field must be set to _dmarc (or _dmarc.yourdomain.com, depending on whether your DNS manager automatically appends your apex domain). The value field contains the formatted string generated above (starting with v=DMARC1;).
What does "p=none" actually do to incoming emails?
A policy of p=none puts your domain into passive monitoring mode. Receiving mail servers evaluate SPF and DKIM alignment, but deliver unauthenticated messages normally to the recipient's inbox without penalty. Crucially, the receiving servers generate and transmit daily aggregate XML telemetry reports back to your rua address so you can identify unauthorized senders.
Can an email pass DMARC if it fails SPF?
Yes. DMARC requires that either SPF aligns or DKIM aligns. If an email fails SPF (for example, when an email is forwarded through a mailing list or relay), but carries an intact, valid cryptographic DKIM signature that aligns with the visible From domain, the message achieves a passing DMARC verdict.
What is the difference between RUA and RUF reports?
rua designates where mailbox providers send daily XML aggregate reports summarizing total message volumes, sending IP addresses, and authentication outcomes. ruf designates destination addresses for immediate, message-by-message forensic failure reports containing the actual headers and snippets of rejected messages. Most organizations rely primarily on rua reports due to privacy redactions in ruf.
What does the "sp=" tag do?
The sp= tag specifies the subdomain policy. If omitted, all subdomains (e.g., marketing.example.com) inherit the primary policy (p=) of the apex domain. Setting sp=reject while p=none allows you to monitor your main domain while aggressively blocking spoofing attempts on unused subdomains.
What happens if I publish two DMARC records for the same domain?
Publishing multiple DMARC records under _dmarc.yourdomain.com is a critical configuration error. Receiving mail servers encountering multiple DMARC records will consider the policy ambiguous, invalidate DMARC evaluation completely, and default to treating the domain as having no DMARC policy at all.

All tag generation, string concatenation, syntax validation, and table rendering occur entirely inside your browser's local JavaScript execution context. Zero domain names or administrator reporting inboxes are transmitted across the network.
