⚠️ Limitations & Disclaimer

Headers below your own servers are claims, not evidence. Any sender can pre-write fake Received lines — invented hostnames, internal IP addresses and timestamps — into a message before it reaches you. Only the hops added by mail servers you operate, starting at your border MTA, can be trusted; treat everything beneath that boundary with suspicion, and rely on DKIM or ARC signatures for anything you need to prove. This tool also reports the SPF, DKIM and DMARC results the receiving server recorded in Authentication-Results; it does not re-check them, because it performs no DNS lookups and has no keys. Hop delays come from each server's own clock, so small discrepancies are normal. Everything runs in your browser and nothing you paste is uploaded. Results are provided as-is; BitDark.net is not liable for decisions made from them.

What This Tool Does

Every email carries a log of its own journey in its headers. Paste the raw headers here and this tool lays that journey out: each server that handled the message, in the order it actually travelled, with how long each step took, the protocol and TLS used, and the authentication results the receiving server recorded. It is the quickest way to answer "where did this actually come from, and did it pass SPF and DKIM?" — and because it runs entirely in your browser, you can paste real messages without sending their contents anywhere.

The Received Chain Reads Bottom-Up

Each mail server that touches a message prepends a Received header. The result is that raw headers are in reverse chronological order: the top Received is the last server (usually your own mail provider), and the bottom one is closest to the original sender. This tool reverses them for you, so the first row in the table is the origin and the last row is final delivery. Each line typically records which host the message came from (with its IP in brackets), which server received it by, the protocol used with, and a timestamp.

The Trust Boundary

This is the part that matters most in an investigation. A Received header is just text added by whichever machine handled the message — and a malicious sender can fabricate a whole stack of convincing-looking hops before the message ever leaves their control. So the chain is only trustworthy from your own border mail server upward. Find the first hop handled by infrastructure you operate: everything from there up was written by servers you trust, and everything below it is the sender's story. Investigators anchor on that line rather than believing the oldest hop.

Authentication Results

Modern receivers record their checks in an Authentication-Results header, and the tool surfaces those verdicts:

  • SPF — whether the sending IP was authorised to send for the envelope domain.
  • DKIM — whether the message's cryptographic signature validated, and which selector signed it.
  • DMARC — whether the message aligned with the From domain's policy, and what that policy is.

Worth repeating: these are the receiving server's recorded conclusions, parsed from the header. This tool does not repeat the DNS lookups or verify the signature itself — which is exactly how header analysis normally works, since the checks had to happen at delivery time anyway.

A Worked Example You Can Reproduce

Load the built-in sample and look at two things. First, the hop table: the rows run from the sender's internal node, through the relay gateway, to the final mail server — the reverse of the order in the raw text — each with its delay from the previous hop, so a slow queue or greylisting shows up as a jump. Second, the authentication panel: the sample's Authentication-Results line reports dkim=pass, spf=pass and dmarc=pass, and the tool pulls out the signing selector and the authorised IP from that same header. Edit the sample's spf=pass to spf=fail, re-analyse, and the verdict changes — confirming it is reading the recorded result rather than deciding one.

How to Use the Tool

  1. Get the raw headers — in Gmail, "Show original"; in Outlook, message properties; or open an .eml file.
  2. Paste them in — the whole header block, or load the sample to see the format.
  3. Read the hop table — chronological order, with delays, hosts, IPs and TLS details.
  4. Check authentication — the recorded SPF, DKIM and DMARC verdicts, then decide where your trust boundary sits.

Frequently Asked Questions

How do I read the Received headers?
Each server that handles a message adds a Received header at the top, so the raw headers run newest first — the last server is at the top and the original sender at the bottom. This tool reverses them into chronological order, so the first row is where the message started and the last is the server that delivered it to you.
Can Received headers be faked?
Yes, and this is the most important caveat. Anything below your own infrastructure can be invented by the sender: fake hostnames, internal IPs and timestamps can all be pre-written into a message. Only the Received headers added by servers you control, starting at your border mail server, are trustworthy. Treat everything beneath that line as a claim, not evidence.
Does this tool verify SPF, DKIM and DMARC itself?
No. It reads the verdicts the receiving mail server already recorded in the Authentication-Results header and displays them. It does not perform DNS lookups or check DKIM signatures cryptographically — it has no network access and no keys. So a pass shown here means the receiving server reported a pass, which is what you want to read in a header analysis.
What do the hop delays mean?
Each hop's delay is the gap between its timestamp and the previous hop's. Large gaps often point to greylisting, queueing or a backed-up relay. Because every timestamp comes from a different server's clock, small inaccuracies are normal, and if a timestamp goes backwards the tool marks it as clock skew rather than a negative delay.
Are my headers uploaded anywhere?
No. The headers you paste are parsed in your browser and nothing is sent to a server. The page makes no network request for your input, so you can analyse real messages — which often contain addresses, internal hostnames and subjects — without exposing them.
