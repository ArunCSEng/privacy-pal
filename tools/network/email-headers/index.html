How RFC 5322 Received Headers Function

Every Simple Mail Transfer Protocol (SMTP) transfer agent (MTA) handling a message prepends a new Received: header to the top of the header stack. Consequently, email traversal must be evaluated in reverse chronological order:

  • Hop 1 (Bottom): The Mail User Agent (MUA) or origin mail submission server that initially accepted the message from the author.
  • Intermediate Hops: Relay brokers, scanning filters, content inspection nodes, and outgoing smart-hosts.
  • Final Hop (Top): The destination border MX server delivering the message into the user mailbox store.
  • Header Forgery: Untrusted senders can prepend arbitrary lines before submission; only hops recorded by your own internal infrastructure can be inherently trusted without cryptographic validation.

Authentication Signatures

The Authentication-Results header records evaluation results performed by the receiving boundary MTA for SPF (Sender Policy Framework), DKIM (DomainKeys Identified Mail), and DMARC (Domain-based Message Authentication, Reporting, and Conformance).

Zero Network Egress Security Guarantee

Email headers frequently contain internal network topologies, private gateway IP addresses, user names, and operational metadata. BitDark parses raw headers entirely inside your browser's isolated JavaScript sandbox without transmitting header dumps to external endpoints.
