What This Tool Does

A syslog line looks like noise until you know where the boundaries are: a number in angle brackets, a timestamp in one of several formats, a hostname, then free text that may or may not contain structure. Paste one here and every field is pulled apart and labelled, including the arithmetic that turns the leading number into a facility and a severity. It is useful when you are reading an unfamiliar device's output, writing a parser against it, or trying to work out why a log pipeline is dropping messages.

How to Use the Tool

  1. Paste a message — a single raw syslog line into the input. Both formats are accepted: RFC 3164 beginning with something like <34>Oct 11 22:14:15, or RFC 5424 beginning <34>1 2003-10-11T22:14:15.003Z. Include the angle-bracket priority if your source emits it; without it the facility and severity cannot be derived.
  2. Or load a sample — Sample RFC 5424 shows the modern structured format, Sample RFC 3164 the older BSD one, and Sample Cisco Event a real-world vendor line that follows neither perfectly. Running all three is the fastest way to see how the formats differ in practice.
  3. Click Parse Syslog — the message is split into one row per field.
  4. Read the field table — each row gives the Header / Element Field, its Decoded Content, and the RFC Specification that defines it, so you can see which standard each part comes from rather than guessing.
  5. Start with the PRI decode — the facility tells you which subsystem produced the message and the severity how urgent the sender considered it. Those two values drive most routing and alerting decisions in a log pipeline.
  6. Check structured data on RFC 5424 messages — the bracketed elements carry machine-readable key-value pairs, which are far more reliable to parse than scraping the free-text message.

If a message does not parse, the usual causes are a missing PRI value, a relay having rewritten the timestamp, or a vendor format that only resembles the standard.

The PRI Value: Two Numbers in One

Every syslog message starts with a priority value in angle brackets, and it encodes two separate things. Divide by eight for the facility; the remainder is the severity.

Take <34>. 34 divided by 8 is 4 with a remainder of 2. Facility 4 is security and authorisation messages; severity 2 is critical. So before reading a single word of the message text you know it is a critical authentication event. The tool performs this calculation and names both halves, which saves looking up two tables every time.

The Two Formats

RFC 3164 is the original BSD layout, and it is still everywhere on network hardware. Its timestamp is a bare Mmm dd hh:mm:ss with no year and no time zone, the hostname is a single token, and everything after that is unstructured text. It is compact and easy to emit, which is why it persists, but the missing year and zone make correlating old entries across regions genuinely painful.

RFC 5424 fixed those gaps. It adds a version number after the PRI, a full ISO 8601 timestamp with time zone and fractional seconds, separate fields for application name, process ID and message ID, and optional structured data — bracketed key-value elements designed to be parsed reliably instead of pattern-matched out of prose.

Frequently Asked Questions

What is the difference between RFC 3164 and RFC 5424?
RFC 3164 is the older BSD format: a priority value, a timestamp with no year or time zone, a hostname and a free-text message. RFC 5424 replaced it with a structured format that adds a version number, full ISO 8601 timestamps with time zone and fractional seconds, explicit application and process identifiers, a message ID, and optional structured data fields.
How is the PRI value decoded?
The number in angle brackets at the start packs two values. Divide it by 8 and you get the facility; the remainder is the severity. So PRI 34 gives facility 4, which is security and authorisation messages, and severity 2, which is critical. The tool does this arithmetic and names both halves.
What do the severity levels mean?
They run from 0 to 7: emergency, alert, critical, error, warning, notice, informational and debug. Lower is more urgent, which catches people out — severity 0 is the most serious, not the least. Most production logging filters at notice or informational to keep volume manageable.
Why do RFC 3164 timestamps have no year?
The original BSD format assumed logs were read close to when they were written, so it records only month, day and time, with no year and no time zone. That makes old entries ambiguous and complicates correlation across regions, which is one of the main reasons RFC 5424 moved to full ISO 8601 timestamps.
Is my log data uploaded anywhere?
No. The message you paste is parsed in your browser and nothing is sent to a server. The page makes no network request for your input, so you can inspect real log lines — which often contain hostnames, usernames and internal addresses — without exposing them.
