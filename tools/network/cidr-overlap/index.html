What This Tool Does

When you plan addressing across several networks — subnets in a routing table, VPCs you want to peer, ranges handed to different teams — two blocks must not cover the same addresses unless you mean them to. An accidental overlap makes routing ambiguous and blocks cloud peering. Paste a list of CIDR blocks and this tool compares every pair and reports the ones that conflict, so you can catch the problem while it is still a line in a spreadsheet. It runs in your browser; nothing you enter is sent anywhere.

How to Use the Tool

  1. Paste your blocks — one CIDR per line in CIDR Prefixes to Audit. IPv4 and IPv6 can be mixed in the same list; they are only ever compared within their own family.
  2. Or load the sample — Load Sample Conflict drops in a list that already contains a containment and a duplicate, so you can see both result types before using your own data.
  3. Click Analyze Collisions — every pair in the list is compared, so a list of twenty blocks is 190 comparisons done at once.
  4. Read the results table — Primary Subnet (A) and Conflicting Subnet (B) name the two blocks that clash, Conflict Type says whether it is a duplicate or a containment, and Details & Topology shows how the ranges sit relative to each other.
  5. Fix and re-run — delete a duplicate or renumber a block, then analyze again until the list reports nothing. Clear Workspace starts over.

Blocks that merely sit next to each other are reported clean, which is correct — adjacency is not overlap, as the integer ranges above show.

Overlap Is Just Interval Arithmetic

Every CIDR block covers a contiguous run of addresses, and an address is really just a number. So the tool converts each block into a numeric range — a first and a last value — and compares those. Two blocks share at least one address exactly when each one starts at or before the other one ends.

Spelling that out with real numbers makes it obvious. As 32-bit integers:

BlockFirst addressLast addressSize
10.0.0.0/1616777216016783769565,536
10.0.5.0/24167773440167773695256
10.1.0.0/1616783769616790323165,536

The /24 starts at 167773440 and ends at 167773695, both comfortably inside the first /16's 167772160–167837695 — so they overlap. Treating addresses as integers is also what makes IPv6 work the same way; those values are simply much larger, so the tool handles them as big integers rather than ordinary numbers.

Adjacent Is Not Overlapping

Look at the third row again. 10.0.0.0/16 ends at 167837695 and 10.1.0.0/16 begins at 167837696 — exactly one address later. They sit flush against each other and share nothing, so they do not conflict. This is the single most common false alarm when people check ranges by eye: 10.0.0.0/24 and 10.0.1.0/24 look like they must collide because the text is so similar, but there is no shared address between them. The tool compares numbers rather than appearances, so it never makes that mistake.

Why a "Half" Overlap Cannot Happen

Here is a property worth knowing, because it tells you what to expect from any conflict report. A CIDR block is not an arbitrary range: its size is always a power of two and it is aligned to a multiple of that size. That alignment has a strong consequence — two valid CIDR blocks are always either completely separate, or one lies entirely inside the other. They can never half-overlap the way two arbitrary ranges like 10–20 and 15–25 can.

You can convince yourself with the numbers above: the /24 fits wholly within the /16, and the second /16 sits wholly outside it. Trying to construct a counterexample fails every time; the alignment rule forbids it. The practical upshot is that every conflict you see here will be either a duplicate (identical ranges) or a containment (one inside the other), and "containment" is the normal shape of a real-world mistake — someone carves a /24 out of a space another team already holds as a /16.

Where Overlaps Actually Bite

  • Cloud peering. Two VPCs or VNets with overlapping CIDRs generally cannot be peered at all. The provider refuses the connection outright, and because the ranges were chosen months earlier, the fix is usually an expensive renumbering.
  • VPN and transit links. If a remote site uses a range that your local network also uses, traffic for those addresses never leaves the local side — the route matches locally and the tunnel is simply never used.
  • Ambiguous routing. When two entries both match a destination, longest-prefix match decides, not your intent. A forgotten /24 inside a /16 silently steals traffic for its 256 addresses.
  • Firewall and ACL drift. Overlapping definitions make rules order-dependent, so a permissive entry can quietly shadow a restrictive one.

A Worked Example You Can Reproduce

Paste this list and run the check:

10.0.0.0/16
10.0.5.0/24
10.1.0.0/16
192.168.0.0/24
192.168.0.0/24

Two conflicts come back. 10.0.0.0/16 and 10.0.5.0/24 are a containment — the ranges above show the /24 sitting inside the /16. The repeated 192.168.0.0/24 is an identical pair, which is the kind of duplicate that creeps into a list after a copy-paste. 10.1.0.0/16 is reported clean: it is adjacent to the first /16, not overlapping. Add 2001:db8::/32 and 2001:db8:1::/48 and you will get a third conflict, since the /48 sits inside the /32 — the same containment logic, applied to 128-bit addresses.

Resolving a Conflict

Once you know which pair clashes, there are only a few honest fixes. If the entry is a duplicate, delete it. If a smaller block sits inside a larger one and that was deliberate — a subnet carved from a parent range — keep it, but record it as a child rather than a peer so it is not double-allocated. If it was not deliberate, renumber the newer block into free space, or split the parent so the two no longer share addresses. Re-run the check after each change; a list that reports nothing is one you can hand to whoever provisions it.

Frequently Asked Questions

What counts as an overlap between two CIDR blocks?
Two blocks overlap when they share at least one address. That happens when one block contains the other (for example 10.0.0.0/16 contains 10.0.5.0/24), when they are identical, or when their ranges partially intersect. The tool reports all three; blocks that sit next to each other without sharing an address, like 10.0.0.0/24 and 10.0.1.0/24, do not overlap.
Why do overlapping subnets cause problems?
Overlapping ranges make routing ambiguous: a destination address can match more than one entry, and the result depends on longest-prefix match and local policy rather than your intent. In cloud networking, two VPCs or VNets with overlapping CIDRs usually cannot be peered, and VPN or transit setups fail or route unpredictably. Finding overlaps before provisioning avoids these conflicts.
How does the tool decide whether two blocks overlap?
It converts each CIDR to the numeric range of addresses it covers — a first and last value — and two blocks overlap when the first of each is less than or equal to the last of the other. Using numeric ranges makes the check exact for both IPv4 and IPv6, with IPv6 handled as 128-bit big integers.
Can two CIDR blocks overlap only partially?
No, and this surprises people. Because every CIDR block is an aligned, power-of-two sized range, two valid blocks are always either completely separate or one sits entirely inside the other — a half-and-half overlap is impossible. So in practice every conflict this tool reports is either a duplicate or a containment.
Can it check IPv4 and IPv6 together?
It parses both, but an IPv4 block and an IPv6 block never overlap — they are separate address spaces. Overlaps are only reported within the same family, so you can paste a mixed list and the tool compares IPv4 against IPv4 and IPv6 against IPv6.
Is my list uploaded anywhere?
No. The CIDR blocks you paste are parsed and compared in your browser, and nothing is sent to a server. The page makes no network request for your input, so you can check internal addressing plans without exposing them.
